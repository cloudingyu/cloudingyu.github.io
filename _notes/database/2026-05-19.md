## 一、事务的基本概念

### 1.1 什么是事务

**事务**（Transaction）是构成单一逻辑工作单元的操作的集合。一个事务包含对数据库的一系列操作，主要是**读操作**（对应 SQL 中的 `SELECT`）和**写操作**（对应 SQL 中的 `INSERT`、`UPDATE`、`DELETE`）。

事务是数据库系统实现中非常关键的概念。尤其是关系数据库之所以能够持续发展至今，一个最关键的因素就是它可以用于对金融资产的管理，能够保证所有数据都是正确的。

### 1.2 为什么需要事务 -- 银行转账的例子

以一个银行转账为例：从账户 A 转 50 元到账户 B，涉及的操作序列是：

1. 读账户 A 的余额
2. 将 A 的余额减 50，写回
3. 读账户 B 的余额
4. 将 B 的余额加 50，写回

**问题**：程序在执行过程中的任何一个时刻都有可能突然中断（系统宕机、内存溢出等）。如果在第 2 步执行完后系统崩溃，A 已经扣了 50 元，但 B 还没来得及加上 50 元——这笔钱就凭空消失了。

因此事务中的这些操作必须是同时成功或同时失败，不能执行到一半就结束，部分成功部分失败是不可接受的。

### 1.3 事务的边界

- **Begin Transaction**：标记事务的开始。在有的系统中，程序一旦开始访问数据库，就自动开始一个新的事务。
- **Commit**：事务执行成功，提交。此时对数据库的所有修改都被写入磁盘，数据库进入一个新的正确状态。
- **Rollback**：事务执行不成功，回退。将对数据库做的所有修改全部撤销，数据库恢复到事务开始前的正确状态。

### 1.4 事务的 ACID 特性

事务具有四个基本性质，简称为 **ACID**：

| 特性 | 英文 | 含义 |
|------|------|------|
| **原子性** | Atomicity | 事务是不可分割的工作单元，要么全部成功，要么全部失败 |
| **一致性** | Consistency | 事务的执行使数据库从一个正确状态变为另一个正确状态，数据不会遭到破坏 |
| **隔离性** | Isolation | 多个事务并发执行时，其结果应与每个事务单独执行的结果相同 |
| **持久性** | Durability | 事务一旦提交，其对数据库的所有更新都是持久的，已写入硬盘 |

ACID 这四个性质是数据库最基本的要求。

对于隔离性（Isolation），并发控制的正确性评估方法非常简单：
- 如果多个事务并发执行的结果与它们串行（单独）执行的结果相同，就是正确的；
- 如果做不到这一条，就是不正确的。

### 1.5 事务的状态变迁

事务在其生命周期中经历以下状态：

```
活跃 (Active) -> 部分提交 (Partially Committed) -> 已提交 (Committed)
                 -> 失败 (Failed) -> 中止 (Aborted)
```

- **活跃状态**：事务正在执行
- **部分提交状态**：事务中的操作已完成，准备提交
- **已提交状态**：事务成功完成，修改已固化到磁盘
- **失败状态**：发现事务无法正常完成
- **中止状态**：事务回滚，数据库恢复到事务开始前的状态

事务的终止有两种情况：
1. **程序自主终止**：程序内部由于某些条件（如账户余额不足）主动执行 rollback
2. **系统代为终止**：程序执行到中间时突然中断，系统自动帮事务执行 rollback

### 1.6 分布式事务与两阶段提交

当数据库运行在多个节点上（分布式环境）时，一个事务可能分布在多个节点上执行。每个节点独立知道自己是否执行成功，但互相不知道对方的状态。

**两阶段提交**（Two-Phase Commit, 2PC）是早期解决分布式事务提交问题的经典方法。

#### 基本思想

在多个节点之上有一个**协调者**（Coordinator），负责管理所有参与者节点的提交过程。类似于 Hadoop 中的 NameNode。

#### 两个阶段

**阶段一：投票/询问阶段**

协调者向所有参与者节点发送询问："你们是否可以提交？"

- 如果某个节点的操作已顺利执行完，回复"同意提交"
- 如果某个节点的操作出错（如余额不足），回复"终止"

**阶段二：提交/回滚阶段**

协调者收到所有参与者的反馈后：
- 如果**所有参与者都同意提交**，向所有节点发送 Commit 命令
- 如果**有一个参与者回复终止**，向所有节点发送 Rollback 命令

各参与者收到命令后，执行对应的 commit 或 rollback 操作。

#### 2PC 的问题

1. **同步阻塞**（Synchronous Blocking）：参与者在等待协调者投票和最终决策的过程中，事务并未结束，仍然占着系统资源（内存、锁等），造成资源浪费。

2. **单点故障**（Single Point of Failure）：协调者至关重要，一旦协调者发生故障，整个提交流程就卡住了。虽然有备份机制，但备份与主协调者之间存在信息差。

3. **数据不一致**：在第二阶段，协调者发出 commit 请求后，可能由于局部网络异常，只有部分参与者收到 commit 命令并提交，另一部分没有收到。此时数据处于不一致状态。

两阶段提交是分布式数据库中长期以来使用最多的提交方法，但它仍然存在一些实际上难以解决的问题。

此外，如果协调者在发出 commit 之后宕机，且唯一接收到该信息的参与者也同时宕机，那么整个事务的状态就变得不可知。

## 二、CAP 定理

### 2.1 CAP 定理的提出

在分布式环境下，2000 年发表的一篇著名文章提出了 **CAP 定理**（CAP Theorem），阐述了分布式系统中三个基本需求的不可兼得性。

### 2.2 CAP 的三个维度

| 维度 | 英文 | 含义 |
|------|------|------|
| **一致性** | Consistency | 同一时刻，所有数据副本的值完全相同 |
| **可用性** | Availability | 即使部分节点发生故障，系统仍然能够响应客户端的读写请求 |
| **分区容忍性** | Partition Tolerance | 当网络发生分区（节点之间无法通信）时，系统仍能对外提供服务 |

### 2.3 CAP 不可兼得

ACID 在集中式环境下是同时成立的，但在分布式环境下，CAP 的三条是无法做到同时成立的。

**直观理解**：假如网络分区后两边不能通信，而数据有多个副本分散在两个分区中。如果还要求系统继续提供服务（可用性），那就无法保证两个分区里数据副本的值保持一致（一致性）。

### 2.4 三种权衡策略

| 策略 | 保留 | 放弃 | 说明 |
|------|------|------|------|
| CA | 一致性 + 可用性 | 分区容忍性 | 一旦发生分区，只能在各分区内部保证 CA |
| CP | 一致性 + 分区容忍性 | 可用性 | 一旦发现分区，为了保证数据一致性，可能终止服务 |
| AP | 可用性 + 分区容忍性 | 一致性 | 分区后两个分区继续工作，但数据可能不一致 |

**AP 策略的典型应用**：许多 NoSQL 数据库采用 AP 策略。

在 AP 策略下，同一个时刻对同一个数据，两个不同的事务可能读到不一致的值。这在银行系统中是不能容忍的。所以实际应用系统中会有很多层检测——比如银行每天会对所有交易做层层审查，一旦发现错误，在业务层面进行恢复。

## 三、BASE 理论

### 3.1 BASE 的动机

既然 CAP 三条无法同时成立，BASE 理论就是对 AP（牺牲强一致性）的一种实践延伸，探讨如何在分布式系统中尽可能实现较高的一致性。

### 3.2 BASE 的三条

| 原则 | 英文 | 含义 |
|------|------|------|
| **基本可用** | Basically Available | 分布式系统出现故障时，允许损失部分可用性，但保证核心可用 |
| **软状态** | Soft State | 允许系统的数据存在中间状态，不同副本之间的同步可以有一定延时 |
| **最终一致性** | Eventual Consistency | 系统的各个副本经过一段时间后，最终会达到一致状态 |

**基本可用**的典型例子：电商大促时，访问量激增，系统可能会将部分用户引导到降级页面，限制连续操作频率（如要求等十分钟再做下一个操作）。这本质上是"降低服务"以保护核心功能。

**软状态**：允许副本同步有一定延时（如允许一秒钟的延迟），这样一旦出问题，只需处理最后一秒的数据即可。

**最终一致性**：强调系统运行过程中可能存在不一致，但经过一段过程后最终会达成一致。这与软状态的区别在于，最终一致性更多是由系统故障造成的，而软状态更多是由网络通信延迟造成的。

### 3.3 一致性等级

| 等级 | 说明 |
|------|------|
| **强一致性** | A 写入一个值后，所有后续操作（A、B、C 等）读到的都是最新值 |
| **弱一致性** | A 写入后，系统不能保证后续操作立刻读到最新值，存在时间窗口 |
| **最终一致性** | 保证经过一段时间后，所有副本最终一致 |
| **因果一致性** | 如果 A 和 B 之间有业务相关性，A 更新后 B 读到的一定是新的；没有相关性的不保证 |
| **会话一致性** | 在同一个客户端会话内，保证读到的值是一致的；不同会话之间不保证 |
| **单调读一致性** | 如果已读到某值，后续操作不会读到更早的值 |

这些一致性等级实际上都是针对实际应用场景和实际事务的结构关系，做一定程度的弱化，让系统能够在分布式环境下尽可能得到比较正确的值。

## 四、Paxos 算法简介

### 4.1 背景

在最近几年，国产数据库（如华为 GaussDB）在分布式事务管理中大量使用 **Paxos** 算法作为事务提交的模型。

### 4.2 基本思想

Paxos 将所有角色分为三类：

| 角色 | 英文 | 职责 |
|------|------|------|
| **提议者** | Proposer | 产生新的值（提案），发起修改 |
| **接受者** | Acceptor | 系统的多个副本，代表数据存储节点 |
| **学习者** | Learner | 读取数据的客户端，不参与决策过程 |

**核心原则**：当提议者提出修改后，需要多数副本（大于一半）都接受了该修改，这个修改才算成功。Learner 在读取时会检查该修改是否已被大多数副本接受——如果已达成多数共识，就可以安全读取新值。

## 五、数据库恢复机制

### 5.1 为什么需要恢复

数据库系统无法保证不出错：
- 机器在跑数据库时突然断电或死机
- 灾难性事件（如 911 事件——当时被撞的两栋楼里有很多银行的数据库）

911 之后人们开始高度重视数据库的备份和恢复。虽然无法事先保证数据库不出错，但可以通过一套机制，保证机器被损毁时数据不丢失。这最多就是中断一段时间业务而已。

### 5.2 数据访问的完整流程

回顾数据处理的整个链路：

```
事务请求 -> 事务工作区（内存）-> 磁盘缓冲区 -> 硬盘
```

1. 事务提出读请求
2. 数据库管理系统（DBMS）首先检查所需数据是否在**事务工作区**（内存）中
3. 如果在内存中，直接处理
4. 如果不在内存中，需要到**磁盘缓冲区**中读
5. 如果磁盘缓冲区也没有，从**硬盘**读入缓冲区，再调入内存
6. 在内存中完成处理后，再将修改写回硬盘

**写操作的两步过程**：
- 在内存中执行修改
- 由一个独立的进程（通常叫 **IO Agent**）负责将内存中的修改异步写入硬盘
- 这两个步骤之间不是完全连续的，是异步过程

IO Agent 相当于一个第三方程序，它不断检查内存里哪些数据被修改了但还没写到硬盘，一旦发现就将其写入硬盘。

### 5.3 恢复的基本原则 -- 冗余

恢复的核心方法是**冗余**（Redundancy），具体实现主要依赖两大类手段：

1. **转储（Dump）/备份（Backup）**：定期（如每天）将整个数据库做一个拷贝，存放到磁带、光盘等介质上
2. **日志（Log）**：记录对数据库的每次修改

### 5.4 故障分类

| 故障类型 | 说明 | 是否涉及磁盘 |
|----------|------|-------------|
| **事务故障** | 运算溢出、存款余额透支等逻辑错误 | 否 |
| **系统故障** | 主板故障、内存故障等硬件问题，但磁盘完好 | 否 |
| **介质故障** | 磁盘本身发生损坏 | 是 |

对于前两种故障（磁盘未损坏），只需依靠日志进行数据恢复；对于介质故障，需要先用备份恢复，再结合日志恢复。

## 六、日志（Log）

### 6.1 日志的作用

日志记录了所有对数据库的修改操作，包括：
- 事务的开始和结束信息
- 每次数据的**插入、删除和修改**操作
- 每条元组**修改前**（before image）和**修改后**（after image）的状态

日志记录了对数据库的每次修改。当系统崩溃后重启时，通过日志就能知道哪些操作做了、哪些没做，然后把需要撤回的撤回、需要重做的重做。

### 6.2 为什么先写日志而不是先写数据库文件

数据库在硬盘上有两类数据：
1. **日志**：记录所有修改操作
2. **数据库文件**：表的实际数据

**关键设计原则**：对数据库的所有修改，**先写日志（WAL，Write-Ahead Logging），再写数据库文件**。

**原因**：
- 写日志是**连续写**（在一个文件末尾追加），速度非常快，与内存写的速度相差不大
- 写数据库文件是**随机读写**，效率非常慢
- 先写日志能尽快将修改固化到硬盘（不易失）
- 等系统有空时，再从日志中将修改同步到数据库文件

### 6.3 Commit 的实质

当执行 commit 时，实际上是将对数据库的修改**先写到日志中**（而未必写到了数据库文件中）。只要已写到日志（在硬盘上），就代表修改已经被永久存储了。至于什么时候将修改同步到数据库文件，由数据库管理系统自己决定。

因此在事务提交的时候，对数据库的修改不一定已经写到数据库文件里了，但日志在硬盘上，信息就已经保存下来了。

### 6.4 补偿日志

在执行 undo（回滚）操作时，也会把撤销操作记录到日志中。这样即使在做恢复的过程中系统又崩溃了，重启后也能知道哪些撤销动作已经做过，从而继续完成恢复。

## 七、检查点（Checkpoint）

### 7.1 检查点的作用

**检查点**是一个工程上的实现手段。数据库处理过程在内存中进行，修改不一定立即写入硬盘。

检查点定期执行以下操作：
- 将所有需要写入硬盘的数据全部写到硬盘
- 可以理解为内存和硬盘之间的**一次强制同步**

检查点在某种程度上是内存和硬盘之间的一个同步过程。一旦到达检查点，就一定保证对数据库的修改全部落到硬盘上。

### 7.2 检查点与事务恢复的关系

假设有五个事务（T1-T5）和一个检查点，系统在故障点发生崩溃：

| 事务 | 与检查点的关系 | 故障时的状态 | 恢复策略 |
|------|---------------|-------------|----------|
| T1 | 检查点之前就执行结束 | 已完成 | **无需任何操作**（在检查点时所有修改已固化） |
| T2 | 检查点前开始，检查点后结束（已 commit） | 已提交 | **Redo（重做）**：将对数据库文件的修改重新做一遍 |
| T3 | 检查点前开始，故障时未结束 | 未提交 | **Undo（撤销）**：撤销已做的修改 |
| T4 | 检查点后开始，故障前结束 | 已提交 | **Redo（重做）** |
| T5 | 检查点后开始，故障时未结束 | 未提交 | **Undo（撤销）** |

**为什么 T2 和 T4 已 commit 还需要 Redo？**
- Commit 只保证日志已写硬盘，但不保证数据库文件已更新
- 如果崩溃时修改还没从日志同步到数据库文件，就需要重做一遍

## 八、ARIES 恢复算法

### 8.1 概述

**ARIES**（Algorithm for Recovery and Isolation Exploiting Semantics）是目前大多数数据库系统采用的标准恢复算法，虽各有细微差异，但基本过程一致。

### 8.2 ARIES 的三个步骤

1. **分析（Analysis）**：扫描日志，确定崩溃时各个事务的状态——哪些已提交、哪些还在活跃中
2. **Redo（重做）**：将已提交但尚未写入数据库文件的操作重新执行一遍，使数据库达到崩溃前的状态
3. **Undo（撤销）**：将未提交的事务对数据库做的所有操作全部撤销

### 8.3 ARIES 的三个原则

| 原则 | 内容 | 说明 |
|------|------|------|
| **1. 先写日志** | 写数据库之前先写日志 | 保证所有修改都有日志可循 |
| **2. Redo 时重做** | 重做已提交但未写入数据库文件的操作 | 恢复数据库到崩溃前状态 |
| **3. Undo 时记日志** | 执行 Undo 时也将操作记录到日志 | 确保恢复过程本身是可恢复的 |

### 8.4 日志的结构

一条日志记录通常包含：
- **事务 ID**：标识属于哪个事务
- **日志类型**：操作类型（insert/update/delete/commit/abort 等）
- **页 ID**：修改了哪个数据页
- **Before Image**：修改前的状态
- **After Image**：修改后的状态
- **Transaction Table**：将同一事务在各处的操作串联起来

### 8.5 恢复实例

一个典型的日志序列可能是：

```
检查点 -> T1 update P1 -> T2 update P5 -> T1 update P5 -> 
T1 abort（撤销T1对P5的修改）-> T3 update P1 -> T2 update P5 -> 
系统崩溃！
```

重启后分析日志：
- 发现 T2 和 T3 都没有提交，但它们对数据库做了修改 -> 需要 **Undo** T2 和 T3 的操作
- 如果再次崩溃，由于 undo 操作也已经记录在日志中，重启后可以知道哪些操作已经处理过、哪些还没处理，继续执行

### 8.6 介质故障恢复（数据库文件损坏）

当磁盘（数据库文件）损坏时：

1. 首先从**最近的备份**中恢复数据库
2. 然后根据备份之后到故障发生时刻之间的**日志**，在恢复的数据库上一步步重做修改
3. 最终恢复到故障前的状态

最严重的灾难是日志丢失。数据库每晚会有备份，但日志没有备份。一旦磁盘上日志区域损坏，是最大的灾难。

### 8.7 日志的保护

**热备（Hot Standby）**：同时把数据库修改的日志在另外一台机器上也做备份。即使原机器的日志丢失，还可以从备用机器恢复。

此外，在应用系统层面也会做业务日志。例如 ATM 机内部有一大卷纸，把所有操作都记录在纸上——即使数据库出问题，也可以通过业务日志重建。

## 九、备份策略

### 9.1 备份的基本概念

数据库一般会定期备份。备份分为：

| 类型 | 说明 |
|------|------|
| **冷备（Cold Backup）** | 定期将数据库完整复制到磁盘/光盘/磁带等介质上 |
| **热备（Hot Backup）** | 另有一台备用计算机，主库的所有操作实时同步到备库 |

热备的好处：主数据库一旦发生损毁，备份机马上可以起来接替工作，效率更高。

### 9.2 增量备份与差异备份

| 策略 | 说明 | 例子 |
|------|------|------|
| **增量备份（Incremental Backup）** | 每天只备份发生变化的数据页，没有变化的页面不备份 | 周一全量，周二只备周二变化的部分，周三只备周三变化的部分 |
| **差异备份（Differential Backup）** | 记录最终值与初始值的差异，而不是每次变化的中间过程 | 如果两天共取了 20 块钱，只记录"取了 20 块钱"，不记录每天的十块 |

### 9.3 两地三中心

国家对重要信息系统（如证券交易系统）有"两地三中心"的要求：
- 在**同一个城市**有两套服务器（如陆家嘴 + 外高桥），且距离足够远
- 在**另一个城市**（如北京）还有第三套
- 这样不管遇到什么样的灾害，系统仍然可以正常运行

### 9.4 热备的演进

在新的分布式数据库架构中（如 GaussDB），备份数据库本身也可以成为提供服务的一部分——备份被天然地集成到分布式副本机制中，效率更高。

### 9.5 SQL 对事务的支持

在 SQL 中，事务通过以下语句管理：

```sql
BEGIN TRANSACTION;  -- 开始事务
-- 一系列 SQL 操作（SELECT, INSERT, UPDATE, DELETE）
COMMIT;              -- 提交事务
-- 或
ROLLBACK;            -- 回滚事务
```

## 十、闪回技术（Flashback）

### 10.1 闪回的概念

随着内存越来越大，数据库会把大量日志放在内存中。华为 GaussDB 实现了一个叫**闪回**（Flashback）的功能。

闪回就是利用内存中的日志，可以"回到过去"查看数据的历史状态。例如要查看某个账户昨天晚上的余额——通过反向回滚从昨晚到现在中间对该数据的所有修改操作，就可以得到昨晚的状态。

### 10.2 闪回 vs 多版本

多版本（Multi-Version）机制也能实现类似效果，但需要存储大量历史数据，真正做起来成本较高。而闪回直接利用日志回滚计算，因为日志本身比数据库小很多，效率更高。

华为 GaussDB 在这个方面有它的特点：当某台机器发生 crash 时，它的日志在另外机器的内存里也有，一旦恢复时直接拿另外机器的内存来恢复即可。这是对日志结合系统架构的一种灵活应用。

### 10.3 日志作用的扩展

随着 **LSM-Tree**（Log-Structured Merge-Tree）等存储架构的出现，日志在数据库中发挥的作用越来越大——不仅仅是用于故障恢复，还可以支持时间旅行查询、闪回等高级功能。

## 核心总结

ACID 是集中式数据库的基石，正是由于 ACID 的存在，使得对重要资产的管理才成为可能，数据库才获得了用户的信任。在分布式环境下，通过 CAP 和 BASE 来做权衡，尽可能在分布式平台上实现比较高的数据一致性。
