## 一、并发问题的提出与概念回顾 [00:05:51–00:07:48]

本节是一次习题课。助教开场后没有直接进入题目，而是先把上周讲过的机制快速过了一遍，用他的说法，这是为了让大家在做题之前先明确"我们要处理的到底是一个什么样的问题"。

### 1.1 并发要解决的核心问题

助教把整门课里并发这一部分的问题定位为一句话：在多线程的任务环境下，不可控的调度会导致程序执行的结果出现不确定的情况，所以我们要用一些机制去保证它的正确性。

这里的关键词是"不可控"和"不确定"。线程什么时候被切换、切换到哪里，都不是程序能决定的；同一段代码跑两遍，结果可能不同。并发控制要做的，就是在这种不可控的调度之上，用额外的机制把结果重新钉死成唯一正确的那个。

助教说，幻灯片上把几个相关概念都写出来了，大家上课时都学过，这里再提一下，其中**临界区**（critical section）比较好理解，而**竞争条件**（race condition）值得多关注一下。

### 1.2 临界区与竞争条件

与它配套的概念是**临界区**（critical section）：一段访问共享资源、同一时刻只应允许一个线程在其中执行的代码。助教没有展开这一条，只说"临界区比较好理解"，重点放在竞争条件上。

**定义**：竞争条件。多个线程同时进入同一个临界区、试图更新同一个共享资源时，程序的结果依赖于线程实际执行的顺序；某些执行顺序会导致错误结果，这种情形称为竞争条件。这是幻灯片上给出的表述，助教在课堂上特别强调其中"依赖执行顺序"这一点。

助教对竞争条件的解释落在"顺序"两个字上：它的意思其实就是这个程序的结果依赖于所谓的线程执行的顺序，也就是说某些执行顺序可能会造成一个错误。

紧接着他做了一个容易被人忽略的澄清，这一点在后面所有题目里都要用到：

> **老师强调**：这里说的"同时"，指的不是物理时间上严格意义上的同时，重点还是落在执行顺序上——不一定是完全同进同出。

也就是说，两个线程在真实的时钟上可能一前一后，但只要它们的操作在临界区里发生了交错（一个读到旧值、另一个还没写回），就构成了竞争条件。判断有没有竞争，看的是操作的相对次序，而不是看两个核是不是在同一纳秒执行。

### 1.3 死锁不是"在等资源"

**定义**：死锁。多个线程相互等待对方已经占有的资源，形成等待环，导致谁也无法继续执行的状态。

助教在这里专门区分了一个点，因为很多同学会把"线程在等一个资源"直接叫成死锁：

> **老师强调**：一个线程在等待一个资源，这个状态不一定就是死锁。正常的锁是可以解除的；而死锁一定要有一个永久的阻塞，是永久无法自行打破的等待关系。

换句话说，判断是不是死锁，要问的不是"有没有人在等"，而是"这个等待关系能不能自己解开"。等一把别人马上就会释放的锁，只是阻塞；而几个人各持一把、又都在等对方手里那把，谁也不肯先放，才是死锁。

### 1.4 同步与互斥的分工

回顾的最后是"解决并发的关键"这一页，助教把它拆成两件事：

- **同步**：讲的是先后顺序问题，即哪个操作必须先做、哪个操作必须后做。
- **互斥**：讲的是共享资源的顺序访问问题，即同一时刻控制谁能访问这个资源。

他特别补了一句，同步是"在这个先后顺序上"做约束，互斥是"去控制谁能访问资源"，两者管的东西不一样，不能互相替代。这一区分在后面每一道题里都会反复用到：一个信号量到底是同步信号量还是互斥信号量，取决于它管的是"次序"还是"独占"。

## 二、互斥与同步的实现机制 [00:07:49–00:10:11]

### 2.1 互斥的三条实现途径

助教说，互斥的实现这里提到了三个：禁止中断、硬件指令、操作系统的机制。

第一种是**禁止中断**（interrupt disabling）。它的做法是暂时阻止一个 CPU 被普通的中断去抢占。助教强调它的适用范围很窄：顶多是在单处理器的内核场景下，用来保护一些极短的关键操作。它不是一个通用的多核互斥手段，原因是去直接禁止一个 CPU 核心的中断，并不能阻止其他核心对这个共享数据的访问——你把本核的时钟中断关了，另一个核照样能读能写那块内存。

第二种是硬件指令，也就是 **TestAndSet**（测试并置位）。它的思路是把"检查"和"修改锁"这两个动作合成一个不可分割的原子操作：读一下锁的旧值，同时把它置成"已占用"，这两件事在一条指令里完成，中间不会被插进来。助教的原话是"把这个检查和修改锁的操作让它不可分割"。

第三种是操作系统的机制，助教举了两个例子：**自旋锁**（spinlock）和 **futex**（fast userspace mutex，快速用户态互斥量）。

### 2.2 自旋锁与 futex 的代价

自旋锁比较简单，它一直在循环等待那个资源。助教给出了它的两面：

- 优点是锁一释放，它就能尽快地获得资源——因为它本来就在那儿反复检查，中间没有一次线程切换的开销。
- 缺点也很明显：它会不断地占用 CPU 的资源，白烧时间片。

futex 是 Linux 中使用的一种同步机制。助教讲了它常见的实现方式：没有锁竞争的时候，在用户态就把操作完成了；只有发生锁竞争、确实需要等待的时候，才进入内核。这样绝大多数加解锁都避开了系统调用的开销。讲到这里他说这一部分大家可以自己去了解一下，没有展开。

### 2.3 同步的两类实现：条件变量与信号量

同步的实现主要就是两个：条件变量和信号量。

**条件变量**（condition variable）的做法是：一个线程等待某个条件成立，另一个线程在修改状态之后再发出一个通知，去通知前面那个线程。助教说，这两个线程之间就是通过"通知"这个操作联系起来的。

**信号量**（semaphore）是本次课的重点。助教的表述是：用计数器以及原子的等待、通知操作，去管理资源数量和线程之间的执行关系。他补充说，通过信号量可以直接实现互斥和同步这两件事。

这句话值得拆开看，因为它解释了为什么后面所有题目都只用信号量一种工具：

- "计数器"对应资源数量——剩几个空位、还剩几个资源可取，都能用一个整数表示；
- "原子的等待/通知"对应执行关系——谁先谁后、谁能进谁要等，靠 P/V 这一对原语排定；
- 因为互斥本质上是"资源只有一份"的特殊情形（计数器的值域退化为 0 和 1），所以互斥也能用信号量表达。

## 三、三类经典问题与"四步法" [00:10:15–00:11:28]、[00:14:50–00:15:14]

### 3.1 三类经典问题及其定位

助教明确了本次课的练习范围：练习信号量，主要是理解三类经典问题——生产者-消费者、读者-写者、哲学家就餐。前两个是重点。

三类问题的课堂定位如下：

| 问题 | 核心矛盾 | 课堂定位 |
|------|----------|----------|
| 生产者-消费者 | 缓冲区满时不能继续生产，空时不能继续消费 | 重点，必须完全掌握 |
| 读者-写者 | 写完之后读者才能读；多个读者可并发读，写者必须独占 | 重点，必须完全掌握 |
| 哲学家就餐 | 多个参与者同时竞争有限资源，可能形成环状等待 | 考的概率一般比较低，本质是死锁条件的综合分析题 |

### 3.2 生产者-消费者：满与空

助教说这个问题从名字上就很容易理解：一个去生产资源，一个去消费资源。它的核心矛盾就在于，这个缓冲区满的时候不能去继续生产了，然后空的时候不能去继续消费了。

后面水果盘那道题就是它的变形，所以这里先把矛盾记住：生产者的推进条件是"还有空位"，消费者的推进条件是"还有产品"，两个条件互为对方的前置。

### 3.3 读者-写者：写后读与读者并发

读者-写者要处理的问题，助教列了两点：

1. 写者写完之后，读者才能读。这是数据依赖：读到的必须是已经写好的内容。
2. 多个读者可以并发地读，但写者必须独占——写的时候不能有别的读者或写者在同时访问。

这两点一放，问题的结构就清楚了：读者之间是"共享"关系，写者与任何人之间都是"排斥"关系，所以后面单车道那道题里，同向的车相当于读者，反向的车相当于写者。

### 3.4 哲学家就餐：本质是死锁条件的综合分析

助教说哲学家就餐这道题比较有意思，考的概率一般会比较低。它的设定是：多个参与者同时去竞争一个有限资源，比如五个哲学家，左右手各有一只筷子，哲学家可以吃饭也可以思考，但他必须同时左右手都拿着筷子才可以去吃饭。

然后他给了一个很关键的判断：

> **老师强调**：从哲学家问题的定义上其实很明显就可以看出，它不是一个严格意义上的同步互斥问题，它重点要解决的只是一个死锁问题。如果我五个人同时都拿到筷子，整个问题就彻底陷入死锁了。

既然重点是死锁，解法就从死锁的成因入手。助教说，解决哲学家就餐问题，完全是从破坏死锁的四个必要条件去入手的：

1. **互斥**这个条件不能破坏。因为"一只筷子只能被一个人拿"是题目本身定义的，改了就不是这道题了。
2. 剩下三个条件里，可以逐个考虑破坏。助教以破坏**循环等待**为例：可以让奇数的哲学家和偶数的哲学家采用不同的拿筷顺序，用这种顺序机制去破坏环状等待。

他连着说了两遍"这个问题有很多种解法"，并让大家自己下去再考虑。本节的重点仍然是前两个问题。

### 3.5 两个原语：P 操作与 V 操作

助教说，中间涉及两个操作，一个是 P 操作，一个是 V 操作（字幕把 V 操作识别成了"微操作"）：

- **P 操作**就是 wait，意思是申请一个资源，或者等待一个条件；
- **V 操作**就是 signal，意思是释放一个资源，或者发出一个通知。

这两个语义在后面所有代码里都要用到，尤其是 V 操作那一半——它不只是"还资源"，还承担"通知"的职责，这一点在同步题里比在互斥题里更重要。

### 3.6 四步法

助教把信号量题目的分析流程固定成四步，要求一步一步走：

1. **找线程**：分析有几类不同的线程/进程，写出每类线程的基本操作；再进一步分析每类线程有多少实例。
2. **找互斥关系**：分析有哪些资源需要互斥访问，每个互斥资源定义一个互斥信号量。
3. **找同步关系**：分析不同类线程之间的操作有哪些依赖关系，一种依赖关系对应一个信号量。
4. **补充代码**：定义信号量与初值，在线程的基本操作上补上 wait/signal。

他强调这套流程的作用是让思路有序：

> **老师强调**：解决这个信号量的问题，大家还是要逻辑清晰一点，用这种四步法一步一步地，从线程开始找线程，然后去定义信号量、定义它的初始值，再通过题目去找互斥关系、同步关系，然后再补充代码。

**补充说明**：根据本节补充材料《信号量复习.pdf》第 3 页，第四步"补充代码"除了定义信号量与初值、在线程基本操作上加入 wait/signal 之外，还要求把多个线程代码写完之后再写一个并发运行框架；课堂只说了"最后再去补充代码"，没有提到这个框架，此条用于补全第四步的完整交付形式。材料给出的写法是：

```c
main()
{
    cobegin {
        producer();
        consumer();
    } coend;
}
```

四步法在后面的三道题里被反复使用，助教每次都会说明"这题也可以用之前说的四步法"，可见他要训练的是流程本身，而不是三道题的答案。

## 四、信号量初值：0、1 还是 N [00:13:26–00:14:50]

### 4.1 要先定两件事

讲完四步法，助教单独拎出了一个容易被忽略的细节：在定义信号量的时候还需要注意一点——信号量的初始值应该怎么定义。

他的说法是：定义信号量时我们知道哪些东西是需要定义出来的（也就是需要几个信号量、分别叫什么），但初值到底是设为零、设为一还是设为 N，这是另一个必须回答的问题，而且往往决定代码对不对。

### 4.2 初值 0：用于线程间的前后同步

初值设为零的场合是线程之间的前后同步。助教解释了它的语义：

> **老师强调**：什么时候设置初始值为零呢？就是线程之间的前后同步的时候。它的含义是先等待，要直到另外一个线程给它通知之后（才继续）——这时候我们把它设置为零。这个一般是通用的，大家可以去记一下。

也就是说，凡是"我要等别人先做完"的信号量，初值都给 0：等待方一上来就必然卡在 wait 上，直到被依赖方 signal 才放行。这时候计数器的 0 表示"这个条件还没有发生一次"。

### 4.3 初值 1：二元互斥

初值设为一的场合是二元互斥。助教给的解释是：资源当前就可以直接供给一个线程去获取，这时候我们一般把它定义为一。

这个 1 表示"资源现在空着，谁先来谁能拿"；一旦有人拿走就变成 0，后来者只能等。

### 4.4 初值 N：有限数量的资源

初值设为 N 的场合是有限数量的资源。助教说：就是说这个有限数量的资源获取，当前最多允许有 N 个资源被获取、被占用，我们这时候把它定义为 N。

他补了一句"大家随着题目的推进，可以逐渐去理解这个问题"——因为水果盘那道题的 plate 初值就是 N，单车道那道题的 mutex 初值是 1，正好把三种初值都用了一遍。

### 4.5 关于负值

助教还讲了信号量取值的一个细节。字幕这里把"负值"识别成了"复制"，从上下文可以确定讲的是负值：

- 信号量一般是不用负值的；
- 有些实现里会出现负值，那是用它来表示当前有多少个进程在等待这个资源；
- 我们一般不考虑负值；
- 具体内容那份 Word 文档里也会有讲解。

**补充说明**：根据本节补充材料《信号量复习.pdf》第 1 页，不同信号量实现对负值的处理并不相同。POSIX 信号量（`sem_wait()`、`sem_post()` 是 POSIX 标准 API）不允许负数：`s` 大于 0 时 `sem_wait()` 把 `s` 减 1，`s` 为 0 时 `sem_wait()` 直接让调用线程等待而不去减 `s`；另一些信号量机制允许负数，此时若信号量值为 $-N$，表示有 $N$ 个线程正在等待该信号量。同一页还按取值范围把信号量分为二进制信号量（Binary Semaphore，只能取 0、1，一般用于 mutex）和计数信号量（Counting Semaphore，可取整数，一般用于表示实际资源数量）。这条补充用于补全课堂"负值表示有多少进程在等"这一句背后的实现差异，课堂上助教只说了"我们一般不考虑负值"。

## 五、生产者-消费者：水果盘问题 [00:16:26–00:34:31]

### 5.1 题目与完整解答

助教说第一道题是生产者消费者类型，让大家先自己写一下。

**例题**：水果盘问题（多类生产者、多类消费者）

**题目**：桌上有一只能存放 $N$ 个水果的空盘。妈妈可以向盘中放苹果，也可以向盘中放桔子；儿子专等吃盘中的桔子，女儿专等吃盘中的苹果。请用信号量实现妈妈、儿子、女儿三个并发线程的同步。

**解答**：助教按四步法逐步给出。

第一步，找线程。一共有三个不同的任务，即妈妈、儿子、女儿，分别负责放水果、取桔子吃、取苹果吃。它们的基本操作是：妈妈准备水果并把水果放到盘子里，儿子从盘子里取桔子并吃掉，女儿从盘子里取苹果并吃掉。助教补充说，这些线程可以是多个实例（例如多个儿子），但一般情况下按单实例处理；如果要多实例，就要进一步考虑同类线程之间的互斥/同步问题。

第二步，找互斥关系。对这三个线程来说，盘子是都要使用的资源，所以需要定义一个互斥信号量 `mutex`，初值为 1。

第三步，找同步关系。三条依赖各自需要一个信号量：

- 女儿取苹果依赖妈妈放苹果：定义 `apple`，初值 0，女儿取苹果前 `wait(apple)`，妈妈放完苹果后 `signal(apple)`；
- 儿子取桔子依赖妈妈放桔子：定义 `orange`，初值 0，儿子取桔子前 `wait(orange)`，妈妈放完桔子后 `signal(orange)`；
- 妈妈放水果依赖盘中有空位（也就是依赖儿子或女儿把水果取走）：定义 `plate`，初值 $N$，妈妈放水果前 `wait(plate)`，儿子或女儿取走水果后 `signal(plate)`。

第四步，补代码并给信号量赋初值，得到：

```c
semaphore plate = N, apple = 0, orange = 0;   // 同步用
semaphore mutex = 1;                          // 互斥用

mother() {
    while (1) {
        prepare a fruit;
        wait(plate);          // 先检查是否有空位
        wait(mutex);          // 互斥地使用盘子
        put the fruit on the plate;
        signal(mutex);
        if (fruit == apple)
            signal(apple);    // 放的是苹果，通知女儿
        else
            signal(orange);   // 放的是桔子，通知儿子
    }
}

son() {
    while (1) {
        wait(orange);         // 等盘中有桔子
        wait(mutex);
        pick an orange from the plate;
        signal(mutex);
        signal(plate);        // 空位加 1
        eat the orange;
    }
}

daughter() {
    while (1) {
        wait(apple);          // 等盘中有苹果
        wait(mutex);
        pick an apple from the plate;
        signal(mutex);
        signal(plate);        // 空位加 1
        eat the apple;
    }
}
```

**结果与点评**：整段代码的骨架是"外层 `while(1)` + 基本操作 + 两端加锁 + 前后加同步"。助教讲评时的落点不在代码本身，而在两处细节：一是 `mutex` 必须紧贴临界区，且必须放在 `wait(plate)` 之后；二是写完要按一条完整流程走一遍，检查每个 `wait` 是否都能找到对应的 `signal`。这两点分别在 5.3、5.5 与 5.6 展开。

### 5.2 代码是怎么一步步搭出来的

助教没有直接把最终代码摊开，而是把搭建顺序也讲了一遍，因为他认为这个顺序就是考试时的思考顺序。

先不管信号量的定义，我们有三个线程：妈妈、女儿、儿子。以妈妈为例，把她的代码写出来：外面先加一个 `while(1)`，让她不断地执行里面的操作。

然后第一步先写基本操作。妈妈可以干什么？第一件事是准备水果，助教说"准备水果这个无所谓"，因为这一步不涉及共享资源；真正核心的一件事是 `put the fruit on the plate`，把水果放到盘子里。所以先把这一行写出来。儿子和女儿同理，也是先把中间那一行具体操作写出来。

第二步才是给这个操作的两头加锁。助教说：

> **老师强调**：第一步先把它的操作写出来，然后再给这个操作的两头去加锁。

对妈妈来说，第一个操作是往盘子里放水果，这很明显要用到盘子，所以就要把 `mutex` 加到这行的两边。加完之后，妈妈已经占用盘子了，儿子和女儿就不可能同时在盘子里动手；取完 `signal(mutex)`，盘子的使用权才交出去。儿子和女儿那边也是同样的操作：取水果的那一行两头各加一个 `mutex` 把它包起来。

这个"先写操作、再包锁、最后补同步"的顺序，助教在后面总结解题流程时又重复了一次：先把线程确定好，第二步把具体操作确定好，然后去加互斥的锁，加完锁再去看同步。

### 5.3 mutex 为什么要紧贴着临界区，plate 为什么必须在它上面

助教在这里留了一个问题让大家想：为什么要把 `mutex` 加到操作的两边、而且是紧紧挨着，而不是把 `wait(plate)` 挪到 `wait(mutex)` 的下面去（也就是先占盘子、再检查有没有空位）？他说这两个位置看上去是可以调换的，**其实是不能的**，并把这个问题标为"大家也需要考虑一下"的重点。

他给的第一层理由是范围：要把 `mutex` 这个互斥量尽可能地把临界区的范围弄小一点——互斥量包住的代码越少，别的线程被挡住的时间越短。也就是说，`mutex` 只应该包住"放水果"那一行，而不应该顺手把"检查空位"这类可能阻塞的等待也包进去。

第二层理由不是效率而是正确性：一旦把 `wait(plate)` 放到 `wait(mutex)` 下面，整个程序就会死锁。这一层助教在后面专门用一整段推演讲过，见 5.5。

### 5.4 补同步：为什么要先 wait(plate)

第二步是检查同步问题：是否有空位。

助教带着大家分析"往盘子里放水果"这个操作：要往盘子里放水果，是不是首先要检查有空位了才可以放？所以逻辑上很通顺，先 `wait(plate)` 一个。`plate` 的空位数量初值是 $N$，先检查这个 $N$，`wait(plate)` 通过之后再去执行这一系列操作。

放完水果之后要往下走，去判断该把通知发给谁。这里用到的是同步操作里"有一个通知"的那一面：

> **老师强调**：同步操作有一个通知的东西——我放了一个水果，是桔子还是苹果，对两个孩子的这个影响是不一样的。

所以妈妈在临界区之后有一个判断分支：如果放的是苹果，就 `signal(apple)`；如果放的是桔子，就 `signal(orange)`。这也是本题与标准生产者-消费者最大的不同：标准题只有一个 `full` 信号量，本题因为产品分了两类、消费者也分了两类，所以"有产品"这个条件必须拆成两个信号量，由生产者按产品种类分别通知。

儿子的代码相对好写：先从逻辑上把中间那行具体操作写出来（取桔子），两头加 `mutex`；然后儿子要的是 `orange`，所以直接去 `wait(orange)`，也就是看现在盘子里面有没有桔子；取完之后再释放盘子——把空位数量加 1，即 `signal(plate)`；最后是吃桔子这一步，助教说这一步不重要，不影响同步互斥的正确性。

### 5.5 关键错误：mutex 放在 wait(plate) 之前会死锁

这是本节讲得最细的一处论证，助教说这是"这道题比较关键的一个点"。

先看错误的写法：如果把 `wait(mutex)` 放在 `wait(plate)` 上面，也就是妈妈先占盘子、再去检查有没有空位。设盘子现在是满的，那么妈妈线程执行时会首先去占用这个盘子——这一步是占用的操作，会成功——然后它才去检查是否有空位。

于是局面变成：

1. 妈妈已经持有 `mutex`，此时儿子、女儿即使想取水果，也会卡在 `wait(mutex)` 上，进不了临界区；
2. 妈妈继续执行，走到 `wait(plate)`，发现没有空位，于是阻塞；
3. 妈妈想把 `mutex` 释放掉，但它的 `signal(mutex)` 写在临界区之后，根本还没执行到，所以释放不了；
4. 盘子里没有空位，是因为水果还没被取走；而水果取不走，是因为儿子女儿都被挡在 `mutex` 外面；
5. 儿子女儿还在不断申请 `mutex`，妈妈还在等 `plate`——整个系统就陷入了死锁。

助教的原话是"所以大家很明显可以看到这地方有一个逻辑问题：它是占用了、已经占上了，然后还没释放、还不能释放，然后才去检查是否有空位；它占上了然后再检查，发现没空位了，没空位怎么办呢？它又释放不了，然后那个儿子女儿又在申请，所以就导致整个就陷入死锁了"。

这个例子说明的是一条通用规则：**申请多个资源时，先申请的那个如果会导致自己阻塞，而它又挡住了唯一能解除阻塞的人，就会死锁**。在这里，`plate` 是"会导致阻塞的条件资源"，`mutex` 是"挡住他人的独占资源"，所以条件资源的申请必须排在独占资源之前，并且 `mutex` 只包住真正的临界区。

讲完这个陷阱，助教收了一句：

> **老师强调**：整个的代码其实不是很难，但是大家需要做这些题的时候，需要把这个逻辑去理清楚一点。

这句话对应的就是他随后给出的固定解题顺序：先把线程确定好，第二步把具体操作确定好，然后去加互斥的锁，加完锁再去看同步，同步按题目一步一步来——橘子、苹果之类的判断都是同样的套路。

### 5.6 写完怎么自查：wait 与 signal 一一对应

助教给了一个检查手段：整段代码写完之后、把该补的都补充完之后，再通顺地走一遍流程，比如"妈妈放一个，然后儿子吃一个"，然后把这个动作拉起来看它是否有对应的 `signal`，下面另外一个位置是不是有一个对应的 `signal`，把全部对应起来。只要你自己觉得完整地对应起来了、框架是合理的，这种题一般自己检查基本就是做对的，逻辑上不会再出现什么问题。

他还点出了这种对应关系的一般形态：

> **老师总结**：`wait` 和 `signal` 在整个代码框架里写完之后，基本上是一一对应的：有一个 `wait` 就有一个 `signal`，它可能不在同一个线程里，但可能在另外一个地方——有一个生产，就有一个消费。

也就是说，配对是按"信号量的语义"配的，不是按"同一个函数里前后配对"配的。互斥信号量在同一个线程内成对出现（`wait(mutex)` 与 `signal(mutex)` 夹住临界区），而同步信号量的 `wait` 和 `signal` 天然分处两个线程，这正是同步与互斥在代码形态上的区别。

### 5.7 多实例与 mutex 的必要性

关于 `mutex` 到底为谁而设，助教讲得很实在：它主要是作用于可能有多个妈妈的情况——如果妈妈、儿子、女儿三类线程都可能有多实例，同类线程之间就会争抢盘子，必须有互斥；本题按单实例处理时，`mutex` 的作用看起来不明显，但写上去是通用做法。

助教让大家动手写这段代码时还交代过实例数的处理方式：妈妈可以只考虑一个实例，儿子和女儿可以考虑多个；只考虑一个实例会让问题变得简单。这也是本题默认的设定。

**补充说明**：根据本节补充材料《信号量复习.pdf》第 5 页的说明，上述代码在妈妈、儿子、女儿都有多个实例时仍能正常工作；如果只有三个线程（三类各一个实例），那么 `mutex` 的操作可以省略——把所有 `wait(mutex)`、`signal(mutex)` 去掉——因为三个同步信号量的关系已经能保证互斥：同类之间没有竞争（只有一个实例），不同类线程之间靠同步信号量顺序执行，即使儿子和女儿同时从盘子里取，他们取的也是不同位置上的资源，并不冲突。这条补充用于补全课堂上"mutex 主要作用于可能有多个妈妈的情况"这一句背后的理由。

## 六、多生产者多消费者：玩具自行车组装 [00:44:48–00:47:18]、[01:14:06–01:15:28]

### 6.1 题目与总体思路

练完水果盘，助教给出的第二道题是玩具自行车组装：玩具自行车由 2 个轮子和 1 个车身构成。生产轮子的工人每做好一个轮子就放到轮子的工作台上，工作台可以放 $N_1$ 个轮子，满的时候暂停生产；生产车身的工人把车身做好后放到放车身的工作台，可以放 $N_2$ 个车身，满的时候暂停生产；组装工人从两个工作台分别取 2 个轮子和 1 个车身，然后组装成一台玩具自行车。

助教先定了性：这题也是一个生产者和消费者的问题，但它是多生产者和多消费者，思路和前面基本上大差不差。

### 6.2 关键：三个取件操作必须一次性完成

真正的差别在组装工人这一侧。助教说，对于组装工人来说，他需要两个轮子和一个车身，最好是这两个轮子和一个车身一次性获取：一次性去获取、去判断有没有两个轮子和一个车身。

如果不这样一次性获取，就会出现死锁：

> **老师强调**：如果不是这样一次性获取，就可能会出现有一个生产工人（组装工人）拿着一个车身一直在等轮子，或者有组装的工人一直拿着两个轮子在等一个车身，然后这样就会造成死锁，所以这个操作是要原子的。

这段推理和 5.5 的死锁论证是同一个结构，只是换了个场景：组装工手中持有的资源（车身或两个轮子）在凑齐之前无法释放，而另一边工作台可能已经满了、生产者被自己那一侧的"满"条件挡住，两边互相等，谁也不动。

### 6.3 课堂问答：两个轮子能不能分两次拿

> **学生提问**：哪两个轮胎是同时拿吗？还是说要分开？

**课堂问答**：助教回答，只要保证它是——比如你拿轮子和拿车身的时候，在这三个操作前后设置一个互斥量，然后保证这三个操作能够一次性进行，就是可以的。也就是说，判据不是"两个轮子必须一条指令拿到"，而是"取 2 个轮子 + 取 1 个车身这一整段被同一把锁包住，对外表现为原子"。

助教随后补充了容量上的限制：如果 $N_1$ 等于 1，那么一次取两个轮子这件事永远不能完成——每轮只能生产 1 个轮子，组装工要凑够 2 个才会动手，于是永远凑不齐。若两个轮子能一起拿到（即工作台容量允许），就没有这个问题。

### 6.4 参考答案的处理与遗留的小问题

助教发了参考答案后，专门回应了"为什么答案把两个轮子分开拿"这个疑问。他说可能有同学会问：为什么要把两个轮子分开？有没有同学是两个轮子一起去拿的，就是直接在两个位置外面包一把锁？

- 一次性拿两个轮子也是可以的；
- 但答案把操作拆细，是因为题目上并没有定义轮子工作台的大小，而一次需要两个轮子；如果工作台只有一个、即 $N_1=1$ 的话，一次性取两个就没法完成；
- 如果 $N_1 \ge 2$，那么一次性取两个轮子再取一个车身完全没有问题；
- 所以参考答案把这里拆得细一点，主要是为了解决 $N_1$ 可能等于 1 这个问题。

不过他也承认拆细会带来新的问题：

> **老师提示**：每次单独拿也可能有一个小问题：比如现在有两个轮子、有两个组装工人实例的时候，我拿一个、他拿一个，然后组装不起来。这个大家可以下来自己再考虑一下。但是这个问题——这个答案也是可以通过的，一般不管是考试还是做练习，写到这种程度已经没什么问题了。

这里留下的是一个真实的开放点：拆开拿解决了容量为 1 的死结，却引入了"两个组装工各持一个轮子、谁都不够"的僵局。助教没有在课上给出统一解法，而是把它留作课后思考。

## 七、读者-写者：单车道通车问题 [00:47:18–00:49:16]、[01:00:54–01:07:43]、[01:10:08–01:10:37]

### 7.1 题目

助教给出的第三道题是：在 A、B 两地中间有一段路，路宽只能容纳一辆车通行，假设汽车不能倒车（只能往前开），试用信号量解决两个方向车通行中的同步互斥问题。

### 7.2 四步法第一步与第二步：两类车、一条路

第一步分析线程：这题有两类车，一类从 A 往 B 开，另一类从 B 往 A 开；每一类里面都有多个实例，也就是有多辆车都可以在同一个方向里面开。每类车的基本操作是 `drive through road AB` 或 `drive through road BA`。

第二步分析互斥共享资源：AB 之间的这段路。助教给了一个很有用的说法——对于同向的车，这条路相当于读者锁；对于反向的车，它相当于写者锁：

- 如果 A 往 B 前面已经有一辆车在开了，那么后面 A 往 B 的车可以紧接着开过去，即同向的车可以连续通过；
- 而反方向的车只能等这一串 A 往 B 的车开完之后，才能从 B 往 A 开。

所以这段路的语义正好是读者-写者：同向共享、反向排斥。

第三步，助教明确说这里没有相互的依赖关系，所以本题不需要同步信号量，只有互斥。这一点和水果盘形成对照：水果盘的 `apple`/`orange`/`plate` 都是同步信号量，而本题的 `mutex`、`SemCountAB`、`SemCountBA` 全是互斥信号量。

**补充说明**：根据本节补充材料《信号量复习.pdf》第 4 页，同步与互斥的区别在于：同步发生在不同任务之间、并且有中间数据生成（典型场景是 A 任务的运行依赖于 B 任务产生的数据）；互斥则是同类或不同类线程按序访问互斥资源，而互斥的资源一般是已有的资源（不是某个任务生成的中间数据）或者线程间共享的状态。这条补充用于说明课堂上"这里没有相互的依赖关系"这一判断的判据。

### 7.3 基本解：第一辆车申请路权、最后一辆释放

```c
Semaphore mutex = 1, SemCountAB = 1, SemCountBA = 1;  // 全部是互斥量
int countAB = 0, countBA = 0;                          // 两个方向车的数量

LeftCar() {                        // A → B
    wait(SemCountAB);              // 修改 AB 方向车的数量需要互斥
    countAB++;
    if (countAB == 1)
        wait(mutex);               // 本方向第一辆车需要获得 AB 间路的使用权
    signal(SemCountAB);
    drive through road AB;
    wait(SemCountAB);
    countAB--;
    if (countAB == 0)
        signal(mutex);             // 本方向最后一辆车需要释放 AB 间路的使用权
    signal(SemCountAB);
}

RightCar() { /* 与 LeftCar 完全对称：把 AB 换成 BA 即可 */ }
```

助教的讲评顺序和数据流一致：对于从 A 往 B 开的第一辆车，它需要去询问这个路权；同样，从 B 往 A 开的第一辆车也需要询问路权；但后续的车是不用的，因为已经有了第一辆车可以从 A 往 B 开，后续的车也就可以继续从 A 往 B 开。

`countAB` 和 `countBA` 就是用来数两个方向各有多少辆车的。当 `countAB` 等于 1 时，说明这是本方向的第一辆车，它需要获得路权——因为现在可能正有 B 往 A 的车在使用当前这段路，而这段路是互斥的，所以必须先获取这个共享资源。等这一批 A 往 B 的车都通过了之后，数量要相应地减下来；当这个方向当前没有车的时候（`countAB` 减到 0），它就可以释放当前的这段路权。`mutex` 这个变量就用来表示当前这段路的使用权。

助教还专门提醒了一个容易漏掉的点：`countAB` 和 `countBA` 这两个数量本身的修改也是需要加对应的互斥量的——否则两辆车同时 `countAB++`，计数就会错，进而导致"第一辆"或"最后一辆"的判断失效，路权要么没人申请、要么被提前释放。这就是 `SemCountAB`、`SemCountBA` 的用途。反向的 `RightCar()` 代码完全对称，把 AB 换成 BA 就行。

### 7.4 基本解的问题：不公平

写完之后助教马上指出，这样写是有问题的。

问题出在路权被持有的时间上：本方向第一辆车获取到 AB 这段路的使用权之后，只要后续一直有同方向的车来，它就可以一直用这条路——因为 `signal(mutex)` 只在 `countAB` 减到 0 时才执行。于是如果此时另一个方向也有车想从 B 往 A 开，它就会一直等下去：只要 AB 方向不断有车，这种情况就会一直持续，用助教的话说就是"造成一个非常不公平的等待"。

按课程里的术语，这就是**饥饿**（starvation）：系统整体并没有卡死（一直在推进，没有死锁），但某一类线程可能永远得不到资源。

### 7.5 公平版：所有车一起排队

助教给出的修法是改变排队结构：无论你是第一辆车还是后面的车，所有从 A 往 B 开和从 B 往 A 开的车都需要在一起排队，大家都需要先提出请求——在想使用这条道路之前都要先提出请求、申请这个资源，通过了才可以通行，这样才不会造成这种不公平的等待。

落实到代码上，就是在刚才的代码前面加上一个更大的互斥量：在对应的位置加一个更大的锁，这样大家都是公平地提出请求，也不会造成一方一直开的情况。

```c
Semaphore mutex = 1, SemCountAB = 1, SemCountBA = 1;  // mutex 是道路资源使用权
Semaphore token = 1;                                   // 两个方向公平竞争的令牌
int countAB = 0, countBA = 0;

LeftCar() {
    wait(token);                 // 先排队申请上路
    wait(SemCountAB);            // 再修改本方向车辆计数
    countAB++;
    if (countAB == 1)
        wait(mutex);             // 第一辆车申请 AB 间道路使用权
    signal(SemCountAB);
    signal(token);               // 立刻交还令牌，让其他车也能提出请求
    drive through road AB;
    wait(SemCountAB);
    countAB--;
    if (countAB == 0)
        signal(mutex);
    signal(SemCountAB);
}
```

**补充说明**：根据本节补充材料《信号量复习.pdf》第 7 页的说明，`token` 的作用相当于维护一个全局队列，按 `wait` 的先后顺序通过；而 `signal(token)` 之所以可以放在上路之前就执行，是因为它只释放"提出请求的资格"，不释放路段本身：如果后续是同方向的车拿到 token，它可以直接上路（此时 `countAB` 大于 1，不会阻塞在 `mutex` 上）；如果释放后是反方向的第一辆车拿到 token，那辆车会被阻塞在 `mutex` 上（因为它要 `wait(mutex)`），因为这一方向还有已上路的车没有释放 `mutex`。这样既保证了两个方向按请求顺序切换，又不会让已在路上的车被迫中断。这条补充用于补全课堂上"加一个更大的互斥量、大家都公平地提出请求"这一句背后的正确性理由。

### 7.6 更复杂的情形：中间设错车平台

助教最后提到本题还有一个变体：在 A、B 之间的道路上可以设置一个类似平台的东西，这个平台是可以错车的，也就是允许两个方向的车同时在区间内行驶、在平台处交错通过。他说这种情况相对复杂很多，感兴趣的同学可以下来在 Word 文档里仔细看一下，并说"一般就只会考某一种"。因此，这个变体的具体解法本节没有展开。
