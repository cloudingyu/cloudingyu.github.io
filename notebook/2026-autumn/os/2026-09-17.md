## 一、课程回顾：操作系统的三大模块 [00:02:24–00:05:23]

### 1.1 三大模块及其分工

本讲接着上次课对操作系统的简要介绍，深入来看第一个主题。我们讲过操作系统有三大模块：

1. **虚拟化**（virtualization）：解决底层的硬件资源怎么样来抽象，比如把代码和它的执行抽象成**进程**（process）；与进程相关的还涉及进程的调度，以及进程的内存资源分配等等。
2. **持久性**（persistence）：讲的是与数据相关的概念，包括数据怎么样持久地保存——也就是保存到硬盘上怎么保存；以及它跟外部设备（硬盘之类）打交道的时候怎么进行抽象。要用硬盘的资源，最基本的抽象就是**文件**（file），文件又由**文件系统**（file system）来组织。
3. **并发**（concurrency）：主要涉及多任务执行过程中大家的**同步**（synchronization）、**互斥**（mutual exclusion）之类的操作。

这三个模块其实是交替相互影响的，但既然可以模块化，我们就不管它，从第一个模块开始。

### 1.2 并发为什么难：上次课的计数例子

多任务执行大家都知道，我觉得最难的就是这种并发的分布式系统。它的很多事件很有突发性或者偶然性，这样如果没有一些机制，某一个任务先执行、某一个任务后执行，执行的结果就有可能不一样。

上次课讲过一个加法的例子，就是 `i++` 或者 `counter++` 这个操作。

**例子**：两个线程或进程同时对变量 `i` 做加一。

- 如果两个线程或进程同时对 `i` 这个变量进行一个加，那么有可能它执行的结果跟我们的预期结果不一样。
- 不一样的原因是什么？原因就在于两个任务并发执行的过程中有一个先有一个后，它在不断地切换。
- 进一步说，有些指令先处理和后处理，对于两个线程来讲得到的值是不一样的，所以结果就与预期不同。

> **老师强调**：并发不确定性的根源不是"加法算错了"，而是同一个操作被拆成多步之后，两个任务在这些步骤之间的交错顺序不同。

### 1.3 持久性的位置

所以整个操作系统设计的就是这三方面：虚拟化、并发加上持久性。今天我们开始进入第一个环节，也就是虚拟化。

## 二、虚拟化：从物理资源到抽象 [00:05:23–00:21:08]

### 2.1 操作系统作为中间层

虚拟化到底要解决什么问题？操作系统是位于硬件和应用之间的这么一个中间层。那么中间层要起什么作用呢？我们一般的理解就是：这个中间层基于最底层提供的功能，然后来支撑上一层。

那怎么样基于底下的功能支撑上一层呢？它就是提供了这么一种**抽象**（abstraction）：把底层的资源抽象化，再面向上层提供额外的支持。

**定义**：**虚拟化**（virtualization）。在操作系统环境下，虚拟化本质上就是要把底层的物理资源进行抽象，让它能够变得容易操作、容易使用。

虚拟化是计算机专业非常重要的一个概念，在很多领域都会用到：编程里面有虚拟化，计算机系统里面有虚拟化，网络里面也有虚拟化，所以虚拟化这个概念其实贯穿整个计算机专业的很多内容。

### 2.2 上层是计算任务，下层是计算资源

底层的资源就是硬件，硬件能提供的就是一些存储资源和计算资源。

上层的应用不外乎是一些计算任务，比如你要打开一个 word 程序去编辑文档，要运行一个视频播放器看部电影，这些都是典型的应用。

**例子**：视频播放器要做什么？

- **题目**：以视频播放器为例说明上层应用的本质。
- **解答**：它就是要打开一个视频文件，然后对一个视频文件进行解码，并且把它呈现出来，就是用解码以后的图像形式把它呈现出来。
- **结果与点评**：这些事情归根结底就是一系列的计算任务。所以本质上就是上层需要一系列计算任务，下层是一系列计算资源。

那怎么样把这个计算任务跟计算资源绑定起来，或者叫做能够把这个计算任务分解成我们底层的计算资源能够提供的能力来执行，这就是我们操作系统要做的事情。

**定义**：**进程**（process）。这里提出一个最简单或者最重要的抽象，就是进程，它是对我们所要执行的任务的一种抽象。

本讲接下来的安排是：关于**地址空间**（address space）以及进程如何创建的一些讨论，最后讲进程和操作系统之间的关系以及怎样进行交互。今天内容主要涉及第 4 到 6 章。

### 2.3 物理资源：CPU 与内存

我们到底有哪些物理资源？这里提到物理资源就是 CPU 和内存。

**例子**：买计算机的时候看配置。

- **题目**：一台计算机的配置里最关键的参数是什么？
- **解答**：这两个也是经常看到的最重要的两个配置。一个是我们的 CPU 是什么型号、它的频率是多少、它有多少个核；另外一个就是内存，你是多少 G 的内存，然后这个是什么技术实现的内存。
- **结果与点评**：CPU 和内存就是计算机硬件资源里非常典型的一种计算能力。很显然，操作系统主要要进行虚拟化的就是这几种资源，就是 CPU 资源和内存资源。

### 2.4 CPU 虚拟化：时分复用

**定义**：**CPU 虚拟化**。CPU 物理上一般来讲只有一个（当然你也可以一台机器装多个 CPU，是完全可以的，但我们一般默认它只有一个）。所谓虚拟化，就是你要把这个物理的资源变成一个类似于资源池的这么一个东西给上层用；我们要有一些技术，把物理的 CPU 抽象成像多个虚拟 CPU 的概念。

**推导**：一个物理 CPU 怎样支持多个任务？

1. 抽象的办法就是允许多个任务同时在一个物理 CPU 上执行；
2. 这多个任务又不断地在这个物理 CPU 上切换，来达到这个目的；
3. 因为一个 CPU 要支持多个任务，而多任务执行最基本的办法或者说最常见的思路就是两种：一种是**时分**，一种是**空分**，也就是**时间复用**和**空间复用**；
4. 要么多个进程在 CPU 里面各占一小块，要么一个 CPU 大家轮流用——要么时间上切，要么空间上切；
5. 很显然，对于 CPU 来讲，它更多的是时间上进行切分；对内存来讲，它更多的是空间上进行切分；
6. 所以 CPU 虚拟化最基本的办法就是通过**时分复用**（time sharing）的方式来允许多个任务同时运行。

> **老师强调**：让大家记住这个核心的目标，就是我们是要允许多个任务在一个物理 CPU 上执行。它的核心思想就是大家轮流用——因为你只有一个 CPU，你也变不出来。

> **老师比喻**：比如只有一辆自行车，你多个人要骑，那怎么办呢？那很显然就是轮流骑，就像类似共享单车一样：每个人在某一个时间段去扫码，然后去骑，骑了还回去，另外一个人要继续骑就继续扫码。基本上就达到了一台自行车多个人用的目的。

### 2.5 内存虚拟化：空间复用

**定义**：**内存虚拟化**。内存物理上只有一套，假定我们的内存就是这么大一个区域，比方说你有 16G 的内存，我们就可以把这个 16G 看作是一个连续的字节空间，从零开始一直编号到 16G 这么大一个空间，这是一个类似于连续的字节地址空间。我们就认为内存可以抽象成这个概念。

$$0 \sim 16\,\text{GB}\quad(\text{连续字节地址空间})$$

要在这个内存空间里放多个不同的进程，就需要把这个地址空间按照空间复用的方式，把不同的进程放到不同的空间去。

**例子**：把进程放进物理内存。

- **题目**：怎样把多个进程放进同一块物理内存？
- **解答**：假定你有一个进程可能只有 50 兆，那你就把这个内存切 50 兆出来放进程一；另外一个进程要 100 兆，那就切 100 兆放进程二。
- **结果与点评**：这就是按照空间来进行划分，是把不同进程放置到物理内存时的办法。

### 2.6 每个进程需要独立的虚拟地址空间

把进程放到物理内存的不同位置是可以的，但还有一个问题要解决：每个进程因为是独立的，独立就意味着什么？它有自己的一套编程的空间，比如每个进程都有一个自己的地址空间。这一点大家在写 C 程序或 C++ 程序的时候都知道：每一个程序它都有一个地址空间，里面有具体的区域划分，哪些区域是 **heap**（堆），哪些区域是 **stack**（栈），还有一些静态的区域。对于每个程序来讲都有这些区域。

那么很显然是，针对这些不同的程序或进程，它的这个地址空间应该是相互独立的。简单地说就是：我这个进程有一个空间，另外一个进程有它自己的空间，而且它们的空间都是从零开始。

那这些多个任务——比如刚才讲的 word 编辑器和视频播放器——怎么样来分享这个地址空间和这个 CPU 呢？CPU 刚才已经讲了，基本逻辑就是按照时间轮流用；那怎么样分享地址空间呢？在物理上你可以把进程各放一处，把播放器和 word 编辑器放到物理内存的不同位置就行了，这个当然是可以的。

**例子**：一个 CPU 上跑多个进程。

- **题目**：word 编辑器和视频播放器在同一台机器上怎样共存？
- **解答**：它们相互不关联（一般情况下当然也可以合作来完成某个事业，但一般情况下是不关联的，视频播放器和编辑器之间应该没有任何关联），都是独立地在运行，而且在同一套物理的硬件上运行；CPU 按时间轮流用，地址空间则按空间共享、物理上分处不同位置。
- **结果与点评**：多个任务可以共享 CPU 与地址空间，但每个进程仍需要自己独立的地址空间。

### 2.7 虚拟地址空间的大小与动态增长

这个空间到底有多大呢？我们知道每一个运行的进程，它的空间可以随时动态增长。

**例子**：`malloc` 的作用。

- **题目**：编程时用到的 `malloc` 做什么？
- **解答**：我们在编程的时候学过一个函数，就是 `malloc`，它做的事情就是给你动态分配内存空间。
- **结果与点评**：所以每一个进程它所占的物理空间可以随时动态增长；既然随时动态增长，那它的虚拟地址空间肯定是一个可以动态增长的空间。

这个动态空间到底有多大，就由它这个地址的位数决定：

$$16\text{ 位系统}: 2^{16} \qquad 32\text{ 位系统}: 2^{32} \qquad 64\text{ 位系统}: 2^{64}$$

所以说它的虚拟地址空间对每一个进程都是这么大。简单地说，每一个进程它都可以使用一个从零到最大的地址空间，可以动态支撑到这么大。

**例子**：32 位系统的地址空间。

- **题目**：32 位系统下每个进程的地址空间有多大？
- **解答**：32 位系统下，每个进程它允许的最大地址空间就是 2 的 32 次方，也就是 4 个 G，就是从零开始到 2 的 32 次方这么大。
- **结果与点评**：$2^{32}\,\text{B}=4\,\text{GB}$。

**推导**：物理内存装不下 4G 地址空间怎么办？

1. 如果每个进程都是 4 个 G，那我们物理内存就不一定能容纳得下；
2. 所以这种情况下，我们的内存就需要有一些机制；
3. 虽然每个进程都是这么大，但是它并不是所有的空间都是被占用的，中间有很多区域它是空的；
4. 我们把空的区域就不要保存起来，只把那些真正有数据的内容保存起来；
5. 所以逻辑上每个进程都有 4 个 G 的空间，但这 4 个 G 的空间并不是硬映射到物理内存的空间上去的，它是只把那部分有数据的内容映射到物理内存就行了。

那么 word 编辑器、视频播放器，它理论上最大的地址空间都可以做到 4 个 G：你可以打开一个超大的文件，也可以把这个视频播放器做得很花哨很炫，占了很大的一个代码区域也都没问题，总之你总共可以做到 4 个 G；但实际上这 4 个 G 的东西并不是所有都保存到物理内存。

**定义**：**页式管理**（paging）与**页表**（page table）。内存虚拟化通过页式管理技术，把这些有数据的页放到物理内存，没有数据的页就不要；我们保留一个页表结构，记录下哪些页是在物理内存里面、哪些页是没有东西的。这样我们就知道，每个进程的一个虚拟地址空间都可以映射到物理地址空间去。

所以内存管理相对来说会比 CPU 复杂一点：CPU 很好理解，就是一个简单的大家轮流用就行了；内存则是先有一个抽象，再要把这个抽象映射到物理当中去——先让每个进程有一个抽象的大空间，再把每个进程的大空间按照实际占用映射到物理内存。这就是内存虚拟化的方式。

> **老师强调**：虚拟化的基本原理其实就这一页 PPT，从基本原理就能理解；后续的内容就是怎么样去实现这两个资源的虚拟化。大家先理解它的基本理念。

## 三、进程抽象及其与程序的关系 [00:21:08–00:28:42]

### 3.1 从"轮流用"到进程实体

刚才讲了轮流用的概念，轮流用 CPU 就是我们实现虚拟化的一个基本途径。那怎么样轮流用呢？轮流用的一个基本逻辑就是：既然大家轮流用、多个任务轮流用，那我们就必须要把每个任务抽象成一个能够运行的这么一个实体，这个运行的实体就叫**进程**（process）。

每个任务我们都把它抽象成一个可以运行的实体，就是进程。这个进程其实就是我们对操作系统提供计算能力的一种抽象：所有的任务你都要把它包装成一个进程的概念，去使用这个计算资源。所以这个进程就是我们如何来使用 CPU 这个资源的一种抽象——你要把上层各种应用的计算任务包装成一个进程，这个进程可以被调度到 CPU 上去执行。

### 3.2 进程是 a running program

**定义**：**进程**（process）。进程是对我们要计算的任务的一种抽象，它本质上就是 **a running program**（一个正在运行的程序）。

所以很显然是，这个进程就来源于我们的程序。大家学计算机每天都在讲编程的事情，那编程到底是做什么呢？我们编程其实就是写程序、构建系统，本质上就是能够写出一个可以执行、可以运行的系统。这个可以执行、可以运行的系统本质上就是类似于在操作系统里面写了一个 APP，或者你写了一个可执行的文件，那这样它可以运行起来，这就是 running program 的概念。

所以 running program 本质上就是我们是可以把某一个程序运行起来，让它参与到 CPU 竞争的这么一个实体——就是进程。

### 3.3 程序：静态的指令集合

**定义**：**程序**（program）。进程是一个正在运行的程序，而程序就是一个静态的代码的集合。

我们用 C 语言编了一个程序，这个程序的呈现形式就是一个**可执行文件**（executable file），比如 `.exe` 文件，它是存放在硬盘上的。怎么样让它变成进程呢？就是我们去双击这个程序的图标，或者用命令行去运行它；然后它运行起来以后，就会在操作系统里面创造一系列的数据结构，这些数据结构记录下这个进程的一些信息，我们可以让它参与调度。

所以程序与进程的关系就是：一个是静态的代码，一个是正在操作系统里面运行的这么一个实体。程序是进程的基础。

**例子**：从 C 程序到进程。

- **题目**：一个 C 程序怎样变成进程？
- **解答**：用 C 语言写一个程序，不外乎就是写了一个 `main` 函数，`main` 函数里面进行各种各样的操作，各种各样的循环控制、顺序控制、分支控制，到最后运行结束；这就构成了相当于是一系列指令的按顺序执行，这就是我们的一个程序。编程都是用这种略微接近自然语言的高级语言来编，编好以后它会翻译成机器指令或者汇编指令，汇编指令相对来说就是一行一行的代码，是机器可以执行的。
- **结果与点评**：程序的指令按照顺序往下执行，它有一个执行的入口，按照入口的地方顺序往下执行，中间当然会有跳转，比方利用分支或者循环会有跳转；把它运行起来，意思就是我们把它加载到内存里面，并且在操作系统里面创建一个进程的数据结构，这个数据结构会被用来进行调度，并且参与 CPU 资源的分配。

### 3.4 创建进程时操作系统要做的四件事

这个静态就体现在程序：你如果不去执行，它就是存在硬盘上的一个文件，就是一个 `.exe` 文件。你要把它运行起来，就会在操作系统里面创建一些数据结构：

1. 创建一个**进程 ID 号**；
2. 给它分配一些**内存空间**；
3. 把它的**代码区域**放到对应的内存空间；
4. 建立**调度机制**参与 CPU 执行的调度，让不同的进程在不同的时间到 CPU 上去运行。

### 3.5 一个程序可以变成多个进程

程序是静态的代码和数据，进程就是程序的一个运行。那么很显然是，一个程序可以变成多个进程：你把这个程序运行很多次，它创建了很多个实例，那么它就相当于是创建了多个进程。

当然，有时候我们操作系统也可以限制，就是说你的这个程序只能是单次运行——你运行一遍以后再点击它，它只会弹起原来运行的那个实例，那这样的话就是单实例的这种程序，也是有的。但通常情况下我们是允许多实例运行的。

**例子**：文本编辑器打开多次。

- **题目**：同一个文本编辑器被打开多次会发生什么？
- **解答**：相当于你把文本编辑器打开多次，它就创建了多个进程，就相当于同一个程序它运行很多次，创建了很多个不同的进程。
- **结果与点评**：在不同的进程之间，它们是相互独立的。A 进程和 B 进程虽然都是文本编辑器生成的进程，但是它们是相互独立的，它们有自己的一个空间，而且有自己的一个数据区域。

### 3.6 进程抽象的目的

为什么要进行进程的抽象？进程抽象的目的就是我们讲的虚拟化，让我们所有的进程都参与 CPU 的一个竞争。所有的程序一旦运行起来以后变成一个进程，这个进程就会参与到 CPU 的竞争。

## 四、并发与并行：多任务执行的动机与上下文 [00:28:42–00:49:32]

### 4.1 并发与并行的辨析

我们通常情况下，大家每天用电脑、每天用手机都有这个体验：其实我们的电脑或者手机可以同时运行多个任务。那这多个任务是怎么样来进行支持的呢？它的支持办法就是刚才讲的，我们允许多个任务同时或者有一个并发的执行。

这里注意这个词：**并发**（concurrency）和**同时**、并发和**并行**（parallelism）两个概念肯定是不一样的。

**定义**：**并发**。就是我们多个任务同时运行，但是这多个任务它们是交替地来占用 CPU 资源，这就是并发。

**定义**：**并行**。所谓的并行就是我们物理上的计算资源就是有多个，这多个任务是物理上在并行地执行、同时执行，这就是并行。

**例子**：怎样区分并发与并行？

- **题目**：给定"多个任务在运行"，怎样判断是并发还是并行？
- **解答**：并发相当于是我们物理上只有一个资源，然后让大家轮流用这个资源，看起来好像大家都在同时用，但其实这个物理资源在微观上是轮流用的；并行就是我们同时有多个资源，而且这多个资源的确在时间上就是同时运行。
- **结果与点评**：所以最容易理解的判别方式就是——物理上有多个 CPU，那么它就是并行；物理上只有一个 CPU，它就是一个并发。你虽然都是多个任务在运行，但这是它的并发和并行的关系。

### 4.2 单核上的并发体验

典型的 CPU 我们都是只有一个 CPU（当然目前主流都是多核了），那我们假定就是一个 CPU 单核的情况下，我们还是可以支持多个任务运行。

**例子**：写论文时背景放着音乐。

- **题目**：打开 word 编辑器写作业或写论文，同时背景又打开了一个音乐播放器，这两个任务之间是什么关系？
- **解答**：它们肯定是在并发执行，因为你感觉在写论文或写作业的时候，这个音乐也没有中断过。
- **结果与点评**：单核下两个任务仍然可以"看起来同时"地服务用户，这正是并发要解释的现象。

### 4.3 时间片轮转

那怎么样能做到这样呢？很显然它就是用了一个我们刚才讲的最基本的技术，就是**时分复用**，就是大家轮流用：你的音乐播放器的代码执行跟我们 word 编辑器的代码执行，它是交替地在 CPU 上运行。

这个交替在 CPU 上运行意味着什么呢？主要是我们把 CPU 的时间分成一个个的时间片。CPU 我们只有一个，但我们可以在这个时间上把它给切分，大家轮流用。

**推导**：时间片轮转的执行过程。

1. 把 CPU 时间切分为一个个时间片：$T_0$、$T_1$、$T_2$、$T_3$……
2. 比如 $T_0$ 是 word 在用；
3. 下一个时间片切到音乐播放器；
4. 再过一会儿又切到 word；
5. 再下一个又切到音乐播放器。
6. 这样两个不同的进程就轮流在 CPU 上执行。

### 4.4 为什么人感觉不到切换

大家可能要想：既然轮流在用，那为什么我们人没有感觉到中断？这个原因很简单：

1. CPU 切换的时间间隔非常快；
2. 而我们人能够感知到的时间范围相对来说要粗得多；
3. 所以我们就仍旧感觉不到它的切换。

就是这两个进程非常快速地在切换：刚刚执行一下马上切到下一个，执行一下切到下一个。对于我们人来讲感受不到这种切换，因为我们人能够感知到的这个时间变化范围相对来说要粗得多，但是 CPU 上进行调度、进行切换的时间粒度要细得多，它们差了几个数量级。

那什么情况下人能感觉得到呢？就是你这个 CPU 上的任务太多了、它不断地切换，结果有可能就是一个任务计算量太大，切过去的时候已经比较晚了，那我们人已经能感受到这种中断了。但通常情况下 CPU 足够强、你认为没那么大的计算量的时候，我们是感受不到这种切换的。

> **老师总结**：怎么样来实现多个任务同时执行，它的基本逻辑就是这个逻辑——我把 CPU 的时间切成很多份，大家轮流来用；只要你这个时间片足够小，我切得足够快，人就感觉不到这种切换的存在。

**定义**：**并发**（严格表述）。我们的播放器和 word 编辑器，我们就称作它在并发地执行。并发的意思就是这两个任务看起来是同时在运行，但是在微观上它们仍然是串行的执行，就是大家轮流在用这个 CPU 这个资源。

### 4.5 影响使用体验的因素

**推导**：多任务执行时，影响每个任务执行速度的因素。

1. 如果这个 CPU 足够快，就是它的频率非常高；频率高就意味着单位时间它执行的指令数量就多。我们一般买 CPU 的时候都会看它的主频是多少，主频高低本质上就是说我们单位时间内执行的指令的数量。这样为了能让切换起来感觉不到这种切换，你肯定 CPU 主频越高越好，这样执行指令很快，大家一下就轮流到下一个了，感受不到这种情况。
2. 还有就是我尽量任务要少一点。任务少的话，大家下次被调度再执行的时候，概率更大；如果你只有两个任务切换跟十个任务切换，它很显然对这个 CPU 的资源的分配是完全不一样的。
3. 所以什么时候能感受到切换的存在：如果你 CPU 很差，那一般人就能感受到这种切换了；还有就是你任务太多、每个任务都是在大量的计算，那我肯定也能感受到这种切换。通常情况下任务不多、计算量也很轻、而且 CPU 足够快，那你就感受不到这种情况。

这样就给我们的一种感觉：所有的任务感觉都是在独立地使用这个 CPU。那么独立在使用 CPU 就给我们一个抽象：我们有**多个虚拟的 CPU** 在各自支持多个任务在运行。这就是实现 CPU 资源抽象的基本办法。

> **老师总结**：时间复用给了我们一种幻觉，就是所有的任务都好像独占这个 CPU 一样。唯一能影响对 CPU 使用体验的因素就是：第一，你的 CPU 是不是足够快；第二，你的任务是不是多。多到一定程度，或者你的 CPU 慢到一定程度，这个效果就不是很好了。

### 4.6 老师提出的开放问题

> **老师提问**：除了 CPU 快慢和进程数量多少以外，还有哪些因素会影响到我们调度时的 CPU 资源利用率？在调度多个进程同时运行的时候，应该考虑哪些因素，才能让这些多个进程在使用 CPU 的时候尽量做到资源效率最高？有很多个进程同时运行时，调度哪些来运行最合理？

老师自己评价这个问题比较开放，随后给出了核心逻辑。

### 4.7 多任务执行的根本动机：IO 等待

**推导**：为什么多任务能提高 CPU 利用率。

1. 大家都知道进程就是一个程序的一次运行，那这个程序的基本逻辑就是一系列连续的指令的运行；
2. 很显然是，我们的进程在运行的过程中，如果没有其他因素影响，它就是不断地连续在执行指令，而这些都要耗 CPU，本质上它就是偏计算的；
3. 但是我们有些指令的运行，它可能不需要太多 CPU 的参与，或者说 CPU 这个资源有时候使用率没那么高；
4. 比如说如果一个进程要频繁地去外存也就是硬盘上去读资源，那么它要去外存上读资源，这段期间可以想象得到，因为外存相对来说跟 CPU 比它就要慢得多；
5. 你要跟外存打交道，也就是进行 **IO**（Input/Output）操作的时候，那这个 CPU 其实要在这里等的：比如你要去读一个文件，你要等这个文件所在的外设把这个数据传回到内存的时候，你才能继续处理；
6. 很显然在读外存的时候 CPU 是在空闲着的；
7. 所以这时候我们把要读文件的这个进程切换出去，其实一点都不影响那个读文件的进程的执行，因为本身它在这里等；
8. 这时候把 CPU 的使用权交换给其他进程来运行，那就是非常合理的一个选择。

**推论**：正因为这个原因，我们才可以允许多个进程并发执行，而且让人感觉好像没啥影响，资源利用率也提高了。本质上的原因就是我们每个进程并不是所有时间都在使用 CPU 这个资源，有时候它需要去等待外部的一些资源，比如去硬盘上读数据；在读数据这个时间段之内，你完全可以把这个 CPU 释放出去让其他进程来运行。

**反例**：如果所有进程都是纯计算的，多任务还有收益吗？

- **题目**：假定所有进程都是纯计算任务，多任务运行还有多大收益？
- **解答**：如果是纯计算，那你多个任务在运行的时候总的收益其实不会太大，只不过是来回切换，只是说先后顺序可能有先有后，而且最后完成时间可能有些长有些短。
- **结果与点评**：但如果有些进程有 IO 操作，那这时候不断切换就变得非常有意义，因为有些进程在进行 IO 的时候 CPU 是空下来的；如果你还让它占 CPU，那这个 CPU 的资源就被浪费了。所以这时候就把它切出去，让另外一些要计算的任务重新来占 CPU 接着执行，那就变得比较合理。

**推导**：进程特征如何影响调度收益。

1. 除了 CPU 更快、任务更多以外，进程本身的特点也会影响它的调度；
2. 进程本身的特点就是：有些任务它是纯计算的，有些任务它是计算和 IO 各占一半，有些任务它可能是 IO 更多；
3. 如果我们在调度的时候，就把那些有 IO 的和那种纯计算的、或者说大部分任务都是既有 IO 也有计算混在一起调度，那我们最终的收益会比较大；
4. 因为让一些正在 IO 的进程让出 CPU，让那些需要计算的进程来占用 CPU，就可以让我们整体的 CPU 利用率是最高的。

> **老师总结**：多任务的本质就是让多个任务并发执行，我们利用这种并发来最大化 CPU 的利用率。这就是并发的主要目的——让多个任务运行，可以潜在地把 CPU 利用率提高。

### 4.8 最佳切换时机

既然并发的目的是让 CPU 利用率提升，那么它的基本逻辑刚才讲就是时分复用：某一个进程占用一段时间 CPU 以后，让它切出来，让另外一个进程运行。那什么时候切呢？

**推导**：把进程切出去的最佳时机。

1. 最好的时机就是正好你这个代码执行到要读 IO 的时候；
2. 它把那个读 IO 指令已经发出去了，要去硬盘上读某个文件；
3. 这时候你要等待这个硬盘上的文件传回来，你把它切出去是最好的；
4. 因为这个时候它反正是要等待这个数据，你让 CPU 在这里白站着也没啥意思；
5. 然后我们就把它切出去，另外一个进程来运行，这时候另外一个进程就可以比较好地来占用 CPU 资源；
6. 等你把这个数据读好以后，你再把它切回来，那不就正好？
7. 这样的话就不会占用你的总的完成时间，也可以让 CPU 资源可以充分利用。

### 4.9 切换开销与上下文的引入

时间上共享需要解决一个问题：多个任务同时执行就意味着 CPU 在不断地切换，那切换就是我们需要考虑的一个设计开销之一。

比如说你刚开始在 word 执行，下一次要换成 player（播放器）执行，那 word 在执行的时候它会有各种各样的**上下文**信息。

**定义**：**上下文**（context）。上下文的意思就是跟这个进程运行相关的一些状态数据，典型的就是寄存器里面保存了一些数据的值。

> **老师比喻**：这就类似于我们上课的逻辑——我们每个同学可以认为就是一台计算机。现在我们每个同学要做很多事情，就是多任务执行：比如我们现在上操作系统课，那也许下一个时刻或者明天大家上另外的课，就可以认为这些不同的课都在我们每个同学身上运行。上操作系统课你有一个上下文，这个上下文就是今天的课程内容讲什么内容、讲到哪里。我们下次再继续上操作系统课时要下周了，就是我们调度的时候是每周过来一次执行，执行到这周结束，它有一个上下文，就是上到哪个地方。执行完操作系统这个时间片，你就要切到下一个课程，下一个课程你又得把它的上下文给恢复过来，就是你要接着我们上次课结束的地方接着来学习。这就是两个不同进程的切换，就跟我们上课一样。

在切换的时候，你大脑里都会把那个上下文保存起来：比如说你要在你的书看到第几页，然后做一个标记，把这一页折一下，这就是你的上下文，相当于你上次看到什么地方，你下次重新来看的时候要接着上次看到那一页接着看。

所以说我们在切换的时候就要考虑这个上下文信息的切换，否则就会出错：下次接着上操作系统课的时候，如果我们没有保存这个上下文，下周五再把上一周内容重新再学一遍，这就没有意义了。所以上下文本质上就是跟进程运行的状态有关，切换的时候就要考虑这个状态。

## 五、时间与空间共享：调度器与调度策略 [00:57:35–01:07:05]

### 5.1 CPU 的时间共享与排他使用

接着来看多任务同时运行时，它们对 CPU 资源的共享。共享来讲，CPU 这个资源就是按照时间来共享，就是 **time sharing**：每个固定的时间段之内，它只有一个进程在占用，就是在某一个时间片之内它是一个 **exclusive use**，就是一个排他性的使用，不可能多个人同时使用。

### 5.2 空间共享

另外一种共享叫做 **space sharing**（空间共享），意思就是我们一个大的空间把它切成很多小的逻辑块，我们每个人只使用其中的一个小块。这就有点像把一个大的空间切小，然后轮流大家每个人使用一部分，这就是按照空间来复用。

**表格**：时间复用与空间复用的对应关系。

| 共享方式 | 英文 | 含义 | 典型资源 |
|---|---|---|---|
| 时间复用（时分复用） | time sharing | 每个固定时间段内只有一个使用者，排他性使用 | CPU |
| 空间复用（空分复用） | space sharing | 把一个大空间切成很多小的逻辑块，每人使用其中一块 | 内存、磁盘 |

对于实现虚拟化来讲，时间复用和空间复用都需要：时间复用的基本逻辑就是 CPU，空间复用的基本逻辑就是内存。

### 5.3 磁盘的空间共享

磁盘这里提到了一个磁盘，磁盘的空间它也是按照空间共享。就是你这个磁盘，比如你买了一个硬盘，它是一个 T 的硬盘，这一个 T 的空间它是按照空间复用的：不同文件肯定是存在这个硬盘的不同位置，它不可能是大家轮流在使用这个位置，那么这个硬盘它一定是按照空间来共享的。

### 5.4 切换机制与调度器

为了能实现每个进程感觉都在独立使用 CPU，我们就需要有一个机制，什么机制呢？就是**切换机制**：切换机制本质上就是我们让不同的进程在不同的时间片排他性地使用这个 CPU，这样就改成每个进程都在独立使用这个 CPU。

为了能实现时间的共享，刚才讲就是需要一个**调度器**（scheduler），让我们的 CPU 资源轮流在不同进程之间使用。

### 5.5 调度器要解决的问题

**定义**：**调度器**（scheduler）。调度器就是负责我们多个进程它的一个轮流运行的顺序。

**例子**：三个进程排队等待调度。

- **题目**：假定有进程一、进程二、进程三，它们都在这个队列里面排队等待运行，而现在我们只有一个 CPU，那下一个时间片到底选择哪个进程运行？
- **解答**：这就是我们调度需要做的事情。比如我们运行的一个最简单的调度算法 **FIFO**（first in first out，先来先服务）的顺序，那我们就先把最顶上的这个 P1 调度来运行，下一个就是 P2，再下一个 P3。
- **结果与点评**：这就是调度器要做的事情。

**推导**：调度器的两个基本要素。

1. 第一个就是一个**数据结构**，把这些所有等待调度的进程保存起来——我们要维护一个队列，这个队列就是等待调度的进程的一个数据结构，有多少个进程在这里排队；
2. 另外一个你就要维护一个**调度策略或者调度算法**（policy），这个调度算法就是负责从这个队列里面选择一个下一个运行的进程。

这就是我们调度器解决的问题。

### 5.6 FIFO、SJF 与超市结账比喻

不同的调度器差异在哪？差异就差在它的一个调度的策略，或者说调度算法不一样。我们每一种算法都有它的一个逻辑：先来先服务的逻辑就是我们按照常见的比较公平的逻辑。

还有一种策略就是 **SJF**（shortest job first，最短任务优先）。比如 P1、P2、P3 三个进程等待调度：

1. 一种办法就是先排队，就是谁先来谁先调度；
2. 还有一种办法，我就看一下 P1、P2、P3 哪个它运行时间短一点，我就先调度它。

为什么要选择时间短的先运行呢？时间短的先运行给我们一个比较好的体验：每个进程都感觉可以平均起来的话，它这个等待的时间会比较短。

> **老师比喻**：就像类似我们在超市那里结账一样。排了一个队，前面一个人买了一车东西，结果你只买了一瓶水，那你这个买一瓶水的人排在那个买一堆东西的人后面，你就感觉很不舒服，因为你要等待他捡那么多东西你才能结。那如果你们两个位置交换一下的话，那很显然是就感觉好像大家体验都还可以接受：那个买一堆东西的人只需要等待你结账一瓶水的时间，然后结果你就不用去等待他结账那么长的时间，那总的平均的等待时间相对来说肯定变小了。

**结果与点评**：就是你交换了一下这个计算的顺序，总的时间不会变，但是每个人的平均等待时间会降低一点。这就是我们为什么要把短任务优先的原因。

### 5.7 优先级调度与银行取号比喻

当然也可以有其他策略，比方说我们就按照**优先级**（priority）。这个优先级的调度相当于是类似于我们银行的策略：

> **老师比喻**：大家去银行去排队、存钱取钱的时候，通常来讲我们都会先取号，取号的话它就是一个排队策略了——你可能是一个 VIP 客户，他给你排队的时候就把你自动地排在前面，你下次得到调度的时候，他就会优先调度你；那如果你是一个普通客户，那可能就是调度的时候就后调度。这是它的一个基本的逻辑。

**例子**：实时任务与长时间计算任务的优先级。

- **题目**：一个进程要处理实时任务，另一个进程只是去做那种时间周期长的计算，谁应该优先级更高？
- **解答**：很显然是，需要实时任务的那个进程肯定优先级应该高一点，才不会让整体的这个体验变差；而那个需要长时间计算的任务，你把它耽误一点其实问题也不大。
- **结果与点评**：所以我们就有不同的调度策略，优先级的逻辑就是按照重要性来排。

### 5.8 调度策略的综合性与优化目标

那我们来想一下，我们在选择调度策略的时候应该考虑哪些因素？比如在什么情况下应该选什么调度策略，或者一个操作系统它到底有几种调度策略？比如我们 windows 里面或 linux 里面，它用的到底是什么调度策略？那很显然是，我们这个就是需要考虑：第一，我们的**优化目标**是什么；第二，任务的**特征**是什么。

> **老师强调**：我们操作系统会维护一个比较复杂的调度算法，它不是一个简单的策略，而是一个比较复杂的调度算法。这个调度策略方面我们可以专门的章节来讲。反正就是说我们常见操作系统，它不是一个简单调度，而是一个比较复杂的一个调度策略，它是会综合考虑多方面因素，既要考虑你这个等待时间，也要考虑相对公平性，所以它是一个综合的因素。

## 六、进程的资源使用与进程状态 [01:07:05–01:17:24]

### 6.1 进程使用的两类资源

既然我们讲到了对 CPU 的抽象使用，它就是一个进程这个概念，而这个进程概念本质上就是一个运行的程序。这个程序就包括一些对这个资源的使用，资源使用包括**内存资源**和**寄存器资源**：

- 内存资源就是我们刚才讲它的一个地址空间；
- 另外就是我们的寄存器，就是我们在 CPU 上的一些临时存储的一些值。这个寄存器就包括一些栈的指针，或者它的一些当前运行的一个指令的计数器，**PC**（program counter）什么之类的。

这就是一个典型的我们需要保存的一些数据。

### 6.2 进程是受状态影响的指令序列

**定义**：**进程**（另一种刻画）。进程本质上就是一个执行指令的序列，这个执行指令的序列会受我们这个进程的上下文或者状态所影响。

简单说就是我们相当于是把一个程序——程序的话翻译过来，它就是一些指令在数据上的运行——所以我们的进程就是执行这个程序当中的指令序列。这个执行的过程中，它会受一些状态变量的一些影响。比如你要去读写 IO，那我们 CPU 可能就会知道这个状态，那这样的话我就不把你切出去，所以这次你的执行可能就会有变化。

我们这个程序在进程执行的过程中，需要把这个状态信息一直保存着，因为我们是在不断切换的，所以你一定要把这个状态信息保存好。

> **老师比喻**：就像我们刚才讲的，我们每个同学就像一台计算机，里面有 CPU 在不断地上课学习。你在切换不同的课的时候，你需要把不同课的上下文保存起来：比如我们今天上操作系统，你学到哪里、学的内容是什么，你下次课再来运行操作系统这个进程的时候，你就不能把上次的内容重新来学一遍，你就要接着上次的这个中断的点接着往下学习，所以这就是一个状态。那么我们今天学的什么内容、学到什么点，就是你的一个状态信息；你再切换到下一个课的时候，这个状态信息一直要保存着，否则这个状态信息丢失了以后，你下次就恢复不了你的现场。

### 6.3 进程相关的 API

既然这个进程在我们操作系统里面是一个非常重要的一个抽象，那操作系统一定是要为这个进程设计一系列的这种 API。这个 API 就包括创建、销毁、等待、各种各样的控制，还有就是查询它的状态等等。

### 6.4 进程的创建

**推导**：进程的创建过程。

1. 进程的创建很简单，就是我们把在磁盘上保存的一个**可执行文件**加载到内存里面去，这个文件的内容就是它的代码和数据；
2. 同时给它分配这个数据结构；
3. 就把对应的这个代码也好、数据也好，放到对应的这个数据结构里面；
4. 这样就形成了一个进程的概念。

所以逻辑很简单。然后有了这个进程的实体以后，我们就会让这些代码跑到 CPU 上去运行，然后轮流来运行。

**推导**：多任务同时执行的基本原理。

1. 实际上内存里面是存了很多进程实例；
2. 我们就是轮流地让这些进程的实例、比如说进程里面的代码到 CPU 上去运行；
3. 具体的流水线是：物理的磁盘上面它存了很多可运行的程序；
4. 这些可运行的程序，我们把它加载到内存里面去；
5. 同时在内存里面分配关于进程的一些数据结构；
6. 然后把它的数据段、包括它的一个代码段都保存到这个内存里面去；
7. CPU 在运行，一个调度器知道轮流把这些在内存里面的一些进程实例放到 CPU 上去运行。

**推导**：创建之后的三个动作。

1. 创建过程刚才讲的是一个加载它到内存；
2. 接着我们给它初始化；
3. 接着我们就会来进行一个调度；
4. 每个进程它都在内存里分了不同的虚拟地址空间，这个虚拟地址空间就包括一些不同的段，包括我们的这个 heap 区域或者是 stack 区域什么之类的，这样就可以让这个程序能够比较好地在内存里面运行。

### 6.5 栈与堆的区别

这里有一个不同的区域，就是除了 stack 还有 heap。这个 stack 和 heap 的区别是什么呢？大家在学这种程序设计的时候应该都知道：

- **栈**（stack）：它保存的内容是那种临时变量，典型的就是我们的一个函数里面的那种局部变量，还有一些这种临时变量；
- **堆**（heap）：相对来说就是一个动态可扩展的区域，一般来讲就是可以动态去扩展的内存区域。主要是你要分配一个数组、新申请一个数组空间，那你就是把它放到 heap 区域，就是用那个 `malloc` 去分配的，这样的就是一个动态可以扩展的区域，就是堆。

**表格**：堆与栈的对比。

| 区域 | 保存内容 | 增长方式 | 典型来源 |
|---|---|---|---|
| 栈（stack） | 函数局部变量、临时数据 | 随函数调用/返回自动伸缩 | 函数内声明的局部变量 |
| 堆（heap） | 可动态创建的数据 | 动态可扩展 | `malloc` 申请的空间，如新数组 |

### 6.6 入口、PC 与现场恢复

操作系统把这些内存区域创建好以后，接着就会按照我们的调度来切换不同程序的运行。切换的时候，当我们这个进程第一次被调度的时候，它的这个代码执行的入口就是这个 `main` 函数的入口，我们都是从这个地方开始执行。

执行到这个过程中的话，它就是按照我们有一个 PC 寄存器，PC 就是 program counter。简单的说：

1. 我们每个进程它的代码都有一个入口，就是 `main` 函数这个入口；
2. 这个入口开始执行后，它就会用一个寄存器即 program counter 记录下当前执行的哪条指令；
3. 接着我们就不断地把这个 PC 加 1，然后往下执行就行了。

这样就构成了我们这个程序控制的一个逻辑：

$$\text{顺序执行时}\quad \mathrm{PC} \leftarrow \mathrm{PC}+1 \qquad (\text{分支、循环则发生跳转})$$

**推导**：切换时如何保证"程序没有被中断"。

1. 我们只需要在切换的时候记录下当前执行到哪条指令；
2. 下次我们恢复的时候，只需要把这个 PC 寄存器中断的指令接着来执行就可以了；
3. 还包括一些状态信息，包括其他寄存器的一些值是多少什么之类的，我们都把它保存起来；
4. 这样就可以保证你在不断地切换进程的时候，也能够恢复到现场。

**例子**：程序在第 100 条指令处被切出。

- **题目**：程序前面执行到比如第 100 条指令的时候被切换出去了，下次再被切换进来时从哪里继续？
- **解答**：就像看书的时候，你昨天看到哪一页，你把那一页记下来做个标记，下次再来看的时候就接着从那个中断的地方去看就行了，这样它不影响你的阅读体验。程序也是这样：下次再被切换进来的时候，你就接着第 100 条指令的地方恢复来执行就行了。
- **结果与点评**：这样虽然是在轮流使用 CPU，但是我们感觉这个程序没有被中断，就是接着来执行。

### 6.7 虚拟地址空间的基本结构

**定义**：**虚拟地址空间**（virtual address space）。我们把这个静态的代码跟数据放到内存以后，就在内存里面形成了一个虚拟的地址空间，就是每个进程它都有自己的一个地址空间，这个地址空间就是从零开始到最大。它的基本结构就是：**代码区**、**静态数据区**、**堆**，还有**栈**。

通常来讲，在这个堆和栈的中间这些区域通常来讲都是没有被占用的，然后我们这个堆它可以动态往下去扩展。这就是它的一个基本的一个空间的结构。

两个典型进程的完整生命周期过程，也说明地址空间是被"分给"各个实例的：内存里同时存在多个进程实例，调度器轮流把它们的代码送上 CPU。

## 七、进程三态及其转换关系 [01:17:24–01:28:51]

### 7.1 三个基本状态

接下来我们再看这个进程的状态。进程状态是什么？就是我们前面讲，每个进程都是可以被动态地切换进切换出的，很显然是就有了一些进程运行的一些基本状态信息。哪些状态信息呢？我们可以从它的一个生命周期的角度来看，就很容易理解它的状态。

**推导**：从单 CPU 事实推出三态。

1. 我们可以简单地认为我们只有一个 CPU；
2. 只有一个 CPU 意味着每一个具体的时刻永远只有一个进程被 CPU 执行；
3. 那么这时候的那个进程它的状态就是 **running**，就是正在运行的这个状态——我们 CPU 正在执行的那个进程，它就是 running；
4. 那么除了这个正在执行的 running 状态，其他的进程肯定都在没有被执行；
5. 没有被执行的进程又分两种：一种是处于 **ready** 状态，一种是处于 **block** 状态。

**定义**：**ready**（就绪）。ready 状态的进程就是在这里有一个队列，这些进程都是在等待被调度。

**定义**：**block**（阻塞）。block 的这些状态的进程一般来讲就是等待某个事件发生。我们简单地说，就是类似于有些进程它去读我们的文件，读文件的话它在等待这个读的文件的数据的时候，它的状态就是 block。这个状态就意味着它是被某个事件阻塞了，被什么事件阻塞呢？就是被从外存上读文件的这个事件阻塞了。只有当那个文件读好以后，它的状态才会改变。

那么处于 ready 状态的进程是哪些呢？ready 状态的进程就是我的这个进程它是不会去等待任何事件，我要等的就是等待下次被调度。

### 7.2 被调度的两个条件

我们可以认为一个进程它要被调度来执行，肯定需要一些条件：

1. 第一个，你要执行的**所有指令和数据都被准备好了**才能被执行。如果数据没有被准备好，你肯定执行不下去。
2. 第二个，我要**物理上把这个指令放到 CPU 上运行**，就是被 CPU 调度选中来运行，那么才能真正的去执行。

**推导**：三态与两个条件的对应。

1. 如果这两个因素都不具备，那很显然你肯定是在这里被调度不了的；
2. 如果你的数据没有准备好，你就是 **block** 状态；
3. 如果你的数据准备好了、只是等 CPU，我们就是 **ready** 状态；
4. 如果你是 ready 状态，同时我又把 CPU 分配给你了，你就是处于 **running** 状态。

这就是几个状态之间的关系。其实这个也好理解：三种状态就是 running、ready、block，这三种状态就是最基本的一个状态，是我们所有调度器、所有关于进程管理的最基本的状态信息。

**例子**：ready 与 block 的直觉。

- **题目**：怎样快速理解 ready 和 block 的区别？
- **解答**：这个 ready 状态你可以认为这个进程它是万事俱备了，只欠 CPU 调度了；block 这个状态就是它还缺一些东西，你不能把它去 CPU 调度。
- **结果与点评**：这两个直觉直接对应上面两个条件。

### 7.3 谈恋爱比喻

> **老师比喻**：我们举个简单的例子，主要是谈恋爱。某个同学最后能不能谈恋爱呢？那很显然他需要满足一些条件：第一个他已经成年了，第二个有其他的男生或者女生喜欢你。那如果你没有成年，你肯定就不能去做这个事情，你就是 block，要等待什么时间呢？等你满 18 岁，然后满足这个条件，然后把你移到这个 ready 队列里面，你可以参与去谈恋爱。那么什么时候可以真正地去谈呢？就是另外的你的男朋友或女朋友把你选中，或者你们俩相互选中对方，那么这样的话就处于 running，就那样就正式开始。

就这样的一个状态：一个是它不满足条件、还不能去谈；一个是满足条件但是还没有遇到另外一个；如果两个条件都满足，那就是正式进入这个 running 状态。

**结果与点评**：所以这就是它的一个状态转换关系，其实就是：第一个你是不是把资源都准备好了；如果资源都准备好了，我只需要给你一个调度的时机，你就可以参与 CPU 竞争。

### 7.4 更复杂的状态

这三种状态是最最基本的状态，还有其他状态，我们会讲进程的部分详细讲，其实就是还有一些类似于更复杂的状态，比方我们如果考虑内存的一些情况，它还有这种 **suspended**（挂起）的一些状态，就是被挂起的一个状态；当然还有就是它结束的一些状态。最核心就这三个状态。

### 7.5 状态转换的触发事件

大家一定要很清楚理解这个状态的转换关系，就是什么时候从一个状态转到另外一个状态。

**推导**：四个转换的触发条件。

1. **→ ready**：这个进程的所有资源都准备好，只欠 CPU 去调度，那么它就是 ready；
2. **ready → running**：被调度了以后，它就处于 running。running 的进程数量是只有一个，就是整个系统只有一个；
3. **running → block**：当我们这个 running 的进程它去运行 IO 操作、就是要去读文件的时候，那就意味着它要等待读外部文件的那个事件完全处理好，它才能接着运行下面的内容，那这时候我就把它转到 block 这个状态；
4. **block → ready**：就是你的这个 IO 读好了，就是那个文件的数据已经读好了，然后重新转到这个 ready，然后等待下次调度；
5. **running → ready**：就是我们 CPU 给你分配了一个时间段，你这个时间段用完了，因为大家轮流使用，不可能你一直用下去，那这时候虽然你不进行 IO、你可以直接运行，但是我们也把你从 CPU 里面踢出来放到 ready 这里面，等到下次调度。

**表格**：状态转换与触发事件。

| 转换 | 触发事件 |
|---|---|
| 新建/条件满足 → ready | 所有资源（指令与数据）都准备好，只欠 CPU 调度 |
| ready → running | 被调度器选中，CPU 分配给它 |
| running → block | 运行 IO 操作，等待外部文件数据就绪 |
| block → ready | IO 完成、所需资源到手 |
| running → ready | 分配的时间片用完，被从 CPU 上踢出 |

### 7.6 转换的单向性与调度候选集

大家看一下：ready 和 running 之间它可以相互转换，但是 running 和 block 之间它是单向的，而且 block 到 ready 也是单向的。

> **老师强调**：大家一定要记住，就是你不可能直接从 block 转到 running。因为你 block 了以后，你把这个所要的资源拿到以后，你要重新到 ready 队列里面去排队，排好队以后你才能重新到 running。也就是说，我们选择调度的那些候选集，只能从 ready 队列里面选，就是所有都准备好的这些进程你才能去参与 CPU 的调度；那些没有准备好的，你就到 block 的这个区域去，等你把那个 block 中需要的东西准备好了以后，你再排队进入这个 ready 队列里面等待调度。

所以它的转换关系跟转换的事件，大家要比较清楚地知道：什么时候它从一个状态转到另外一个状态，以及这个状态转换的时候能从哪个转到另外一个。

> **老师强调**：大家一定要把这个图理解得比较清楚。这个图就是进程的三大状态之间的转化关系。

### 7.7 例子：两个进程并发运行的状态转换

这里举了一个简单的例子，就是两个进程：零号进程（P0）、一号进程（P1），他们两个都是在并发运行。并发运行就意味着我们单位时间只能有一个处于 running 的进程，就是我们 CPU 只能运行一个进程，每个微观时刻只有一个进程 running。

**例题**：P0 与 P1 并发运行，各自经历怎样的状态序列？

**题目**：进程 P0 与 P1 并发运行，请描述它们的典型状态转换过程。

**解答**：

1. 进程零先运行，运行的第一个时间段是它运行，第二个时间段也是它运行，第三个时间段也是它运行；
2. 结果到第四个时间段，它可能执行了 IO 操作，就 P0 执行了 IO 操作；
3. 这时候它就被阻塞掉，阻塞掉的话我们就切到 P1 来运行；
4. P1 运行到这里的时候，我们这个 P0 的那个 IO 操作接着完成了，完成了它就会转到 ready 队列；
5. 如果是下一步 P1 这个运行结束，那么就切换到 P0 重新来运行。

**结果与点评**：我们就经历了从 running 到 block 再到 ready 再到 running 的过程——P0 经历了 running、block、ready、running 这个过程，P1 经历了从 ready 到 running，然后再到结束的这么一个过程。这个状态转换的典型的事件就是一些 IO 的操作和我们 CPU 调度器的一些调度。

## 八、进程控制块 [01:28:51–01:32:02]

### 8.1 操作系统维护的控制数据结构

刚才讲了，我们进程它是由程序的一次运行实例构成的，这个运行实例在操作系统里面它要给它分配内存空间，这个内存空间里面它就保存了一些典型的数据结构，这是用来做控制的数据结构。

这个控制数据结构是我们操作系统维护的，它跟那个进程的空间是相对来说是独立的，就是我们操作系统维护了一个来保存进程信息的这些元数据，那我们就认为它是关于我们的进程控制的一些数据结构，比如这个**进程列表**，还有**寄存器的上下文**，以及还有一些什么 **PCB**，就是这个进程控制块。

### 8.2 PCB 的定义与用途

**定义**：**进程控制块**（Process Control Block, PCB）。它其实就是用来保存某一个进程的基本信息的这么一个数据结构。每个进程都有一个 PCB，就相当于是维护了这个进程的基本信息。

我们这个进程的基本信息，它是用来后续方便来进行调度的，要读它一些对应的字段来进行调度。

> **老师比喻**：类似于我们每个同学是一个进程，我们在这个学校的这个管理系统里面维护了每个同学的基本信息，比方说你的名字是什么、你的专业是什么、你的年龄是什么，这就是他的 PCB，就是关于这个进程的一些基本信息。

### 8.3 PCB 的字段：以 XV6 为例

这个进程控制块的基本结构可以看一下，这里是用 XV6 系统里面它记录下的一些基本结构：

1. 包括它的一些**寄存器信息**；
2. 包括这个**上下文信息**，包括我们的这个寄存器、`stack pointer`，还有它的一个 `base register` 等等，这是它的上下文；
3. 这个上下文很显然是进程运行的过程中需要保存的一些状态信息，这个状态信息就是一些典型的指针和它存的一些数据；
4. 另外的话就是**状态**，状态就是典型的几种状态，这里列了一些 `unused`、`sleeping`、`runnable`、`running` 等等。

那么到底有哪些呢？就是保存了一些进程的基本信息：比方说它的一个进程的 ID、它的一个父进程是什么、它的一些打开的文件，还有一些它的上下文那些存的一些数据等等，还有一些其他的信息。

> **老师总结**：简单的说，就是进程控制块就保存了跟这个进程所有相关的信息。

## 九、系统调用与进程 API（fork / exec / wait） [01:32:02–02:01:20]

### 9.1 系统调用的概念

前面我们讲了进程这个抽象的概念，它其实就是一个程序在我们操作系统的一个运行的实例。为了能让这个实例能够比较好地控制，我们就要提供一些 API，比如说创建，比如说结束，这是典型的对进程控制的 API。

**定义**：**系统调用**（system call）。这里提到的典型的 system call 就是系统调用，这个系统调用是指我们操作系统它实现的一些功能的一次访问，就是调用。

比如典型的就是我们操作系统有各种各样的操作，比如说它要对文件操作、对进程操作、对内存操作，但是这个调用你就可以认为就是类似于一些 API：我们操作系统的底层代码实现了很多不同的功能，这些功能包括对文件、对进程、对内存的一些操作，而这个 API 的使用你就可以通过系统调用的方式去使用。

所以你可以认为，你把操作系统当作一个类似于很大的一个库，它提供了很多 API，然后这个 API 都可以供上层进行一个使用。

### 9.2 为什么不能交给应用程序直接操作

那系统调用为什么叫系统调用？因为它就是提供了对底层的一些功能，这个底层功能你要通过系统调用去访问。

那为什么不能交给应用程序直接去操作？因为你如果应用程序直接能操作这种底层的一些功能，有可能会造成那种安全的隐患。比如你的某个应用程序去修改人家的这个调度器的一些代码，或者是修改内存里面的一些数据结构什么之类的，那很显然这就很危险。

所以我们就必须要用一个系统调用的方式去让它合理地使用。这就是系统调用。

### 9.3 三个典型的进程系统调用

我们对进程相关的一些操作也可以通过一系列的系统调用来完成。这里列了三个典型的系统调用：一个叫做 **fork**，一个叫 **exec**，一个就是这个 **wait**。这三个系统调用是我们在进行创建进程或者是控制进程运行的过程中所常见的一些系统调用。

### 9.4 fork：克隆语义

**定义**：**fork**。这个 fork 是最常见的对进程的创建的一个系统调用。简单地说，这个 fork 就是创建一个进程。

**推导**：`rc = fork()` 的执行过程。

1. 我们看一下就是这样 `rc = fork()`，那么就相当于是我们调用了这个创建进程的一个系统调用；
2. 这时候我们操作系统就会复制一个跟当前进程一模一样的进程出来；
3. 就相当于是你这个代码、这个 `main` 函数之所以能够运行，它本身就是一个进程；
4. 这个进程如果执行到这个 fork 的时候，它就会创建一个这个进程的一个分身出来，就克隆了一份出来；
5. 克隆一份出来，现在就原来一个进程，现在变成了两个进程。

所以这就是 fork 的基本作用。你可以认为 fork 就是把当前的进程创建一个克隆的分身出来：本来是一个，你现在是克隆一份一模一样的出来，但是它变成了两个。它们有两个不同的 ID 号，在进行调度的时候，它是独立地进行调度，就相当于是两个不同的进程。

### 9.5 fork 后父子的区分

这个 fork 创建出来以后，大家可能要问了：原来只有一个，那现在变两个了，我怎么区分这两个？另外创建出来一个代码，它是从哪开始执行？

**推导**：父子进程的区分办法。

1. 它就是从这个 fork 后面的代码开始执行，就相当于你创建了一个分身，这个分身就接着从这条语句后面的代码接着执行，他们两个都是从那个语句那里执行；
2. 执行的时候怎么来看哪个是分身呢？那我们就要这里有个判断语句，就是 `if (rc == 0)`，那我们这个说明它就是新的，即子进程；
3. 如果是 `rc` 等于他的进程号，那么可能就是他是一个 parent 这一层，即父进程；
4. 这样就相当于我们两个进程通过这个 if 语句来进行区分了。

后续大家就可以通过这个判定语句来判断到底是哪个是父进程、哪个是子进程：

```c
rc = fork();
if (rc == 0) {
    /* 子进程分支 */
} else {
    /* 父进程分支，rc 为子进程的进程号 */
}
```

### 9.6 fork 创建过程的要点

我们来看一下创建的这个过程其实很简单，就是某一个正在运行的代码执行到这个 fork 以后，系统给他复制了一份出来：这两个进程是一模一样的进程，它的代码和其他东西都完全一模一样，只是说我创建了一个分身；接着它执行的这个进程的一个点就是从下一条语句开始分，这样这个父进程执行 if 的一个分支，子进程执行 if 的另外一个分支，这样就是两个各自独立运行的。我们在进行调度的时候，就要用调度算法来不断地切换这两个进程，就是 fork 所创建的。

> **老师强调**：fork 大家一定记住，它就是克隆了一个同样的进程出来，只是说克隆出来这个进程它的进程的 ID 肯定是要重新给它分配，但它的代码什么东西都完全一样的。

### 9.7 fork 后父子执行顺序的不确定性

大家可能要问了：既然 fork 以后它会创建两个一模一样的，那我们这个到底是哪个先运行、哪个后运行？因为现在是一个变两个。

**推导**：谁先运行由谁决定。

1. 哪个先运行哪个后运行，这个要看 CPU 的调度；
2. 这个是有一定的不确定性的；
3. 我们运行多次可以发现，它执行的这个顺序可能是 parent 先，也可能是 child 先，这个不一定；
4. 就是下一条到底谁先执行，这个要根据我们的调度器：那有可能正好是调度 parent 先，有可能调度的这个 child 先，都有可能。

### 9.8 wait：控制父子执行顺序

另外一个系统调用叫做 wait。这个 wait 又是干嘛的呢？

**定义**：**wait**。wait 这个系统调用简单地说，就是我们创建了它的一个子进程以后，它就是会让这个子进程先运行，然后运行直到这个子进程运行结束以后，我们才返回过来运行，也就是以控制这个父进程和子进程它的一个执行的顺序。

我们为了让它有一种确定性——到底谁先运行——那就是加一个 wait 在里面，这样的话就是我们的这个 parent 就会等待指定子进程运行，子进程运行结束以后，父进程再运行。对，这就是怎么样来控制到底是谁先谁后：你加一个 wait 的一个控制的这么一个系统调用就行了。

**例题**：父进程分支加 wait 后输出顺序是什么？

**题目**：父进程和子进程的代码分支在 if 语句这里，子进程执行一个分支、父进程执行另一个分支；如果父进程分支里有 wait，运行结果如何？

**解答**：

1. 子进程是执行这个分支，父进程是执行这个分支；
2. 如果这个父进程里面有个 wait，它就会等待子进程先调出来运行；
3. 那这样的话就是我们子进程肯定是先运行；
4. 所以说运行的结果它就只有一种情况：我们每次都是这个 child 先输出，然后后面才是 parent 的输出。

**结果与点评**：这就是加了一个 wait 以后，就可以控制一个变两个的时候——它变成并发、并发的时候到底谁先运行。我们可能有时候希望有一个顺序，那怎么样控制这个顺序？你会加 wait 这个控制。

### 9.9 exec：代码替换语义

**推导**：从 fork 的局限引出 exec。

1. 刚才讲的这个 fork 这个 system call，它主要的作用就是创建了一个一模一样的进程；
2. 创建一模一样的进程之后，我们为了控制到底是子进程还是父进程谁先运行，加了一个 system call wait；
3. 接下来我们就有另外一个需求：大家可能想，就是我们创建一个新进程，它只能创建一个跟原来一模一样的进程，这显然好像不是能（满足）我们的大多数需求；
4. 我们通常情况下还是希望你创建一个进程，这个进程有可能是一个不一样的进程。

那怎么样来实现这个呢？那我们就需要用到另外一个就是这个 **exec**。

**定义**：**exec**。这个 exec 本质上就相当于是我们创建了一个新进程，并且用另外一个程序的代码作为这个新进程的一个代码区域。

所以它就相当于是类似于我们经常看到的一种穿越小说：你的一个灵魂附到另外一个人的躯体上面去了，那就相当于是这个只提供创建的进程只提供躯体，但是它的灵魂我们是运行另外一个程序。这就是它的一个 exec 的逻辑。

fork 是创建一个完全一模一样的，两个是完全一样的；那现在 exec 就是我们把它的代码去替换成我们这个新的程序。

> **老师比喻**：就类似于就是你创建了一个躯体，但是这个躯体被夺舍了，然后相当于是装了另外一个灵魂在里面。这就是 exec 这个作用。

**表格**：fork 与 exec 的对比。

| 系统调用 | 作用 | 新进程的代码 | 形象的比喻 |
|---|---|---|---|
| fork | 复制当前进程 | 与原进程完全相同 | 克隆出一个一模一样的自己 |
| exec | 用另一个程序的代码替换进程的代码 | 来自另一个程序 | 躯体被夺舍，装了另一个灵魂 |

### 9.10 例子：fork + exec 的运行结果

**例题**：子进程 fork 之后 exec 另一个程序。

**题目**：一个进程用 fork 创建了一个进程，在子进程这里需要去输出一些内容，并且我们会让它去执行另外一个代码（exec 带输入参数，运行另外一个程序），父进程还是维持原来代码。最后运行出来会看到什么？

**解答**：

1. 它这里需要去输出一些；
2. 并且我们会让它去执行另外一个代码，另外代码就是在这个 exec 这里，然后另外一个输入参数，然后来运行另外一个程序；
3. 相当于实际上它就是运行了另外一个程序的代码；
4. 而我们的父进程还是维持原来代码；
5. 最后运行出来的话，就是看到主进程的输出跟父进程的输出它是不一样的。

**结果与点评**：那原因就在于 exec 这里——这里是 exec 的另外一个呈现，就加了参数的一个呈现，那就相当于是用另外一个程序的代码来替代的逻辑。其实也比较简单，详细使用的话大家去试一下就知道了。

**例题**：打开 P4.c 并创建进程运行另一份代码。

**题目**：把 exec 加到另外一个进程，比如打开 `P4.c`、创建一个进程，会得到什么？

**解答**：这样的话就是可以去运行另外一个程序，可以详细看。

**结果与点评**：那逻辑其实就是大家知道的，就是相当于是在创建了另外一个进程，这个进程我们用其他的程序的代码来替换，就这样的。（该例中的具体文件名以原始课件为准，ASR 记录为"P4.c"。）

## 十、受限直接运行：用户态、内核态与系统调用 [02:01:24–02:18:48]

### 10.1 虚拟化的目标与时分复用的两个约束

我们前面讲，我们这个虚拟化的一个核心目的是什么？核心目的就是让多个任务在同一套物理的基础设施上面运行，这个就是虚拟化的一个基本逻辑。

那怎么样让这个虚拟的 CPU 它能够运行的效率比较高呢？通常来讲我们实现的办法就是时分复用，就是 time sharing。

**推导**：time sharing 必须考虑的两个因素。

1. 第一个你要考虑**性能**：我们在实现这个虚拟化的时候，要考虑不能有太大的性能损耗。你为了能实现多个任务同时运行，结果你加了很多不必要的开销进去，那有时候这个开销跟你的收益相比，有可能还不能跟收益打平，这样的话其实就不是我们想要的；
2. 另外就是 **control**：就是我们怎么样能够维持对 CPU 的一个控制。因为你存在多个任务的时候，你肯定需要在多个任务之间切换，那我们这个切换的过程中到底是由谁来主导、谁来控制？这样的话我们肯定有一个调度器来控制，怎么样来实现这个调度器就是我们需要考虑的。

### 10.2 最简单的直接运行模型

为了能实现进程在 CPU 上的运行、或者说程序在 CPU 上运行，我们一般是怎么做？我们可以从两个角度：第一个我们操作系统要做什么，做了以后程序的代码是怎么样被加载来运行。

**推导**：允许程序直接在 CPU 上运行时的流程。

我们假定我们允许程序直接在 CPU 上运行，那我们看一下这个操作系统要做什么呢？做的事情就是：

1. 我们给这个进程列表创建一个 entry——就相当于为了能让这个程序运行，你要在这个程序列表里面加一个条目，就是你新加的这个进程；
2. 接着给这个程序分配内存，就是前面我讲你要把这个程序加载到内存里面去，你要事先给它分配；
3. 接着我们把这个程序里面代码和数据加载到这个内存分配的内存里面去；
4. 接着我们也给它分配这个对应的栈；
5. 就是把当前 CPU 的这个寄存器给清零；
6. 接着我们就执行它对应的程序的这个入口，就是 `main` 这个入口。

这时候我们的控制权就交给了程序了。程序只有等它运行结束以后，才会把这个空间交回给我们操作系统。操作系统接着就是把它分配的内存给清掉、释放掉，然后接着把这个进程给它分配的 ID 信息什么之类的全都从这个列表里面清掉。

这就是最简单的逻辑，就是我们为了能让操作系统运行一个程序的最简单逻辑。

### 10.3 该模型的缺陷

很显然，我们这种逻辑对于这个程序来讲，它没有任何控制：就是如果一旦我们把控制权交给程序了，我们只能等这个程序运行结束，才会把这个控制权重新交回到我们这个操作系统这里来。所以操作系统它控制不了我们程序的运行。

这就是我们最早期的操作系统的实现，它就这样做的，就是我们单任务系统的时候，或者说我们就是轮流运行的这种机制，它就这样做的：你运行一个进程以后，这个进程要运行结束以后，它才把这个控制交回到你的操作系统。

**推导**：这个模型的问题所在。

1. 这种简单的实现肯定不是我们想要的，因为这时候我们操作系统对程序的运行控制很少；
2. 或者说我们这个操作系统就感觉是一个库一样，它可以提供各种各样的 API 让我们程序来运行，然后最后在运行的过程中我们操作系统就没有任何对它的控制权了，就是只能由这个程序自己运行，只有等它自己结束以后，它才会把这个控制权释放回来；
3. 那显然就是我们通常来讲这种模式就有很大的问题：让程序自己去实现很多功能；
4. 因为一个程序运行它可能有很多不同的功能要实现，比如它要去读文件什么之类的，如果你操作系统不提供任何支持，在这个程序运行过程中由它自己去做，那这样有可能会带来什么后果呢？
5. 就是这个程序如果它写了些这种潜在的恶意代码或什么之类的，就会影响我们操作系统运行的稳定性；
6. 比如它假定去自己去实现一些对文件的操作、对内存的操作，或者是对我们底层代码的修改，那有可能就会对整个系统造成一个非常大的安全隐患。

### 10.4 权限分离：用户态与内核态

那怎么样来解决这个问题呢？一种办法就是我们把这个对底层资源的使用权限尽量进行一个分离或者是隔离。

**定义**：**用户模式**（user mode）与**内核模式**（kernel mode）。我们这里定义出两种模式：应用程序它只有一些有限的权限，它不能访问所有的资源；所有的底层资源的访问或者是那种权限的定义，只能由操作系统来完成；我们应用程序只能通过操作系统提供的某些功能来进行对应的一些操作。这就是所谓的用户模式和内核模式。

这样的话通过这种两种模式的一个分离，来保证我们操作系统的一个稳定性或者安全性：你不能让应用程序去控制所有的东西，我们操作系统应该对底层的某些资源进行一些保护。

**推导**：两种模式下的操作边界。

1. 在用户模式下面你只能运行程序的一些基本的代码；
2. 你要对我们底层的一些内存或者是 IO 进行访问的时候，你就不能操作；
3. 你只能通过操作系统内核模式提供的一些特定的接口来操作；
4. 就相当于我们把它代码能进行的操作进行了限定：在用户模式下，这种用户态的各种操作你可以随意用，但是如果你要对底层进行修改或对其访问，你就只能通过我提供的标准接口去访问，你不能去自己写代码访问。

这就是它的一个核心逻辑：通过这种内核模式和用户模式的分离，把一些潜在的底层的资源的访问的安全性保护起来。

**推导**：系统调用接口的设计逻辑。

1. 我们操作系统它可以把各种功能进行一个封装，以某些接口的形式来提供给我们的应用程序；
2. 那应用程序就可以调用这种接口来进行对底层的某些资源的使用；
3. 哪些底层资源使用呢？一个就是我们要去访问一些文件系统，我们要创建或者是销毁一个进程，或者是进程间通信，或者是分配内存之类的；
4. 这些的话都涉及跟我们的硬件资源，或者是对我们操作系统的一些关键数据结构进行操作；
5. 所以说这时候你就不能让普通的进程随意来操作，随意来操作很显然就会带来安全隐患；
6. 所以这个就相当于我们把一些危险的操作、或者说我们认为重要的操作进行了封装，只能定义有限的一些功能暴露出来；
7. 这个有限的功能可以给你应用程序调用，因为核心的内核的代码是我操作系统自己实现的，它的安全性可以保证；
8. 这样就可以让我们操作系统不至于受到某些应用程序的这种安全的一种攻击。

> **老师总结**：这是它的一个新思路：我只暴露一些我们自己实现、而且认为是安全的一些功能出来，这样就是让应用程序不至于破坏底层操作系统的运行。

### 10.5 trap 与受限直接运行

**定义**：**trap**（陷阱）。system call 设计的一个基本逻辑就是我们这里设置一些 trap，这个 trap 直接翻译是翻译成陷阱；这个 trap 指令显然就是指我们是通过这个 trap 可以进入到内核态的代码的运行；运行代码运行结束以后，我们再回到我们的用户态代码。这样就可以保证我们只以操作系统自己实现的、能够保证安全的这种代码来运行底层的一些操作。就是你不能自己去实现一些指令去随便操作底层的东西。

**定义**：**受限直接运行**（limited direct execution）。这样的话就形成一种叫做 limited direct execution，就是受限的直接运行。它的核心逻辑就是：我们把一些重要关键或者是有危险性的一些操作，我们把它封装成系统调用，我们的应用程序只能通过这个系统调用的方式去执行对应的这些操作。

**定义**：**trap 表**。我们这个操作系统它有一些 trap 的表，这个 trap 的表就相当于我们如果是执行的某些系统调用，它就会去查这个系统调用对应的这个内核代码的入口地点，这样就是我们执行对应的这个 table 所指定的那个代码的一个入口，这样就可以执行对应的我们底层的一些操作。

我们可以看一下它的过程：我们的这个操作系统它可以执行我们操作的硬件相关的一些代码；我们这个系统的用户程序，它只能通过这种系统调用去执行它底层的一些代码，就是这样的一个逻辑。相当于我们这里操作系统里面维护了一个类似于这种 trap 的一些列表，这样就是我们进行调用的时候，就可以通过做一个 trap 指令，进行一个执行这种底层的一些代码。

**推导**：受限直接运行模式下整个系统的运行过程。

2. 接着我们去给它设置一些栈；
3. 接着我们是执行它的一个退出这个 trap，然后就相当于操作系统代码执行这部分代码就是一个内核代码了；
4. 这样然后我们这个硬件就从它这个内核态重新进入用户态；
5. 用户态的话，我们就执行这个 `main` 函数的代码了，再往那就是这个程序执行的过程；
6. 如果它要接着执行那种内核的代码，那么它就是进行系统调用，然后重新进入这个操作系统来运行的状态；

9. 然后执行完这个底层代码以后，我们再把结果返回给这个用户态的一个程序，这样就可以保证它这个代码执行的安全性；
10. 也就是：执行用户的代码以后，我们把当前的这个状态给保存，进入这个内核态，然后我们就处理这个 trap；
11. 执行完以后，它又把这个内核态转回用户态——我们硬件的话会支持它这个状态的一个转换；
12. 然后接着又返回这个用户态的程序执行；
13. 然后就已经结束，然后把这个内存释放掉，同时把那个 ID 信息给删除。

**结果与点评**：所以这就是它的一个过程。

### 10.7 系统调用的双重收益

所以有了这个用户态与内核态的区分以后，就相当于是我们操作系统它提供（实现）什么基本的操作或者核心的操作，我们所有的用户程序如果要执行跟底层操作相关的一些功能，你就必须要去调用操作系统提供的这种系统调用，这样就可以完成你的一些底层的代码操作。

比如你要去打开一个文件、读一个文件，这个就是我们系统调用来完成的，你的这个用户代码只需要去调用这个接口去完成就行了，你不需要去实现对这个文件底层的一些操作，这底层操作都是操作系统做好了，只需要去调用就行了。

所以我们可以简单地认为：操作系统把系统调用提供（出来），你就可以认为它是提供了一系列的对底层操作的 API，我们的应用程序就可以调用这种底层操作的 API 来完成一些底层的操作，而不用自己去实现。

> **老师总结**：既减少了这种安全风险，也让我们程序员相对来说是不用去关心太底层的代码。

操作系统它提供了一个黑盒子，但是它把这个接口告诉你应该怎么用，这个底层代码它怎么实现、怎么做你不用去关心。最后反正就是你在调用它这个代码的时候，执行过程从用户态就切到内核态，执行这个对应的操作系统的内核的代码，然后执行完结束以后，再把控制权交给你应用程序，然后接着来这个用户代码的执行。所以有了这个模式的话，就给我们的这个程序和操作系统之间形成了一个比较好的安全保障。

刚才讲了怎么样保证控制权的问题，就是我们的控制（权）问题——操作系统一定要对底层有一个非常好的或者非常完善的一个保护机制。那么怎么样来实现呢？就是它把我们的运行分成用户态和内核态：用户态就是执行我们进程自己的代码；如果进程调用了系统调用它就会切到内核态，然后执行我们操作系统自己的一些代码；操作系统代码执行完以后，它又重新返回给应用程序，然后应用程序这里再接着来恢复到用户态去执行。所以这就是它的对使用权的一个控制问题。有了这种机制以后，可以保证我们用户进程比较好地安全运行。

这样就相当于某个进程它运行到 fork 这个点的时候，系统就给它创建了一个这个进程的完全一模一样的复制的一个进程出来，它的代码都完全一样，只不过是你在执行的时候，它一个是执行了 if 的一个分支，一个是执行 if 另外一个分支，所以这就是它们用 fork 以后形成了一个效果。

那 fork 的作用很显然，它就是创建进程、复制一模一样的进程。有时候的话就是我们也希望它两个进程执行的代码不一样，那怎么样来实现这个目的呢？就相当于是你要用另外一个 exec：你把另外一个进程的代码用 exec 的代码来替代，然后这样就可以保证就是你创建了一个进程，它执行的代码是另外一个代码的内容。这是它的一个基本的一些操作。

> **老师强调**：这个 fork 的话大家一定要明白，主要是我们运行了这个 fork 以后，它到底会变成几个进程，这个大家一定要清楚，它肯定是变成了两个进程了，就是两个一模一样的进程。主要（是）我们假定给一个代码，然后里面有 fork，而且 fork 了很多次来问你这个到底创建了几个进程，那你肯定要首先把它这个基本逻辑理清楚：就是一个 fork 它肯定就是一个变两个，那如果它继续 fork 的话，还是每个 fork 都是一个变两个，这样就是会创建出一些新的进程出来。

### 12.4 受限直接运行与操作系统的接口视角

最后我们这个叫做一个 limited direct execution，解决什么问题呢？就解决了我们怎么样来实现它的一个切换过程。实现切换过程我们讲了两个逻辑：

1. 一种是配合，就是合作的；
2. 一种是非合作。

合作的逻辑的话就是我们让每个进程主动放弃，显然你让大家都来配合做这个不太现实；我们更多的是一种非配合，就是让这个有一个机制，就是让它定期地把这个使用权限给交出来，然后这样的话就是让其他进程可以来执行。

在保证这个操作系统的安全方面，我们讲了一个机制就是 system call，就系统调用。这个到底用来做什么？系统调用的作用就是它把那些底层的代码操作系统实现了、直接实现了，同时暴露出一些接口给你，然后你可以去调用它这些底层的接口。那为什么要这样做？刚才已经讲了，就是为了能安全，就是我不能让应用程序直接去控制我的底层的一些操作，包括对硬件的访问、对硬件的控制，你不能让应用程序直接去做，这是保证它的安全。那这样的话就是我们可以通过系统调用的形式去实现或者使用底层的一些功能。

所以操作系统它到底是什么？如果我们从应用程序的角度来讲，它就是系统调用。因为这是（操作系统）向应用程序暴露出来的一些能用的接口。就这些东西就是说，你如果从应用程序的角度来讲，它操作系统到底是什么？你可以认为它就是系统调用、很多系统调用，因为这系统调用它可以提供从文件、从内存到进程相关的各种各样的操作，它的核心功能都是这些系统调用能够提供的。

> **老师总结**：所以我们对应用程序来讲，前面我们讲操作系统是对底层能力的一种抽象，下面是 hardware，上面是应用程序。我们从应用程序的角度来讲，这个操作系统到底是什么呢？它就是一系列的面向应用程序提供的一些 API、就接口，就系统调用。那显然对我们的应用程序来讲，API 其实就是它能看到的操作系统提供的能力。就是说我们硬件的各种资源都被操作系统封装成各种系统调用，然后提供给上层使用。有了这个封装的系统调用，那我们很显然就可以比较好地来使用这个底层的资源，而且也比较安全地使用。这是它的一个基本思想的逻辑。
