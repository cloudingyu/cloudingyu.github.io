## 一、调度的基本问题：机制与策略 [00:02:45–00:08:00]

### 1.1 从进程抽象到调度

上次课讲了**进程**（process）这个概念，它是对程序的一次运行实例的抽象。引入进程的根本原因是要分配计算机系统的资源：我们要去分配内存、分配 CPU，就必须有一个参与分配的实体，这个实体就叫进程。所以进程本质上就是参与 CPU 资源分配的单位，同时也是我们进行调度的单位。

进程表现成一种形态：在操作系统中一个正在运行的程序实体，它对内存中占用的空间——包括代码段、数据段——进行管理，另外还带有一些与调度相关的参数，比如它的优先级之类的信息。

### 1.2 调度要解决的核心问题

今天的内容是**调度**（scheduling）。调度主要讲的是多任务系统里面，系统里同时存在很多个任务（比如 A 任务、B 任务），这两个任务都要使用 CPU 的时候，必须要设计一个规则来决定到底谁先用、谁后用，以及每个人用多久。

> **老师总结**：调度解决的核心问题就是"谁先运行"以及"运行多久"。

### 1.3 底层机制与高层策略

调度包含两个方面：一个是**底层的机制**（mechanism），一个是**高层的策略**（policy）。

底层的机制主要讲我们怎么样把一个进程换到另外一个进程，也就是具体切换时的一些操作。比如现在有两个进程，让 A 先运行、B 后运行，那么必然涉及 A 运行结束以后让给 B 的时候，要把 A 的**上下文**（context）保存起来，把 B 的上下文恢复过去。另外，当有多个任务、它们之间还有优先级的时候，必然涉及**抢占机制**（preemption）：有时候某个进程可以中断当前正在运行的进程，从而把 CPU 的使用权夺取过来，这就是抢占。简单说，凡是涉及进程之间切换的，都属于底层实现机制，包括上下文切换和抢占。

高层的策略讲的是我们在选择多个任务的时候，到底按照什么原则去选。比如我按照一个先来先服务的顺序去选，这是一个策略；我按照优先级高的去选，这也是一个策略。

所以调度既需要有底层的实现，也需要有高层的一些策略。

### 1.4 机制相对固定，策略才是关键

调度的内容相对来说比较容易理解，它主要涉及有多个任务时到底选哪个，以及选好以后怎么样让它不断地切换。

相对来说，底层的机制比较固定一点——反正就是涉及进程之间的切换；高层的策略反而比较关键，它涉及不同的原则：可以先来先服务，也可以优先级高的先服务，还可以按照任务的长短来服务，这是各种各样的策略。

因此调度需要考虑很多因素。为什么选这个策略而不选另外一个策略？这里的因素包括优先级、任务的长短、任务的类型（有些是交互性任务，有些是计算型任务），当然还涉及目前背景的负载情况：如果负载很重，调度策略可能就要换成另外一种。

这里列举了一些典型的因素：任务到达的时间、任务运行的时间长短、任务的优先级等等。

今天的内容主要涉及课本里面第 7 到 10 章的内容。

## 二、调度的理想假设与评价指标 [00:09:47–00:15:03]

### 2.1 四个假设

为了让调度算法的讨论尽量简单，我们先从一个最简单、最理想的场景入手。这里对当前待调度的进程做了一些假设：

1. 每个任务运行的时间都一样；
2. 所有的任务都是同时到达；
3. 所有的任务只做 CPU 计算，也就是不进行 IO 操作；
4. 每个任务的运行时间都是已知的、或者说可预测的——简单说就是它要运行多久，我们可以预测。

这些假设加上以后，问题就变得比较简单了：现在变成了我们有一个队列，队列里面放了很多任务，这些任务的特征完全一样，那么我们现在就要决定到底选哪个任务来进行调度。

### 2.2 周转时间

选择哪个任务来调度，显然要考虑一些不同的优化目标：有可能我们要优化它的完成时间，也有可能我们要优化它的周转时间。

**定义**：**周转时间**（turnaround time）。一个进程的周转时间定义为它完成的时间减去它到达的时间。

$$T_{\text{turnaround}} = T_{\text{完成}} - T_{\text{到达}}$$

简单说就是你这个进程从进入系统到完成的总时间，其中也包括它的等待时间。这个时间本质上包含两部分：第一部分它可能要等一段时间（刚开始进来的时候轮不到它），第二部分它需要去算一段时间；等到它被调度来执行，最后执行完结束。这两部分时间加起来其实就是它的周转时间。

我们优化的第一个目标可能就是周转时间。当然希望系统效率最高，这样每个进程的周转时间都很短，快速进来、快速结束。

### 2.3 公平性与效率的权衡

除了周转时间这个优化目标，还要考虑一个因素叫 **fairness**，就是**公平性**。有多个任务的时候，你必须考虑公平的因素。

这两个因素本质上就是我们经常讲到的两个优化目标：一个是**效率**（efficiency），一个是**公平**（fairness）。很多情况下都要同时去优化这两个目标。我们讲社会运行中进行优化的时候，优化的也是这两个目标——既要提升效率，又要保障公平。

有时候效率高会牺牲一些公平性。比如有很多个等待调度的进程，有的进程运行时间长一点，有的运行时间很短，那到底先运行哪个呢？如果选择"周转时间最短"去优化，那有可能那些长的进程就永远被放在那里，因为长的进程周转时间也长，于是你就优先去选短的任务执行。这样完成的总数量也多、平均周转时间也短，但对那种长的进程显然是不公平的。这就是既考虑周转时间、也要考虑公平性的原因。

## 三、FIFO 与护航效应 [00:15:03–00:22:32]

### 3.1 先进先出（FIFO）

**算法**：**先来先服务**（First In First Out, FIFO；也叫 First Come First Serve）。

它之所以经典，是因为它来源于我们现实生活中的算法——就是排队。它的思路非常简单：谁先来就先调度谁。这样调度策略非常简单，只需要维护一个队列，永远从队列的头部去选进程就可以了。

**例子**：三个等长任务。

**题目**：有三个进程 A、B、C，它们几乎同时到达系统，每个进程运行时间都是 10 秒，采用 FIFO 调度，求各自周转时间与平均周转时间。

**解答**：按先后顺序运行，A 先运行，接着 B，接着 C。总完成时间是 30 秒。

- A：到达时间为 0，结束时间为 10，周转时间 $10 - 0 = 10$；
- B：到达时间为 0，结束时间为 20（先运行 A 再运行 B），周转时间 $20 - 0 = 20$；
- C：到达时间为 0，但要等 A、B 都结束才运行，结束时间为 30，周转时间 $30 - 0 = 30$。

平均周转时间 $= (10 + 20 + 30) / 3 = 20$。

**结果与点评**：在我们假设所有任务都一样长、同时到达的场景下，FIFO 的确是一个不错的算法——它比较简单、听起来也公平（谁先来谁先服务），而且能达到比较好的效率，不需要复杂的调度策略。

> **原文待核实**：老师口述三个进程"各自的周转时间就是 10、20、30"，随后算出的平均值 20 与之一致（[00:18:38–00:18:47]），字幕此处出现数字误识别。

### 3.2 放松"任务等长"假设：护航效应

如果把"所有任务都一样长"这个假设去掉，即有的进程运行时间长、有的进程运行时间短，那么还用 FIFO 就会出现一个比较典型的现象——**护航效应**（convoy effect）。

**定义**：**护航效应**（convoy effect）。某一个长的进程如果先运行，那些短的进程就要等很长时间才能得到调度，感觉就像这个长进程带了一个编队一样，后面跟着不同的进程，运行的总周转时间就比较长。

**例子**：长短任务混合下的 FIFO。

**题目**：三个任务 A、B、C 同时到达，A 最长需要 100 秒，B 和 C 都是 10 秒，采用 FIFO 调度，求各自的周转时间与平均周转时间。

**解答**：

- A：到达时间 0，本身要运行 100 秒，完成时间是 100，周转时间 $100 - 0 = 100$；
- B：到达时间 0，但要等 A 运行结束才运行，等待 100 秒再加上自己运行的 10 秒，周转时间 110；
- C：到达时间 0，要等 A、B 都结束，总时间为 $100 + 10 + 10 = 120$，周转时间 $120 - 0 = 120$。

平均周转时间 $= (100 + 110 + 120) / 3 = 110$。

**结果与点评**：可以看到，如果按照长的进程先调度，会导致一个比较典型的现象——所有进程的周转时间都比较长。这个现象就叫护航效应：所有进程像一个编队一样排在那里轮流运行，结果后面进程的周转时间显著变长。

## 四、最短作业优先与抢占式版本 [00:22:32–00:34:36]

### 4.1 SJF：短作业优先

FIFO 的一个改进版本是 **shortest job first**（SJF，短作业优先）。从字面意思理解就是最短的任务优先：如果存在多个进程，我在调度的时候优先选那个运行时间短的进程。

**例子**：超市结账。

**题目**：超市结账时，有的顾客只买了一瓶矿泉水，有的顾客推了一大车东西，收银台应该先给谁结账？

**解答**：很显然，买矿泉水的先结账。因为买矿泉水的人结账用不了多少时间，对整体来讲大家的等待时间会比较短；如果你让推了一大车购物车的顾客先结账，他前面就要耽误很多时间，结果买水的那个顾客可能就会等得比较不耐烦。

**结果与点评**：这就是一个典型的现象——如果不同的任务有不同的长度，用 FIFO 就有可能得到一个不太优化的结果，这个"不太优化"就体现在平均周转时间会比较长。

一个更好的思路就是尽量让比较短的任务先去调度：短任务调度来以后马上就可以结束，结束以后就马上调度其他进程，这样总的等待时间相对来说就会短很多。所以 SJF 的核心思路就是把短的任务先运行，把长的任务后运行；对于整体来讲，所有进程平均等待的时间最短，或者说总的周转时间最短。

### 4.2 SJF 的局限：放松"同时到达"假设

SJF 显然可以解决刚才讲的短任务长时间等待的问题，但前面还有两个假设：一是所有任务都一样长（这个已经松弛了），二是所有任务都同时到达。

所有任务同时到达意味着它们加入系统的起始时刻是一样的，但实际上所有的任务并不一定同时到达，这也符合实际：计算任务或其他任务可能就是按照一定的先后顺序到达的，也就是说并不是所有进程都在零时刻到达。那么这时候调度算法应该怎么设计呢？

如果还是按照 SJF 来调度，就有可能遇到这种情况：SJF 调度没问题，但当一个长的进程先到、短的进程还没到的时候，你只能先调度长的。运行到一半，后面那个短的进程到了，那这时候要不要把它切换过去呢？这就要看情况：

- 如果你允许切换，那就意味着这个调度算法是一种**抢占式的调度**（preemptive scheduling）；
- 如果你不允许切换，那它就是一种**非抢占式的调度**（non-preemptive scheduling）。

**定义**：**抢占式调度**。一个进程正在运行时，如果来了一个优先级更高的新进程，它可以中断当前进程的运行，从而把自己调度上来运行。从字面意思也可以看出来，就是它去把别人的资源给抢了。

反过来，**非抢占**就是指我们不能允许新来的进程去中断已有进程的执行。FIFO 就是一种非抢占式的算法，SJF 也是一种非抢占式的算法。

> **老师强调**：抢占和非抢占的核心逻辑，就是我们是否要把当前正在运行的一个进程给中断掉。需要中断，就是抢占；不需要中断，就是非抢占。

**例子**：任务不同时到达时的 SJF。

**题目**：三个进程到达时间不一样，A 先到，B 和 C 后到（等 10 分钟才到）。A 的运行时间比较长，采用 SJF 调度，结果会怎样？

**解答**：进行调度的时候，因为 A 最先到，那时候 B、C 还不在，调度时也只能先把 A 调度来运行。但 A 的运行时间比较长，结果后来 B 和 C 到了，我们也还是没办法，只能把它们放到最后去。

**结果与点评**：这也会产生比较长的等待时间。原因很简单：A 那个任务本身运行时间就长。这个例子里算出来的平均周转时间大概是 103.3。可见如果允许不同任务有不同的到达时间，再按最传统的算法去优化，优化的空间就不大了，这时候我们可能要想一些机制——也就是你当前的任务能不能被中断掉。

### 4.3 STCF：抢占式的最短完成时间优先

假定我允许当前任务被中断：即使先把某个进程调度上来了，我也可以把它切出去，接着换一个短任务来运行。于是就有了考虑抢占的"最短任务优先"，这就是 **shortest time-to-completion first**（STCF，最短完成时间优先）。

**算法**：**STCF**。它的核心逻辑是：当前正在运行的进程，如果遇到了一个更短的任务到达，那么更短的任务就可以把当前这个任务中断掉，换自己来运行。简单说就是把最短的这个任务到达以后，如果系统里当前有一个长的任务，就把当前长的任务中断掉，换最新的那个短任务来运行。

如果把这个短作业优先做成抢占式版本，允许新来的进程去中断已有的进程，那么它就是一个抢占式调度。

**例子**：STCF 与 SJF 的差别。

**题目**：A 最长，运行时间是 100 秒；B、C 都一样，都是 10 秒。A 先到，运行 10 秒后 B 和 C 到达。比较抢占式与非抢占式的差别。

**解答**：主要的区别就在 B 和 C 到达的时刻。A 先运行 10 秒，这时候 B、C 来了，抢占式的版本会让 A 把资源放弃掉，换 B、C 来运行；如果是非抢占式，就让 A 接着运行。

**结果与点评**：抢占式版本在这个场景下面可以显著优化周转时间——按短任务优先运行，而且把任务实际的运行时长参数考虑进去了。

## 五、响应时间与时间片轮转 [00:34:36–00:51:17]

### 5.1 新的优化目标：响应时间

前面我们优化的目标是周转时间或完成时间，这对某些任务来讲是合适的，比如某些需要保证可靠性或者保证冗余的场景，它是有用的。但我们再看另外一种场景——比较实时的系统。这意味着我们的调度可能需要考虑一些额外的优化目标，典型的优化目标就是**响应时间**（response time）。

**定义**：**响应时间**（response time）。进程到达系统，到它第一次被调度来运行，这个时间差就是响应时间。

$$T_{\text{response}} = T_{\text{第一次被调度}} - T_{\text{到达}}$$

响应时间对于交互系统来讲非常关键。如果这个系统在排队的时候是没有优先级的，只是按照先来先服务的顺序去服务，那某些需要比较紧急的场景下，其实时的需求也需要考虑进去。

响应时间显然跟任务本身的长度有关，也跟你的调度算法有关。

### 5.2 时间片轮转

为了针对实时性需求、也就是那种对响应时间比较在意的系统，我们可以采取另外一种调度策略，叫做**时间片调度**（time slicing scheduling），也就是**轮转调度**（round robin, RR）。

它的意思是把 CPU 的时间分成一块一块、或者一段一段的，不同的任务就放到对应的这个块里面去。这是一个 round robin 的角度：大家轮流来用。轮流用就意味着某一个进程需要跟后续同样排队的进程共享使用，而不是说一个先运行完、另外一个后运行。

**算法**：**轮转调度**（Round Robin, RR）。核心思想就是大家轮流使用。假定有 A、B、C 三个任务，都是交互性任务、意味着响应要非常快：把 A、B、C 这三个需要调度的进程放到同一个队列里面，调度的策略就是 A、B、C 轮流来使用，比如一秒钟一次然后进行切换——A 运行一秒换成 B，再换成 C，C 运行一秒以后又换回 A。这就是典型的多任务调度器里面的调度思路。

投影上的讲义（录屏画面 [00:40:00]）把这一机制表述为：为了改善响应时间，让就绪进程每隔一个**固定长度的时间片**（time slice）交替运行；一个作业运行一个时间片后就切换到运行队列中的下一个作业，反复如此直到作业全部完成；这个时间片有时也叫**调度量子**（scheduling quantum）；时间片的长度必须是**定时器中断周期**（timer-interrupt period）的整数倍。同一页讲义还用加粗的黄框给出了一句结论：轮转调度是公平的，但在周转时间这类指标上表现很差。

> **原文待核实**：字幕此处出现"ABC 疫苗""BBB 型疫苗"等误识别（[00:39:45–00:39:48]），按上下文应为"A 运行一秒、换 B 运行一秒、换 C 运行一秒、又换回 A"。

**例子**：轮转调度的响应时间。

**题目**：三个进程，每个任务运行 5 秒，如果采用 SJF，它们就是按照任务的长短来进行排序来运行；如果切换的周期比较短、采用轮转调度，结果会怎样？

**解答**：轮转调度的结果就是每个进程运行一个时间片（老师口述为"运行了一分钟"，**原文待核实**，按上下文应为"运行一个时间片"）然后切下一个，一直到运行结束。响应时间按定义就是它进入系统到第一次被调度这个间隔；周转时间按每个进程最后完成的时间减去它进入系统的时间来计算。轮转调度里没有体现优先级，就是大家轮流用。

**结果与点评**：按照轮转调度，通常可以有效地减少响应时间。响应时间是它的优化目标，主要是因为有些实时系统要不断地跟外部进行交互；如果你不把这个调度机制做得合理一点，其他前面的优化做得再好，效果也会很差。

### 5.3 时间片长度是一个权衡

时间片的长度是用来控制什么？可以想象到，轮流用的调度器设计非常简单，但除了轮流用这个宏观的策略以外，其实还包括一些其他的考虑：比如这里提到的 shorter time slice（更短的时间片），还有就是需要去追求更快的响应时间。

追求更快的响应时间意味着，我们希望进程从进入系统到第一次被调度的时间尽量短。要实现这个目标，我们就要考虑时间片的长短：如果每个时间片短一点，那么大家等的时间就短；如果每个时间片长一点，大家等的时间就长。但最后为什么可能还是需要长一点的呢？因为长一点可以尽量让它的周转时间缩短——前面我们讲，如果你要频繁地切换，频繁切换本身是有代价的。

那么一个 round robin 调度器的时间片到底取长还是取短，应该考虑哪些因素？这里还提到一些因素，就包括它的**切换开销**（context switch overhead）：你把一个进程切出去、把另外一个进程切进来，中间肯定会带来开销。

**课堂问答**：

> **老师启发**：大家觉得设计 round robin 调度，这个时间片到底应该考虑哪些因素？哪些场景可以长一点，哪些场景需要短一点？

- 有同学提出：**时间片不能太长**，比如如果设计成一年，那显然不太合适。老师肯定了这个回答：如果你把它设计得足够长，那它就变成了一个先来先服务了——每次把任务调度进来以后，如果时间片足够长，那肯定能让它运行结束，运行结束就没有去切换，相当于对这个任务而言太长肯定不好。
- 又有同学提出：**太短的话调度用的时间就多了**。老师解释：太短就意味着它这个调度的开销会比较大，因为你要不断地切换；而不断切换实际上是会带来开销的，因为你要把上下文保存起来、把上下文恢复回来。理论情况下我们假设没有开销，来回切都没问题；但实际系统它肯定有开销——如果你把时间片设得非常短，那就意味着调度器不断地在切，CPU 就被浪费在做上下文切换这个事上了。所以太短肯定也不行。

**老师进一步说明**：到底应该是多长呢？首先可能要考虑**应用场景**。比如我用我自己的电脑，可能很多进程我都想要它能够同时看起来在运行，那就需要短一点；如果是一大批量已经包装好的任务，那可能就不要有太频繁的切换。如果我们需要考虑有多个任务同时运行、而且每个任务都希望有一个比较快速的响应，那这个时间片可以短一点；但是如果有些任务其实对实时要求没那么高，那其实也不用那么频繁切换，感觉也可以。

**例子**：后台下载任务。

**题目**：某个任务就是去后台下载一些文件，这个任务需要频繁切换吗？

**解答**：这个任务你切来切去好像对它来讲也没多大意义，而且它也不需要实时交付；那这样的话我们其实可以把它这个时间片弄长一点也可以。

**结论**：本质上这个时间片到底多长多短，其实是一个 **trade off**，是一个需要平衡的点。

- 我们通常情况下会设计得比较短，但是它要足够容纳大多数的一个 CPU 周期；
- 如果太长，它就变成了 first in first out，因为你一个时间片周期就足够让这个任务完成了，其实没有切的意义了；
- 如果太短，又变成了所有的开销都花在不断地切换任务上，因为切换带来的开销会占据 CPU 的大部分时间，性能利用率反而会低一点。

投影上的同一组讲义（录屏画面 [00:40:00–00:43:10]，幻灯片标题被画面裁切）把这个问题归纳为：时间片太短会导致过多的上下文切换开销，时间片太长又会退化成先来先服务，所以取值是一个需要在两者之间取得平衡的折中。

**例子**：时间片与 CPU/IO 周期。

**题目**：一般的时间片应该按什么原则设置比较好？

**解答**：一般的计算任务其实都有一个周期性，就是 CPU 计算的周期，还有 IO 的周期——它 CPU 计算一段时间就要进行 IO。我们尽量让时间片的长度能够容纳下这么一个 CPU 周期：正好它把一段计算指令处理完，下个时间要进行 IO 了，那这时候如果一个时间片能够容纳这个，就正好把它切换出去；切换出去以后它就在等 IO，等 IO 的时候其实不影响我们，我们就让那些需要计算的任务再进来。

**结果与点评**：所以尽量让这个时间片长度能够容纳下一些典型的 CPU 周期的长度，这样比较合理一点。当然如果我们对时间要求很高，那当然应该把这个时间片设得短一点。

## 六、引入 IO 以后的任务组合与调度 [00:59:08–01:08:31]

### 6.1 IO 任务带来的新约束

前面讨论的主要是以计算为主的任务。其次，某些进程其实还有一些 IO 的任务。IO 的任务通常来讲是某些进程里面要进行对外部设备操作的一些任务，比如典型的就是某个进程要打开一个文件、读一个文件，这就是一个典型的 IO 任务。

IO 任务会带来一些典型的需要中断的现象：你进行 IO 的时候还把 CPU 给占着，那显然是不合理的。所以我们进行调度的时候，还需要考虑它典型的需要 IO 的特征。比如 CPU 执行一段时间，后面要执行 IO 操作，那么执行 IO 操作的时候，我们就要设置一个调度的策略，把它从正在运行状态切换出去，切换成等待状态，这样才能保证整体 CPU 利用率比较高。所以调度器也必须要考虑 IO 的问题。

### 6.2 有 IO 后的等待条件变多

考虑 IO 以后，我们再来看前面的场景：以前我们只考虑纯计算，纯计算时调度起来比较简单——你把它调度进去它就执行，把它切换出来它就等 CPU。现在有了 IO 以后，它除了要等 CPU 以外，还得等 IO，所以说它等待的约束条件就增加了，调度器考虑的因素就应该更多了。

### 6.3 例子：A 与 B 交替执行

**例子**：IO 任务与纯计算任务的组合调度。

**题目**：假定所有的程序都要执行 IO 操作。A 和 B 都需要 50 毫秒的 CPU 时间。A 运行 10 毫秒以后就要进行一次 IO 操作，IO 操作要执行 10 毫秒；B 则直接是 CPU 执行 50 毫秒，不执行 IO。调度器应该怎样调度？

**解答**：

- 如果仍然只是先运行 A 再运行 B：A 一直在 CPU 上运行，它的执行过程就是"运行 10 毫秒 → 进行 IO 10 毫秒 → 又运行 10 毫秒 → 再用 IO 10 毫秒"这样交替，总的时间加起来大概到 90 毫秒左右。这样这个进程在运行过程中，有些时间片就没有充分利用 CPU——它处理 IO 的时候 CPU 实际上是空下来的。如果要等到 A 运行结束再运行 B，那么这个调度算法就会让 CPU 这种资源在某些时间段被浪费掉。
- 更好的办法是：当 A 要进行 IO 的时候，把 A 切换出去，把另外一个进程 B 切换进来；等 B 运行了 10 毫秒，正好等到 A 的 IO 完成，就把 B 又切换出去，这时又来接着运行 A。这样 A 和 B 的时间片交替执行，最终让 CPU 一直都处于忙的状态，CPU 的资源就充分利用起来了，总的完成时间就可以缩短：以前要等 A 大概 90 毫秒再运行 B，可能要到 140 才全部完成；现在 A 和 B 交替运行，最后到 100 的时候两个任务就都完成了。

**结果与点评**：有了 IO 以后，我们这个调度可以优化的空间更多了，当然调度的难度也更大了。要完全、比较精确地做到这个程度当然不容易，但总体来讲，只要我们允许这些进程在进行调度的时候充分考虑它 IO 和 CPU 的计算需求，我们就可以把这些进程组合起来，得到一个更好的组合调度的收益。

### 6.4 该组合哪些任务

**课堂问答**：

> **老师启发**：如果全都是纯 CPU 的任务，把它们组合在一起，对总的完成时间有收益吗？

**解答**：如果全都是纯计算，你不管是切也好、还是一个运行结束再换另一个也好，最终所有任务完成的总时间应该是一样的。但是如果我们把一部分任务是那种大 IO 的、一部分任务是纯计算的，把它们俩进行组合，那显然肯定会有收益：因为在进行 IO 的那部分时间，反正这个进程都要等，你把这个时间让给另外一个进程来运行，那显然就会让两个进程感觉真的像是在并行执行了。所以通过这种方式可以对 CPU 资源进行最大化利用。

所以进行调度的时候，通常优先要做的是这样的一个组合：**把纯 CPU 计算的任务和 IO/CPU 混合的任务组合到一起调度**，通常会得到一个比较好的效果。

当然全都是 IO 也不行：全都是 IO 就意味着 CPU 本来大部分时间都被空下来了，"要把 CPU 变成忙的"这个目标就达不到了。我们最好的情况其实就是既有纯 CPU 的、也有 IO 与 CPU 各占一部分的，这样组合起来相对来说就可以得到一个比较好的收益。

- 如果是纯 CPU：不管怎么样都得把所有任务完成，只不过是谁先谁后的问题，CPU 的利用率不因切换而改变；
- 如果全部都是纯 IO：IO 的时间占得比较长，CPU 不能被充分利用起来，不管怎么组合 CPU 还是有一部分时间被空出来。

**结论**：进行调度的时候要考虑尽量把 **CPU bound**（CPU 密集型）的任务和 **IO bound**（IO 密集型）的任务进行组合调度，通常可以得到比较好的收益。

### 6.5 IO 完成后的重新排队

把任务组合以后，在调度的时候，如果有一个任务发起了 IO 请求，那么我们就把它调度出去，换另外一个任务来运行；当它的 IO 完成以后产生**中断**（interrupt），这时候操作系统又可以重新把这个任务排到 **ready 队列**（就绪队列）里面，让它重新等待调度。这就是它的核心思想。所以有了 IO 以后，调度看起来变复杂了，但是资源利用率会变得更高。

投影上的讲义（录屏画面 [01:08:00]）按进程三态把这一过程写得更明确：一个作业发起 IO 请求后，这个作业进入**阻塞**（blocked）状态等待 IO 完成，调度器应该在 CPU 上调度另一个作业；当 IO 完成时会产生一个**中断**，操作系统把该进程从阻塞状态移回**就绪**（ready）状态。

## 七、多级反馈队列 MLFQ [01:08:31–02:06:08]

### 7.1 最后一个假设的松弛

前面我们把各种假设都做了松弛：每个任务运行时间一样、所有任务同时到达、所有任务都只执行 CPU 计算，这些假设都去掉了，而且也讨论了各种改进。现在还有一个假设没有松弛掉——**每个任务的运行时间长度是已知的**。

这个条件能不能松弛掉呢？很显然我们必须把它松弛掉，因为每个任务运行多长其实本来就是不可预估的。你可以去预估，但这个预估一定是不准的，因为它要受很多因素影响。也就是说，这个进程到底运行多长能够结束，其实只有等它结束的时候你才真正知道它有多长。

但是如果我们要进行优化，就必须考虑实际的环境，而实际环境就是不可预知的。那这种情况下我们怎么样来做一个合理的调度呢？这就是**多级反馈队列**（Multi-Level Feedback Queue, MLFQ）要解决的问题。

### 7.2 MLFQ 要同时满足的冲突目标

这个通用的调度算法要解决哪些调度难题呢？主要在于：我们必须要让这个调度器既支持那种运行时间长的进程，也要支持那种运行时间短的进程。

- 有些进程是那种**批处理任务**，比如它是纯计算的任务，特点就是用 CPU 为主，但它不强调交互的效率，反正只需要让它运行下去就可以了；
- 另外一种是**交互进程**（interactive process），它强调的是响应时间，类似于我们的桌面系统：最大的特色就是需要比较快速的响应，这样让用户得到比较好的体验。它的一个特点是**short burst**（短脉冲）：计算的那种周期相对来说比较短，一个计算周期只需要处理几条指令、或者很少的指令就结束了。

对于 short burst 这种进程，通常需要一个比较快速的切换调度，这样才能达到较好的效果。而对于批处理进程，我们又希望它能够比较稳定地获得 CPU 的时间长度，得到一个比较长时间的运行，这样尽快把任务完成。

所以这些不同进程的目标是不一样的：有的是追求响应快，有的是追求分配的 CPU 周期长一点、让计算任务快速推进。这些看起来是冲突的目标，我们怎么样把它放到一个调度算法里面呢？为了实现这种冲突的目标，我们就设计一种叫做 multi-level feedback queue 的调度，直接翻译就是**多级反馈队列**。

### 7.3 名字里的三个关键词

多级反馈队列从名字就可以看出来它的核心：

1. **队列**：它一定是有队列的；
2. **多级**：肯定是有多个队列；
3. **反馈**（feedback）：指它在排队的时候肯定可以在不同队列里面来回移动，也就是有这种反馈。

所以大致思路就是我建立多个队列，多个队列的优先级可能不一样，不同的任务可以排到不同优先级的队列里面，并且可以来回移动。

### 7.4 核心机制：根据过去推测未来

设计 MLFQ 的时候，这个调度器很显然不知道每个进程运行的时长，但是它可以根据进程的过去去推测未来：

- 如果这个进程过去表现出来它可能运行的时间也不会太久，那么我们就可以推测它有可能快速结束；
- 如果这个进程在过去运行了好多个时间片也没有运行完，那我们可以推测它可能就是一个比较长的进程。

为了优化调度的目标——第一个目标是优化周转时间（尽量让短任务先运行），第二个目标是优化响应时间（尽量让所有进程都能快速得到一次运行）——我们怎么设计呢？

核心思想是：

1. 我们创建多个队列，每个队列都有一个优先级；
2. 在同一个队列里面采用 **round robin**（轮转）；
3. 不同队列的 round robin 时间片又不一样，这样就达到一个相对比较均衡的效果；
4. 进行调度的时候，优先从优先级高的队列里面去调度；
5. 优先级高的队列里面放的进程，通常它的时间片比较短，就是能快速切换、切换完以后能快速结束；
6. 当它被调度一次以后如果没有运行结束，我们就把它放到下一个队列里面去，这样就可以保证它的优先级降一级，但也可以保证它后续能够得到调度。

> **老师总结**：MLFQ 的核心思想就是设计多个队列，每个队列里面都可以排很多个进程，每个队列的优先级不一样；同一个队列里面的调度算法都是 round robin；调度的时候优先从优先级高的队列里选来运行；在优先级高的队列里排过一次以后就降一级，通过这种方式保证高优先级队列能够快速得到响应，同时低优先级的进程也能得到调度、并且一旦被调度就能得到一个比较长的时间片。

### 7.5 IO 情形下的处理原则

因为调度的时候还要考虑 IO，所以还要补充一条原则：如果某一个进程在执行过程中进行了 IO，怎么处理？

假定某个进程属于最高优先级，它的时间片没有用完，这时候它又进行了 IO，这时候怎么办呢？一般的逻辑就是：**当一个进程处理 IO 的时候，我们仍然让它保留在原来的级别**。所以说如果某一个进程在最高的那个队列里面、时间片正好没有用完的时候进行了 IO 操作，那下次它被切换回来的时候，仍然要在优先级最高的队列里面调度。如果它的时间片用完了，那就把它换到下一个优先级的队列里面排队。

投影上的讲义标题写作"基本规则（续）"（录屏画面 [01:23:00]），把这条原则概括为：**根据作业被观察到的行为来改变它的优先级**——如果一个作业在等待 IO 的过程中反复让出 CPU，就**保持它的优先级高**；如果一个作业长时间高强度地占用 CPU，就**降低它的优先级**。讲义上还给出了一行目标：**用过去的行为来预测未来的行为**（use past behavior as predictor for future behavior）。

### 7.6 例子：优先级与降级

**例子**：八个队列的优先级次序。

**题目**：现在我们有八级队列，从 Q1 到 Q8，Q8 的优先级更高。Q8 里面有两个进程 A、B，Q1 里面有 C、D。调度结果如何？

**解答**：进行调度的时候很显然优先调 A 和 B 来运行，而且 A 和 B 是轮流来运行；C 和 D 肯定是最后运行——如果 C 没有得到调度，那么 D 肯定也得不到调度；只有等到 A 和 B 运行结束以后，C 和 D 才能得到调度，因为它们的优先级不一样，优先级高的先运行、优先级低的后运行。

**结果与点评**：为了能保证优先级低的进程不会被饿死——简单说就是它不会最终变成一个永远得不到机会的进程——我们还需要让所有的进程在调度一次以后都往下降一个级别。这样的话等到足够长的时间，后面进程就有可能得到调度的机会。

**例子**：只有一个任务时的降级过程。

**题目**：如果系统里只有一个任务，它的调度过程是怎样的？

**解答**：刚开始它的优先级是最高的 Q2（原文待核实：此处字幕与前文"八级队列 Q1 到 Q8"不一致，按上下文应是从最高优先级队列开始）；在最高优先级队列里调度一个时间片以后给它降一级，降一级以后在下一级队列里再得到一次调度，调度以后又降到最低，最低以后就接着在最低优先级里面得到调度运行——因为它也没法再降了，就直接来运行了。每个进程进来以后都放到最高优先级，调度一个时间片用了以后把它降一级，然后调度一个时间片又降一级，直到最后最低的一个优先级。

**结果与点评**：这就是只有一个任务时它的一个降级操作过程。

**例子**：最低优先级进程遇到新来的短任务。

**题目**：假定一个任务已经在最低优先级里面运行了一段时间，这时候来了一个短任务，调度结果如何？

**解答**：短任务首先进入最高优先级，很显然是先调度它；调度它以后它没有运行结束，就把它降一级；降一级以后它的优先级还是高于最低优先级，所以第二次还是它运行；正好这个时间片运行结束以后它就运行结束了。那这次我们再恢复到最低优先级的那个进程去运行。

**结果与点评**：所以这个调度算法就是优先运行高优先级的队列，同时运行完一个时间片就得降一级；如果是在同一个优先级里面，大家就轮流用。

### 7.7 公平性问题一：饥饿与 IO 让出

前面讲了一个原则：如果某个进程它的时间片没有用完就要进行 IO，那这时候它还需要维持在原来的优先级队列里面。这样可能会产生一个现象：如果某个进程它的时间片是 10 秒，它每次用 9 秒就进行一次 IO 操作，那这样它就永远待在那个高优先级队列里面了。

这种情况客观上可能会存在，但它显然不太公平——因为假定我们知道这个调度策略以后，某个进程就可以去优化它"作弊"的策略了：我反正不管怎么样，运行 9 秒我就执行一个 IO 操作，这样我永远得到一个高优先级，从而让其他进程可能永远得不到调度机会。

**例子**：IO 密集任务与 CPU 任务混合。

**题目**：有两个任务：job A 是一个 CPU 任务，已经运行了很久，已经降到最低级了；job B 是一个交互性任务，隔一段时间要进行一个 IO 操作，可能中间会中断。按原来的规则运行会是什么结果？

**解答**：把需要 IO 的进程放到最高优先级是合理的，因为需要进行长时间 CPU 计算的任务其实没有那么高的优先级需求；而且每次这个 IO 任务执行的 CPU 周期都很短，这样就会让另外一个 CPU 计算的任务得到一个比较长的时间片。

**结果与点评**：从这个角度来讲，这两种组合其实比较合理，不存在"它作弊了、然后它能得到更好的好处"的问题。这个例子里两种任务合在一起能达到一个比较好的效果，是因为高优先级的任务要进行 IO，它把 CPU 让出来以后让低优先级的 CPU 任务运行；等它的 IO 执行结束以后，马上又恢复它的 CPU 操作。这样就可以保证进行 IO 的进程得到一个很高的响应速度，同时执行 CPU 的进程也能得到一个比较大的 CPU 占比。所以这两种组合的进程合在一起其实对大家都有好处。

### 7.8 公平性问题二：饥饿现象与欺骗调度器

当然会有一些情况不是理想状态。如果我们系统里面有太多那种交互任务、也就是频繁进行 IO 的任务，因为它们一直要待在最高优先级：如果只有一个，那简单，它还是有机会把 CPU 让给那个 CPU 进程；但如果是很多个 IO 进程都在运行，那就意味着第一个 IO 完成以后切下一个、下一个 IO 完成以后它的 IO 好了又恢复过来，这样那个纯 CPU 的低优先级任务就永远得不到运行。这就会造成一个很危险的现象——**饥饿现象**（starvation）。

第二个问题就是**欺骗调度器**。假定某一个 IO 的任务正好把它的时间片用到 99% 的时候才发起一个 IO 操作，那相当于它用了一个满满的周期，接着发起 IO；IO 操作以后我们下次回来的时候，它还是位于最高的优先级。那这样的话，我们这个调度器永远都是把这个优先级安排给这个执行 IO 操作的进程，显然就不太合理了。

### 7.9 公平性问题三：进程性质会变化，必须能升优先级

还需要考虑的一点是：有些进程前期 CPU 多、后期变成 IO 多，这完全有可能，因为程序的代码可能前一部分是纯计算的、后面部分是 IO 的，或者反过来都有可能。所以某一个进程运行到不同阶段，它的 CPU 和 IO 的特征也会发生变化。

如果一个进程被放到一个固定位置以后就不再变化，有时候会产生一个比较致命的效果：如果它刚开始是 CPU bound 这种进程，你把它放到最低优先级以后，如果没有一个机制让它的优先级变高，那到了后期即使它变成了 IO bound 的进程，它也得不到一个调度的机会，也就是它的交互性也得不到保障。

所以这个情况下我们就需要考虑另外一个机制：我们有降优先级的情况，还得考虑升优先级的情况——升和降都得有才行。有些进程在调度的时候要不断降优先级，但是有的进程运行一段时间以后，你还得给它升优先级。

### 7.10 规则 5：周期性升优先级

升优先级的逻辑就是：当经过一个时间周期 $S$ 以后，我们把所有的任务重新搬到最高优先级。

**算法**：**规则 5（优先级提升）**。经过时间周期 $S$ 以后，把所有的任务重新放到最高的优先级。

这相当于运行一段时间以后，所有进程可能已经按照前面的调度策略降到最低级了，而我们考虑的是某些进程的性质可能会变：原来它本来是 CPU bound 的进程，降到最低级没问题；但是过了一段时间它又变成了一个 IO bound 的进程、要频繁进行 IO 操作，这时候你还把它放到最低级，那显然不合理，因为它需要得到一个高的响应速度。这时候我们就必须把这些进程重新移到最高的优先级，让它们重新从最高优先级又来跑一遍，这样就可以潜在地让一些进程得到一个更好的调度机会。规则 5 的核心思想就是让大家都有机会重新开始。

### 7.11 MLFQ 全景总结

总结起来，MLFQ 其实讲了一个故事：我有多个队列，我们怎么样让进程在多个队列里面来回移动、并且得到一个调度。这样我们既要满足交互的效果，又要满足完成时间的效果，还要考虑公平性。所以 MLFQ 本质上就是一个综合了多个目标以后的调度算法——它既要考虑优先级，也要考虑公平性。

最后我们就设计了一个多级队列，你的进程就在队列里面来回移动：刚开始是最高优先级，让你调度一次；如果你还做不完，你就降一个优先级；还做不完又降一个优先级，降到最后；过一段时间又把你重新放到最高优先级去。

> **老师比喻**：相当于你以前是在最高的一个优先级，逐渐降、降到最底下的时候，你也许感觉这个都没希望被调度了，那突然它又让你到最高优先级去，那又有机会得到调度。

> **老师总结**：这是一个比较有意思的设计，既有下降也有上升，既考虑优先级也考虑公平，是一个设计得比较精巧的调度算法。

### 7.12 对欺骗问题的改进

针对"利用 IO 漏洞保持高优先级"这个问题，怎么来解决呢？

有一个办法是：既然我们在每个优先级里面待的应该是一个完整时间片、待满就该让出来，那我们还可以采取一个策略——统计它在队列里面待的时间长度。如果它在这个队列里实际被调度的次数、或者总的时间已经超过了分配给它的额度，那你不管怎么样、IO 不 IO，都得降一级。

这是对"欺骗调度器"的一个小小的改进。改进实现起来也不麻烦，但是稍微增加了很多状态信息：你要统计每个进程在队列里面运行了多长时间，相当于要做一些额外的统计信息。

**例子**：改进前后的对比。

**题目**：某个进程经常进行 IO，按原来的逻辑和改进后的逻辑分别会怎样？

**解答**：按原来的逻辑，它时间片没用完就进行 IO，那接着它留在这个高优先级，结果就导致这个进程永远占了一个比较多的 CPU 时间。改进以后变成了：它的时间片用完以后你必须得降级——虽然它一个 IO 周期这个时间片没有用完，但最多再用一部分时间，用完以后你就必须得降了。

**结果与点评**：这个逻辑相对来说对其他进程略微公平一点，但带来的代价就是你要统计它在里面的时间长度，相当于加一个额外的状态变量，增加了不少统计的开销。

> **老师强调**：为了变得公平，就要加一些额外的开销。

投影上的讲义（录屏画面 [01:34:00]）把这一组问题归纳为"基本 MLFQ 的问题"，分三类：

1. **饥饿**（starvation）：系统里存在"太多"交互型作业时，那些长时间运行的作业永远得不到任何 CPU 时间；
2. **欺骗调度器**（gaming the scheduler）：作业在时间片运行到 99% 的时候发起一个 IO 操作，就可以一直获得更高比例的 CPU 时间；
3. **程序的行为会随时间改变**：一个原本是 CPU bound 的进程可能变成 IO bound 的进程（讲义上写作"…bound process → I/O bound process"）。

这三类问题与老师课上口述的三种现象一一对应。

### 7.13 各队列时间片的设计

MLFQ 有多个队列，优先级高的队列得到调度的机会越大，优先级低的队列得到调度的机会就越少。那么各个队列里面的时间片应该设计成什么样比较合理呢？

这里给了一个简单逻辑：**尽量让高优先级的队列时间片短一点，然后低优先级的队列时间片偏长一点。**

这样一是可以保证响应速度——高优先级队列里面如果你设了一个很长的时间片，它的响应速度就没那么快了，你就必须设一个很短的时间片，这样轮流切换马上就能得到一个响应；二是低优先级队列好不容易得到一次调度机会，我尽量让你多运行一会儿。

**例子**：高、低优先级队列时间片的量级差别。

**题目**：高优先级队列和低优先级队列的时间片长度大概应该是什么量级？

**解答**：老师给的例子中，高优先级队列里的时间片长度比较短，大概是 10 毫秒；低优先级队列里的时间片大概是一百多毫秒（字幕作"一百多秒"，**原文待核实**，按上下文应为与 10 毫秒同一量级的更长值）。

**结果与点评**：这样可以比较好地达到平衡——尽量让短任务在高优先级里面快速地执行、得到一个比较高的响应速度；长的任务尽量在低优先级的队列里面得到一个比较长的时间片，减少切换。

同一页讲义还给出一条更一般的取值原则（录屏画面 [01:59:00]，可见文字为"…increase the length of the time slice"）：**让各个队列的时间片长度逐级递增**——优先级越低的队列，时间片越长。

### 7.14 与 FIFO、SJF 的关系

前面讲了几个调度算法，MLFQ 跟它们是什么关系呢？

- **FIFO** 是一个非常简单的调度算法，就是先来先服务、先来先调度，相对来说非常简单，它没有其他额外的优化；
- **SJF** 是短任务优先，核心逻辑是我能预期你这个任务的执行时间长度，我选那个执行时间最短的任务先运行，这样保证后面另外一个进程等的时间要短一点，总的周转时间会短一点；
- **MLFQ** 其实就是对 SJF 的一个**近似**。为什么说是近似呢？因为 MLFQ 其实是不能预测未来的长度的，它通过不同队列里面时间片不一样来进行区分：如果你在短时间片的队列里面可以快速地得到调度，而且得到调度以后你下次仍然待在这个队列，那说明你就是一个比较短的任务——因为它考虑了我们有 IO 的情况，你通过 IO 的中断又能继续待在那个队列里面，那这说明就是一个非常短的任务。对于短的任务，当然尽量让你得到一个快速响应。

### 7.15 实际系统中的应用与历史

MLFQ 本身就提供了一个比较综合的、面向通用场景的调度算法，所以后来被用到很多典型的系统，或者说改进后被用到很多典型的系统。

**例子**：Solaris 的调度器。

**题目**：Solaris 的调度器是怎样采用类似思路的？

**解答**：Solaris 采取类似的思路，它的调度类别大概有 60 个队列，可以看出来队列还是比较多的。每个队列都会逐渐增加它的时间片的长度。最后当我们降到最低级的时候，每隔一定的固定周期它又会把所有的进程放到最高优先级——这里列了一个时间的数据，大概是 1 秒钟，也就是每隔一秒钟就会把所有的进程移到最高优先级。

MLFQ 的主要提出者是 **Fernando Corbató**（费尔南多·科尔巴托）这位教授（字幕作"费兰多柯尔巴托"），他应该是 1990 年的**图灵奖**（Turing Award）获得者，主要贡献就是他在**分时系统**（time-sharing system）以及里面的贡献，其中 MLFQ 就是其中的一个贡献之一。分时系统主要讲的就是做任务的时候怎么样来设计不同任务之间的调度。

所以我们可以看出来，多级反馈队列其实比较实际地解决了多任务系统的一个调度问题，而且比较平衡地去优化了各种目标，这就是为什么要讲 MLFQ 的原因——它就是一个比较综合地解决了比较通用的调度问题、并且能达到比较好性能平衡的算法。

### 7.16 五条规则

MLFQ 的核心其实就是几个规则，大致有五个：

1. **规则 1**：调度的时候永远先调度高优先级的队列；
2. **规则 2**：同一个优先级里面就是轮流（round robin）；
3. **规则 3**：新来的进程放到最高优先级；
4. **规则 4**：当它的时间片用完就降级；
5. **规则 5**：当我们过了固定的时间间隔，就会把所有进程重新放到最高优先级。

> **老师总结**：MLFQ 就是把整个多级队列的体系通过这五个规则给定义了——这些规则定义了我们怎么样让进程在不同的队列里面移动，以及在调度的时候选择哪个队列来进行调度。

### 7.17 后续系统的改进

后来 Linux 一般用的调度器是 **CFS**（Completely Fair Scheduler，完全公平调度器）（字幕作"CSS"），CFS 是在 MLFQ 的基础上改进了一些东西，大家有兴趣也可以去看一下 CFS 的调度算法。

## 八、按比例公平：彩票调度与步长调度 [02:06:52–02:37:27]

### 8.1 为什么还需要按比例公平

接下来看调度里面关于公平的一部分，这里提到一个按比例公平的问题。

前面讲的 MLFQ 其实也考虑了等待时间，相对来说比较公平，但是还要考虑一个问题：MLFQ 并不能保证每一个进程在里面的一个公平的比例到底是多少。我们今天这个讨论内容，其实就是要考虑我们怎么样实现一个调度器，让调度器尽量在不同类别里面尽量公平，这就是这个调度器的实现要点。

核心逻辑就是：假定我们有些场景它有不同的任务，不同任务有不同的优先级，我们尽量让 CPU 的时间在不同的优先级里面分配的时间片比例有所区分。

为了达到这个目的，这里提到两种调度算法：一个是**彩票调度**（lottery scheduling），一个是**步长调度**（stride scheduling）（字幕作"不长调度"）。我们先看比较简单的彩票调度。

### 8.2 需求：按比例分配 CPU 时间

彩票调度的逻辑其实就是根据概率的因素来进行确定的一个调度算法。

假定我们有一些需求：现在有不同的进程，不同的进程在竞争 CPU 的时候，我们希望它们得到的这个时间片的比例呈现一定的相关关系、或者跟它的优先级正相关。比如有 A 进程我们希望他占 30% 的 CPU 时间，B 进程我们希望他占 70% 的时间，那怎么样在调度的过程中能保证 A 大致占 30%、B 大致占 70% 呢？

这里提到的思路就是：我们类似于用一个彩票抽奖的方式来确定它的比例。

### 8.3 彩票与票数

为了达到刚才说的这个目标——比方说我要给 A 进程分 30% 的时间、给 B 进程分 70% 的时间，也就是 CPU 使用的比例——我们就类似于这种彩票的概念。

**定义**：**彩票（ticket）**。每个进程拥有一定数量的彩票（ticket），就类似买彩票时你拥有的号码；你拥有了一个号码，你就拥有了一个抽奖权。

如果彩票的数量越多，那很显然你在这个抽奖中能抽中的概率一般来讲就会比较大一点。如果我们把彩票的数量跟它最终使用的资源的份额进行挂钩，那我们就可以根据它的数量来进行各自份额的分配。

### 8.4 彩票调度的算法

**算法**：**彩票调度**（lottery scheduling）。它的核心思想是：

1. 给对应的任务、对应的进程一定数量的彩票；
2. 在调度的时候，随机生成一个中奖号码；
3. 如果对应的这个进程正好拥有了这个中奖号码，那就调度它；
4. 它用一个时间片周期，用完以后下次再继续抽。

这个调度算法听起来逻辑比较简单：相当于给各个进程分配若干个抽奖的号码，我在进行调度的时候每次调度就抽一次奖，如果是抽中你，那么你就得到 CPU 来调度。

**例子**：75 张与 25 张彩票。

**题目**：两个进程 A 和 B，进程 A 有 75 张彩票，进程 B 有 25 张彩票。它们各自大约能得到多少 CPU 时间？

**解答**：如果我们有 100 张中奖的号码，其中一个人拿了 75 张、另外一个拿了 25 张，那么每次抽奖的时候，那个拿 75 张的人中奖概率肯定会大一点。我们假定抽奖时是随机抽的、没有任何确定因素，那很显然我们随机抽一个号码，被抽中的这个进程就来参与 CPU 的调度。

**结果与点评**：所以最终 CPU 的时间就大致跟它拥有的彩票数量成正比了：75 张彩票的这个进程，我们希望它大约收到 75% 的 CPU 时间；25 张彩票的这个进程，大致是希望它收到 25% 的 CPU 时间。这就是彩票调度的核心思想。

**例子**：编号区间的具体实现。

**题目**：100 张彩票，A 分配 75 张、编号 0 到 74，B 分配 25 张、编号 75 到 99。调度时具体怎么做？

**解答**：进行调度的时候就生成一个 0 到 99 之间的随机数，每次调度的时候就生成 0 到 99 之间的随机数；生成的这个数被谁拿着了，我们就让谁来调度运行。

**结果与点评**：最终就可以保证对应的这个进程获得跟它彩票数量相对应的比例的调度机会。实现上非常简单：如果是小于 74 那就是 A，大于 74 那就是 B，就是一个生成随机数再用一个大小比较，就能进行一个调度了。

**例子**：讲义上给出的一次具体抽奖序列。

**题目**：100 张彩票，进程 A 持有 0～74，进程 B 持有 75～99，调度器每次随机抽取一个中奖号，得到的调度序列是什么？

**解答**：投影上的讲义（录屏画面 [02:16:00]）列出了一组中奖号码：`63 85 70 39 76 17 29 41 36 39 10 9 68 83 63`，对应的调度序列是

```
A B A A A B A A A A A A A B A
```

**结果与点评**：这组序列里 A 出现了 11 次、B 出现了 4 次，大致接近 75% 与 25% 的比例，但并不是严格的 3:1。讲义同时给出了一句加粗的结论：**这两个作业竞争的时间越长，它们就越可能达到期望的百分比**（The longer these two jobs compete, the more likely they are to achieve the desired percentages），这与老师强调的"要有足够多的调度轮次才收敛"一致。

**例子**：讲义上关于份额的比例说明。

**题目**：投影上为什么写的是 30% 与 70%？

**解答**：老师在黑板上写的是"A：30%、B：70%"（录屏画面 [02:11:00]），这是抽奖比例的一般性示意，用来对应讲义上"**一个进程应该获得的资源份额**用它所持有的彩票百分比来表示"这一说明；随后讲义和老师给出的具体算例都是 A 持 75 张得 75% 的 CPU、B 持 25 张得 25% 的 CPU。

**结果与点评**：两者只是同一机制的示意值与算例值，不构成冲突。

### 8.5 概率保证，而不是确定保证

大家可以想一下，这个彩票调度有没有那种保证——就是说我一定要 75%、一定要 25%？那其实是没法保证的，但是它的概率是差不多的。

所以这是一个我们说的、**概率保证**的一种按比例公平分配：我要把 CPU 时间按照某种比例分配给不同的进程，如果按照彩票这种调度去分，很显然可以比较好地达到一个近似的效果。

在平均性能上来讲，CPU 时间的分配就跟我们每个进程拥有的彩票数量正相关。这个典型的算法实现起来比较简单，就是根据彩票数量来分。

彩票调度很显然是一个概率性的算法。如果我们分配的彩票数量足够多，那么最终它的这个概率分布就会越来越接近我们想要的那个比例。

### 8.6 彩票调度的优点

这个算法里面很显然用了一个因素就是**随机数**：你在调度的时候随机生成一个彩票号码。随机数的好处是什么呢？

1. 它可以避免很多 **corner case behavior**（异常的边界行为）——就是那种异常的边界、或者不经常遇到的这种情况，用随机的方式来解决这个问题；
2. 它的开销也比较小：我就是随机地去生成一个数，每个进程只需要保留它的一个彩票号码就行了；
3. 调度也非常快：就是生成一个随机数，然后确认一下这个随机数在哪里就行了，相对来说也比较简单。

这是一个非常容易实现的调度算法。

### 8.7 概率分布的讨论

**例子**：彩票数量与中奖概率。

**题目**：一个线程或者一个进程拥有 7 张彩票，它中奖的概率是什么？如果在 $N$ 次调度中讨论被抽中的次数，会服从什么分布？

**解答**：它的一个中奖的概率就是总的数量跟它拥有的数量的一个比值，这个逻辑很简单。如果是希望在 $N$ 次调度的时候讨论被调度抽中的概率，那我们其实就可以用一些概率的公式把它描述出来：它服从一个分布，可以通过它的方差把它的期望也可以算出来。

**结果与点评**：这里提出中彩票的次数是服从**二项分布**的（字幕作"警察分布"），这其实就是一个数学概率的问题。

### 8.8 彩票怎么分配

在这个算法里面，我们是需要考虑每个进程分多少张彩票的：对应的就是你分得多，那你中的概率就越大。那么彩票怎么分法呢？

一般来讲可以采取一些优先级的算法。比如我们如果想要让那种短任务优先，那么你就把这个彩票分多一点给这个短任务，那么它调度的时候很显然被选中的概率越大，那这样我们就可以近似于类似于 SJF 这个算法。当然为了避免饥饿，至少每个任务要有一张票，这个是肯定的。

最后我们还需要考虑任务本身的变化：有些任务前期可能比较重要，后期可能会变得优先级没那么高，那怎么样来解决这个问题呢？这里提到一个**降级**的概念。降级的逻辑其实就是我可以把每个进程的彩票数量进行变化：要么就是增加、要么就是减少，这样就可以改变它被抽中的概率。

### 8.9 二级分配：全局票与用户内部票

**例子**：进程内部再分配彩票。

**题目**：假定某个进程里面又分了多个线程，为了保证它在调度的时候概率比较大，我们应该考虑什么？

**解答**：我们需要把线程的因素也考虑进来。另外，某一个用户也可以在他的多个任务之间分配这里的彩票，这样就可以实现"系统级的额度分配"跟"用户级的额度分配"之间的转换。

**例子**：200 张全局票的二次分配。

**题目**：假定现在有 200 张票，这个票这里叫做 **global currency**（全局货币）（字幕作"全局的现金"）。进程 A 有 100 张，进程 B 也有 100 张。进程 A 把它这 100 张的份额分成了 1000 份，500 份给 A1、500 份给 A2，也就是进程 A 里面有两个线程；进程 B 里面只有一个线程 B1，它把所有的份额都分给了 B1。最终三个线程 A1、A2、B1 各占多少？

**解答**：A 和 B 看起来各自最终占的比重应该是近似的：进程 A 100 张、进程 B 100 张，那么最终 A 和 B 分配的时间应该是近似的。不同的地方在于进程 A 把他的这个份额切成了 1000 份分给 A1 和 A2，那意味着实际上 A1 和 A2 拥有的这种全局的票其实只有 50 张；而进程 B 只有一个线程，这个线程用满了全部 100 张，所以说它占用全局的票就是 100 张。

**结果与点评**：所以最后进行调度的时候，我们最终的份额分配就是按照 A1 大概 50、A2 大概 50、B1 是 100 这个比例去分配。这就是彩票调度可以进一步进行二次分配的逻辑。

> **老师总结**：这个算法听起来还是比较简单的，就是一个按比例的分配——谁用的份额多，谁的调度概率就大；反正我用一个随机数生成器，随机数落在哪里就给谁。

### 8.10 彩票机制的灵活性

彩票机制很显然就是每个进程都分了一定的份额，那有没有可能就是某个进程可以把他的份额交给其他进程呢？是允许的，就是比方说有些进程可以把自己的份额交给其他进程。

还有一些机制，这里提到一个叫 **ticket inflation**（彩票膨胀）。彩票膨胀的意思是：我们某个进程可以临时性地增加或者减少它的彩票数量，这样就可以动态地调整优先级。比如如果某一个进程它突然优先级变高了，我们就可以临时给它多分配一些，这样它被抽中的概率就更大一些。

### 8.11 彩票调度的公平性与实验

这个彩票调度，相对来说它的公平性这里利用了一个叫做 **unfairness metric**（不公平性指标）来衡量。它其实是根据概率进行的一个公平分配，相对来说是不存在太大的不公平问题；而且它的分配比例一般来讲会比较稳定。

这里也做了一些实验比较：当任务长度不是很长的时候，它的不公平性可能会比较显著。这很好理解，因为你是彩票调度，只有调度次数足够多的时候，它最终的这个概率才会比较收敛到某一个值；如果你只是偶然地扔几次硬币，那这个谁多谁少其实都是不稳定的，最终要到一定的次数以后它才会比较稳定。

**例子**：抛硬币的类比。

**题目**：为什么任务不长的时候彩票调度的比例不稳定？

**解答**：这个就相当于跟扔硬币正面反面一样：你只要扔的次数足够多，它的正面跟反面的比例肯定是接近的；但是如果你扔的次数没那么多，那么正面反面的比例也许并不是我们期望的各占一半，那有可能是某个多点、某个少点。

**结果与点评**：同样，彩票调度也是同样的逻辑：如果你调度的次数没那么多、也就是它的任务没那么长，那么它按比例分配近似的这个值可能就不一定跟我们期望的那个值一致；如果任务足够长，可以看到它是越接近我们期望的那个值。

### 8.12 彩票调度的缺点与步长调度的动机

这种随机性的调度其实给了我们一个机会：我们其实是可以用一个非常简单的调度算法来实现相对比较公平的分配。

接下来看这个随机调度，它有它的优点——非常显然就是简单；但是它有一个缺点：它的这个比例必须要通过长时间、或者足够轮次的调度，你才能达到我们期望的那个值。如果本身某个进程就很短，结果你去用这个 random，也许就存在比较大的一个误差了。

这就是后面的**步长调度**（stride scheduling）要解决的问题。步长调度希望达到的目标就是一个**确定性的分配**。

### 8.13 步长调度的算法

**算法**：**步长调度**（stride scheduling）。它首先给每个任务分配一个叫做**步长**（stride）的量，这个步长跟前面我们讲的它的彩票数量成一个**反比例**关系。

**例子**：步长的计算与 pass 值的更新。

**题目**：假定有一个比较大的数是一万。进程 A 拥有 100 张票，进程 B 有 50 张票，它们各自的步长是多少？调度时怎么选？

**解答**：进程 A 拥有 100 张票，那么它的 stride 就是 $10000 / 100 = 100$；进程 B 有 50 张票，那么它的 stride 就是 $10000 / 50 = 200$。也就是刚才我们讲的、用一个数除以它的彩票数量。

每个进程在运行的时候，它会增加一个计数器，然后每次增加的就是它的 stride 值（这个计数器就是 **pass value**）。我们选择这个进程来运行的时候，就选择拥有最小的 pass value 的这么一个进程来调度。

**结果与点评**：各自维护一个计数器，每次都会增加它对应的数值，每次我们选择小的那个来进行调度。因为他们俩增加的步长是不一样的，那就是有的增加得快、有的增加得慢：增加得快的那个有可能得不到调度，而增加得慢的那个反而是有机会得到调度。

投影上的讲义（录屏画面 [02:33:00]）把步长的定义补全为

$$\text{stride} = \frac{\text{一个大数(large number)}}{\text{该进程持有的彩票数量}}$$

并给出了它的伪代码实现：

```
current = remove_min(queue);      // 选 pass 值最小的进程
schedule(current);                 // 让它运行一个时间片
current->pass += current->stride;  // 按它的步长递推 pass 值
insert(queue, current);            // 放回队列
```

> **原文待核实**：投影上这一页标题与第一行文字被画面裁切，公式左边的符号与标题首字无法辨认（[02:33:00]），上式为按可见文字与老师口述补全的结果。

**例子**：三个进程的步长调度过程。

**题目**：进程 A 每次增加 100，B 每次增加 200，C 每次增加 40，到底谁得到调度？

**解答**：我们每次选择最小的那个。第一次可能是 A 得到调度，A 加 100；接着让 B 来运行，B 一次运行加 200；然后 C 来运行，每次它只加 40；加 40 的话下次还是 C，因为它加得比较少。每一次我们就是选择那个数字比较小的来运行。

**结果与点评**：所以 stride 比较小的进程，它的优先级就会高一点。在加的过程中，每次被调度了就加一个值、被调度了就加一个值；在调度的时候选择最小的那个来调度。可以想象得到，最终因为这个步长是固定的，所以调度的结果就会得到一个比较确定性的比例分配。虽然步长小的进程优先级高一些，但是其他的进程也不会被饿死，因为它也会同步增长，总归增长到一定程度它就会赶上、从而得到调度。

### 8.14 步长调度与公平排队、CFS

步长调度的提出也是在 1995 年，跟彩票调度是近似的，它其实就是对彩票调度的一个改进，也是 MIT 提出的一个技术报告。

这个调度算法其实就类似于一个叫做 **fair queueing**（公平排队）的算法，也就是一个**加权的公平排队**（weighted fair queueing）。

后来的 Linux 的 CFS 跟这个步长调度其实是有点类似的。本质上我们考虑的就是每个进程它的份额问题。
