## 一、三大模块回顾与并发问题的引入 [00:03:09–00:10:56]

### 1.1 这门课的三大模块

老师先把整门课的结构重新摆了一遍。操作系统这门课一共三大模块：第一个模块是**虚拟化**（virtualization），第二个模块是**并发**（concurrency），第三个模块是**持久性**（persistence）。今天是第二部分的第一讲。

这三个模块之间的关系，老师是这样讲的：第一个模块讲虚拟化，主要解决的是 CPU 和内存这两大资源的共享问题。虚拟化带来的好处是资源利用率更高了——一个 CPU 可以支持多个进程，内存也可以支持多个进程来共享。但资源利用率提高是有代价的：既然有了多个进程、多个线程，就必然会涉及多个进程、多个线程在竞争资源时的访问顺序问题，也就是谁先访问、谁后访问。怎么解决这个访问顺序问题，就是并发这一部分的重点。

### 1.2 虚拟化部分的回顾

老师用几分钟把虚拟化的内容快速过了一遍，作为进入并发的前提。

CPU 部分，虚拟化的基本途径就是**分时复用**：把 CPU 划分成很多个很小的时间段，每个时间片（time slot）都可以分配给不同的进程，大家轮流使用，就造成了一个假象——所有进程都感觉自己同时在使用 CPU，而实际上是轮流交替在使用。

既然要轮流交替使用，就必然涉及三件事：第一，什么时候把当前的进程换出去；第二，什么时候把待调度的进程换进来；第三，换哪个进程进来。这就涉及**上下文切换**（context switch）——两个进程交替的时候，要把各自对应的上下文交换过来；以及在选择下一个进程时需要合理的算法，比如先进先出（first in first out）或者最短作业优先（shortest job first）之类的各种调度算法。

内存部分，老师讲了很多机制，包括分配、分段、分页。其中分页是重点，因为它是主流的机制。分页里面讲了典型设计的开销，比如页表开销，以及怎么降低页表开销：**快表**（translation lookaside buffer, TLB），也就是通过缓存的方式；还有**多级页表**；还有**反置页表**等各种方式。另外也讲了**交换**（swapping）机制——需要把内存和外存统一来考虑，有时候某些页面在内存、某些页面在外存，需要合理的机制让缺页率降到最低，这里也讲了各种各样的替换算法（上一节课的那个小测验其实也是在讲替换算法）。

这一段回顾的落点是：虚拟化解决的是资源更高效利用的问题，也就是让更多的进程来共享计算机系统的 CPU 和内存这两大资源。

### 1.3 并发带来的新问题

在第一步的基础上，第二部分要考虑的问题是：有多个任务、多个进程同时在运行的时候，就会涉及多个任务、多个进程之间运行的时序问题。

老师举了一个最小的场景：有一个变量，A 进程和 B 进程都会访问它。既然都要访问，就必然带来谁先访问、谁后访问的问题，而访问顺序不同，结果可能就不一样。因此就可能出现「因为访问顺序不一致，导致结果也不一致」的现象，这就是程序运行的不确定性。

> **老师强调**：不确定性就是我们这种多任务系统或者并发系统带来的一个典型问题。因为我们希望我们的程序是确定性的运行，所以需要有些机制来保证：即使它在并发地运行，也要能够得出一个确定的结果。

### 1.4 并发部分的技术地图

老师把这一章要讲的东西先列了一张清单：

1. 对锁的抽象。既然要共享访问一个资源，最简单的办法就是大家不要同时访问，而最简单的办法就是锁——锁是一种抽象。
2. 实现锁的机制。锁怎么实现有各种各样的手段，可以软件实现，也可以硬件实现。软件实现是用一些合适的算法来实现这把锁；硬件实现是在底层用硬件的方式让它实现，典型的机制就是中断。
3. 忙等（busy waiting）。这是一种纯靠算法流程的控制来实现的锁，它最大的特点是会降低 CPU 的利用率——虽然在这里等，但仍然要消耗 CPU 周期。
4. 条件变量（condition variable）和信号量（semaphore）。条件变量可以实现更高效的一种等待，信号量同样也是实现更高效的等待。这两个是当时实现时序控制的主要机制。

后面会用例子讲清楚：为什么用信号量、条件变量能够实现时序控制。

关于「禁止中断」这一条，老师讲得比较细，因为它是后面理解锁的基础。之所以会出现进程切换，一般来讲都是发生了某些事件，一个典型的事件就是产生中断。如果在一段时间里把这个中断禁掉，那么这段时间原来的进程就不会因为某些事件被中断掉，它就可以一直运行下去，也就不会被其他线程打断。这就是用禁止中断来实现锁。

## 二、并行与并发 [00:11:03–00:18:17]

### 2.1 两个必须分清的概念

老师先强调这对概念的重要性：并行和并发，从中文听起来好像没什么区别，但作为计算机专业的学生，一定要非常清楚它们到底指什么。

**并行**（parallelism）讲的是：如果有多个计算的单元，那么这些不同的计算单元可以同时执行不同的任务。它隐含了一个条件——物理上必须有多个计算的单元。这里的「单元」就是 CPU 核（CPU core），或者说不同的 CPU 都可以，本质上就是多个物理的单元；比如 GPU 本身就是这种架构，它本身就有多个计算的单元。多个计算单元同时执行任务，就叫做并行。

**并发**（concurrency）讲的是：即使只有一个 CPU，它也允许多个任务同时运行。多个任务怎么「同时」运行呢？就是第一章讲的虚拟化——大家轮流运行；但从宏观上来看，这些任务又很像在并行地运行。

### 2.2 区别在哪里

老师把区别归结为一句话：并行和并发最大的区别，就在于物理上是否有多个计算单元。

- 并行：物理上或者从非常细的粒度上看，是有多个单元同时在执行。
- 并发：从微观上、从细的粒度上看，虽然宏观上有多个任务同时运行，但微观上所有任务都是串行在执行。就像只有一个 CPU，你「同时」执行多个任务，这多个任务之间一定是来回切换、交替执行的；但从宏观上这些任务感觉是在同时运行。

老师用课件上的两张示意图作了对照说明：左边那张是典型的并行，从多个任务来看它们就是同时在运行；右边那张虽然也有多个任务，但这多个任务并不是所有时间都在同时运行，而是交替在运行。

### 2.3 并行的目的与适用场景

再总结一下什么是并行：最核心的要点是「执行多个任务是同时的」，这个「同时」就是指多个任务都在并行地运行。

这种机制很显然可以显著提升**吞吐率**（throughput）。典型的做法就是有多个计算设备，让多个计算设备执行不同的任务。

老师接着问：并行的典型应用场景适合什么？答案适合「有很多个数据要处理，而这些数据处理之间相互没有依赖性」的场合——用很多个不同的核算这些任务，效率肯定是最高的，因为它们之间不需要有依赖，各自并行独立运行就可以了。如果它们之间会有依赖，效率相对来说就不高，因为有依赖就意味着一个要等待另外一个，多个单元总归会有些浪费。

具体的例子老师举的是**网络爬虫**（web crawler）：如果你需要同时从多个节点爬数据，就用多个节点去爬，这样爬的效率更高，而且很可能不会被封掉。这就是一个典型的、需要用多个节点同时去不同地方爬任务的场景。

**补充说明**：根据本节补充材料《26. Concurrency- An Introduction》第 6 张幻灯片，并发这一侧的目的与并行正好相对：并发的主要目的是降低响应时间，机制是在不同线程之间切换——某个线程能有效推进时就运行它，不能推进时就挂起它去运行别的线程；典型例子是在单个 CPU 上同时跑时钟、编辑器、聊天软件，操作系统给每个程序一个很小的时间片（约 10 ms）。由于切换上下文的代价，并发往往会降低吞吐率。这一段字幕只讲了「多个任务以合理方式共享计算单元」，未展开响应时间与吞吐率的权衡，故按材料补充。

### 2.4 并发的特征

并发刚才讲了，它的典型特征也是有多个任务，但这多个任务需要以一种合理的共享方式来访问这个计算单元。这就意味着：我们有多个任务，但哪个任务先执行、哪个任务后执行其实是不一定的，因为它们只有一个计算单元，到底选哪个先执行、哪个后执行，要依赖于前面的调度算法。

这个过程很显然会带来一个典型的后果：要考虑不同任务执行的**时序**——就是谁先谁后的问题。而谁先谁后的问题，就要求我们必须有一些机制来保证 A 进程或 A 线程运行在 B 进程或 B 线程后面。

> **老师强调**：我们要通过一些合理的机制，实现既要对资源的互斥访问，也要让这些任务的执行按照合理的顺序进行。这就是这一章的两个要点：第一个是互斥的问题，第二个是同步的问题。

## 三、并发要解决的两大核心问题：互斥与同步 [00:18:19–00:21:16]

### 3.1 互斥

互斥解决的是：某一个资源不能被两个进程或两个线程同时访问。也就是说，大家轮流访问某个资源。A 和 B 都要去访问某个资源，那就意味着 A 访问的时候 B 不能访问，B 访问的时候 A 不能访问。

实现互斥的典型机制是锁。老师在黑板上把这个过程拆成几步讲：

1. 有一个资源，我们希望实现对它的互斥访问。
2. 在这个资源外面加一个锁。
3. 每次要访问这个资源的时候，两个线程或两个进程都要去申请锁。
4. 当锁是空的时候，你就可以访问，同时你把这个锁设置成不可访问（被别人占用的状态）。
5. 接着另外的进程来访问的时候，它首先要看锁，现在锁被别人占了，它就不能去访问。

这就是典型的通过锁来实现互斥。

### 3.2 同步

同步解决的是：某些事件一定要发生在另外一些事件之后。

老师给了一个三阶段的例子：A 进程（A 线程）负责从硬盘读数据，B 进程（B 线程）负责把硬盘读出来的数据进行矩阵求和，C 进程负责把这个矩阵运算的结果输出。它们之间必须有依赖关系：你必须等 A 进程把数据读好以后，才能接着执行 B 进程；B 进程把结果算好以后，你才能执行 C 进程去把它显示出来。这就是一个需要同步的问题——A、B、C 之间存在一个时序。

### 3.3 两类机制的分工

实现同步的典型机制是**条件变量**（condition variable, CV）和**信号量**（semaphore）。这两个是当时实现同步的两种典型机制，用它们可以让我们实现 A 进程和 B 进程之间合理的执行顺序。

所以分工是这样的：锁用来实现互斥，条件变量和信号量用来实现同步；当然，信号量也能实现互斥，这一点后面会讲。互斥和同步，就是贯穿着并发这一部分的核心主题。

## 四、线程：从进程到线程的抽象 [00:21:19–00:34:13]

### 4.1 进程的双重身份与线程的引入

讲线程之前，老师先把进程的身份说清楚。讲进程的时候讲到过：进程是一个资源分配的单位，同时也是一个 CPU 调度的单位。也就是说，我们通过进程这个概念把资源分配到进程，同时我们用 CPU 调度算法的时候，也是去调度不同的进程来运行。

既然有了进程，好像已经很合理了：对某个进程可以分配资源，也可以按照不同的优先级来调度。那为什么还要引入线程这个概念？

线程其实是对进程的进一步抽象。简单说，就是要把进程作为资源分配的单位和调度单位这两件事分离开：把进程只作为资源分配单位，把调度的单位变成线程。一个进程里面允许同时存在多个线程，这些线程共享同样的（已经分配好的）资源，并且可以被调度到不同的 CPU 上去并行执行。

所以线程理解起来就是：线程是一个调度的单位，而进程变成了一个资源分配的单位，一个进程里面可以允许多个线程。

### 4.2 为什么要引入多线程

多线程的引入，主要是为了解决进程调度的开销问题。进程调度要进行上下文切换的时候，会涉及很多处理：要把寄存器切换掉，要把各种各样的寄存器信息都重新切换、恢复现场。这个切换开销是比较大的，因为每个进程带了很多资源，切换它的代价比较大。

另一条线索是多核。在一些典型的多核系统里面，很多任务是需要共享一些资源的，但这些任务又需要并行地执行，所以就引发出另外一种抽象——线程。这个抽象把要执行的任务抽象成多个并行的线程，这些线程又共享同样的资源。这样一来，就可以用进程来分配资源、用线程来作为调度的单位，执行效率会更高一点：线程的切换跟进程的切换相比要轻量级很多，线程切换很容易，进程切换相对来说开销很大。

老师把「为什么要有线程」归结为两点。

第一是一个趋势。CPU 的发展遇到了瓶颈：你不可能无限地把单个 CPU 的频率做得很高，因为目前已经到了一个瓶颈——CPU 的频率只能到某个值，再多就上不去了。为了提升算力水平，单个 CPU 不行就设置多核：纵向升不上去了，就横向去扩展。横向扩展必然涉及有多个 CPU 核，也就是 multi-core 的多核 CPU。

第二是多核带来的新问题：既然是多核的 CPU，你怎么样让这个 CPU 的多核发挥它最大的能力？当然可以把不同的进程调度到不同的核上去，但这里有一个典型的问题——进程是一个资源分配单位，同时也是一个调度单位，那么如果多个进程之间要共享数据，开销就比较大。因为进程间的通信开销还是比较大的，它们各自的地址空间不一样，你要通过操作系统去实现地址的共享，从而让它们的数据能共享；操作系统要设计很多机制来支持进程间通信，这个效率其实是不高的。

于是就想到：能不能把要执行的任务放到同一个进程里，让这些任务共享一份数据资源？这样共享就变得简单了——它们虽然是不同的执行单元，但共享同一份内存资源，那么就不用去切换内存资源了。这样多核的利用率就可以更高一点。原来的话，如果要多个进程之间合作，你要通过操作系统去实现进程间的数据通信，效率比较低；而现在，如果本身这多个核上面运行的线程就能够访问同一份资源，那就不需要去解决进程间通信的问题了，因为它在同一个进程内部，同一个进程内部就是可以共享这个数据的。

### 4.3 线程与进程的共享项与独有项

同一进程里面的多个线程共享：

- 进程号（PID）
- 地址空间
- 代码（指令）
- 大部分数据（堆）
- 打开的文件描述符
- 当前工作目录
- 用户 ID 与组 ID

而每个线程有自己的：

- 线程号（TID）
- 一组寄存器，包括程序计数器（program counter, PC）和栈指针（stack pointer）
- 用于保存局部变量和返回地址的**栈**（这个栈也在同一个地址空间里）

所以进程和线程最典型的区别是：进程是资源分配的单位，线程是任务调度的单位。从数据结构上也能看出来：进程对应的是地址空间（相当于内存的资源空间），还有打开的文件、当前工作目录这些资源；而线程对应的是它自己的线程 ID、它的一组寄存器、以及它的栈区域。原来进程身上作为调度的功能被弱化了，调度功能放到线程这里来。

### 4.4 线程切换与进程切换的开销差别

进程切换需要把进程所有的资源重新切换；而线程切换只需要切换线程相关的上下文就够了，也就是线程控制块（thread control block, TCB）里面的一些数据。TCB 里面的数据比进程控制块（process control block, PCB）里面的数据要少得多，所以切换起来更简单。典型的就是程序计数器和寄存器：程序计数器是当前执行的指令的计数器，寄存器是上下文相关的一些信息。

切换的时候，寄存器肯定要切换，包括 PC 寄存器和其他寄存器；但是地址空间是不变的，因为这些线程属于同一个进程。这就是切换进程和切换线程开销不一样的原因——线程切换只需要考虑寄存器。

### 4.5 地址空间中的栈

从地址空间的角度看多线程系统是这样的：一个典型的地址空间包含几个典型区域，包括代码段、堆、栈。如果是单线程系统，栈只有一份，因为它只有一个执行单元；如果是多线程系统，栈就有多份了，因为每个线程都需要保存它的临时变量、返回值之类，所以对应的栈也是多份。这里有两个线程，就有两个栈；多份都没问题。但是它们其他的结构都是共享的，包括堆、代码段，这些都可以共享。

所以多线程系统和单线程系统在内存空间结构上的差异，本质上就是不同的线程有不同的栈。

## 五、线程的操作系统支持 [00:34:18–00:41:07]

引入线程这个概念以后，必然要涉及一个问题：操作系统怎么来支持这种多线程、多任务系统？操作系统的实现是千差万别的，有的操作系统有线程这种抽象，有的没有。而应用程序在编程的时候，既可以写多线程程序，也可以写非多线程程序。如果你写的程序是多线程的，但操作系统又不支持多线程，那怎么办？那显然就有一种映射关系。

老师用 Java 举例：类似 Java 这种语言在运行的时候，专门有一个虚拟机（Java Virtual Machine, JVM）。它怎么把这个多线程的程序解释成操作系统理解的那种执行单元？其实就是 JVM 实现的时候有各种各样的映射机制。

### 5.1 用户级线程：多对一

第一种机制叫**用户级线程**（user-level thread）。它的意思是：我们编程实现的这个线程，只是被程序员所感知——程序员写的是多线程，但这个多线程最终运行到操作系统上的时候，操作系统是没有线程这个概念的，操作系统没有实现多线程，它只能以进程的方式来调度。这就是多对一（many-to-one）的映射。

多对一的意思是：我们可能实现了多线程，但这多个线程运行到操作系统上的时候，它不是以多线程的存在形式，而是多个线程被当作一个任务来执行。

优点是：

1. 不需要操作系统支持，任何操作系统都可以运行，可移植性好。
2. 实现起来比较简单，因为不需要进行系统调用——你的多线程只是应用层程序的一个库函数支持，操作系统上并没有实现线程的概念。

缺点是：

1. 不能实现多核的资源利用。因为你是把多个线程最终映射到一个进程了，那多个线程并没有并行地运行，只是在同一个进程里面串行地执行。
2. 如果一个线程被阻塞了，整个进程都会被阻塞。因为操作系统看不到线程的存在，它就把所有的线程当作一个任务；任何一个线程被阻塞了，那么其他线程也都在这里等待，操作系统不会把其他线程单独调度到其他核上去运行，因为它是看不到的。

用户级线程简单理解就是：程序员写了个多线程的任务，但操作系统不支持多线程，最终这程序员写的多线程程序会被映射到操作系统上面的单独一个进程。

### 5.2 内核级线程：一对一

第二种叫**内核级线程**（kernel-level thread）。它的意思是：操作系统本身就有多线程的概念，操作系统内核支持线程，本身有对应的线程调度机制和实现机制。这样就可以实现用户级线程和内核级线程的一一映射（one-to-one）。

简单说，程序员写了一个多线程的程序，最终编译出来在操作系统上运行的时候，它也是多线程的执行。操作系统内核支持多线程，我们编写出来的线程也是以多线程的方式真实地在执行。

优点是：

1. 可以充分利用 CPU 的多核资源，因为多个线程是被操作系统感知的，操作系统在调度的时候就可以把不同的线程放到不同的核上去。
2. 一个线程被阻塞，其他线程不受影响，因为它的所有线程运行在不同的计算单元上面，其中一个计算单元受阻，其他计算单元不受影响。所以执行效率肯定高一些。

缺点是：

1. 线程操作（创建、调度、同步）的开销相对来说会大一点。
2. 操作系统需要额外的机制来支持内核级的线程机制，它不是对所有操作系统都适用，只能在支持多线程的操作系统上使用——操作系统内核必须得支持线程。

老师补充说：多线程的实现目前来讲已经变成了一个主流，几乎所有任务都是支持多线程的，主流操作系统也都支持线程这个概念。

## 六、竞态条件与非确定性 [00:41:12–00:50:16]、[00:58:18–01:04:00]

### 6.1 竞态条件的定义

既然有了多个线程，就意味着多个任务之间可能会存在一种叫做**竞态条件**（race condition）的东西。

**定义**：竞态条件指两个线程或两个任务共享地访问某些资源，并且在访问这些资源的时候相互之间存在竞争关系。

### 6.2 一个加一操作其实有三条机器指令

老师用了一个非常简单的例子：假定两个线程都有一段代码，对共享变量 counter 进行访问，各自都对 counter 加 1。如果两个线程各自执行了一遍，我们期望的结果就是最后 counter 加了两次，变成加 2。比如 counter 的初始值是 50，执行完这两次以后，期望值是 52。这是我们认为理所当然的事情。

但这个理所当然的事情，有时候并不是那么理所当然，因为存在竞态条件：两个线程同时在访问 counter 这个资源，访问的先后可能导致结果不一致。

关键在于：`counter = counter + 1` 这条语句看起来是一步操作，但在实现的时候要执行三步。老师把这三步拆得很细：

counter 是一个变量，它在内存空间里面必然分配了一个地址。如果它是一个 int 值，在内存空间里面占了 4 个字节，那么它就被放在某 4 个字节的空间里，给定起始地址，然后连续的 4 个字节就放在这里。要对 counter 加 1，就要把这个变量从内存里读出来，让 CPU 去计算加 1。所以第一步是把 counter 这个数据从内存读到 CPU 能够访问的一个寄存器里面去——相当于把 counter 移到某个寄存器，这是第一步。接着 CPU 对这个寄存器的值进行加 1，这是第二步。这个值现在在寄存器里面，下一步就是要把寄存器的这个值重新写回 counter 所在的内存地址，这是第三步。

所以理论上看似一步的操作，翻译成机器语言至少是这三条：

```
mov  0x8049a1c, %eax   ; 把 counter 从内存读入寄存器
add  0x1, %eax         ; 寄存器加 1
mov  %eax, 0x8049a1c   ; 把结果写回 counter 的内存地址
```

也就是说：第一条把 counter 从内存读入寄存器；第二条让寄存器加 1；第三条把结果写回 counter 的内存地址。

### 6.3 交错执行如何得到 51

执行这三条语句，意味着两个线程都要执行这三步，而它们执行的时候可能是以一种交替的方式执行——你不能保证它到底谁先谁后。无论是在同一个核上（因为调度的关系会交替），还是在两个不同的核上（物理上可以完全独立并行，但哪个核跑得快、哪个核跑得慢你没法确定），都会涉及谁先谁后的问题。

**例子**：假定刚开始 counter 是 50。T1 运行，把 counter 移到 register1，那么就是把 50 放到 T1 的 register 里，register1 变成 50。这时候执行完这一步，马上就切到 T2 去执行，T2 也把这个 50 拿到 register2 里面去。然后它们各自加一：register1 变成 51，register2 也变成 51。接着 T1 把 register1 写到 counter，counter 变成 51；T2 也把 51 写到 counter，counter 还是 51。

| 步骤 | T1 | T2 | counter | register1 | register2 |
|------|----|----|---------|-----------|-----------|
| 1 | load counter | — | 50 | 50 | — |
| 2 | 被切出 | load counter | 50 | 50 | 50 |
| 3 | add 1 | — | 50 | 51 | 50 |
| 4 | — | add 1 | 50 | 51 | 51 |
| 5 | store register1 | — | 51 | 51 | 51 |
| 6 | — | store register2 | 51 | 51 | 51 |

最终的结果是：它们俩分别执行了一遍加一的操作，但最后结果还是只有加了一遍——期望 52，实际得到 51。

老师把这个结果的原因归结得很直接：不一致的最大来源，就是 T1 和 T2 在执行的过程中没有按照我们预期的顺序去执行，它们同时访问了 counter 这个变量，导致 counter 的结果不是我们预期的结果。

### 6.4 什么情况下才会发生竞态

老师在这里停下来提了一个问题：两个线程访问同一个变量，什么情况下会发生竞态条件？什么情况下即使共享也不会造成竞态条件？他提示从读和写的角度来看。

- 如果两个线程只是读：肯定不会出问题。因为它不涉及对这个变量的修改，不管你怎么读，反正都是同一个值。
- 如果两个写：肯定会出现，因为两个都要写，这正是刚才那个例子。
- 如果一个读一个写：理论上也会出现。只要有一个写就可能出现，因为它涉及「写前读」和「写后读」的问题——写前读得到的是一个值，写后读得到的是另外一个值。

所以结论是：读和写，只要其中有一个写操作，就会出现竞态条件的问题。在设计多个线程共享访问某个资源的时候，一旦有写操作，就会造成竞态条件。

### 6.5 非确定性及其危害

竞态条件带来的结果，就是前面提到的**非确定性**（non-determinism）。非确定性的含义是：我们执行的结果跟运行的具体过程有关，依赖于具体的调度顺序。

这种非确定性可能不是我们想要的，因为从宏观上讲，我们逻辑上希望达到的结果，跟你这个具体的执行结果可能预期不一致。带来的后果就是：我们写的程序，你的意图是一个意图，但执行的结果是另外一个结果，这中间出现了不一致，而不一致的原因就在于出现了竞态条件。

非确定性最大的问题是：它每次结果都不一样，你也不知道错在哪里。有可能你做测试的时候这次是一个结果，下次测试又变成另外一个结果。但这肯定不是我们想要的结果，因为我们意图上肯定是需要一个确定的结果。

> **老师强调**：这个非确定性肯定不是我们想要的结果，因为我们意图上肯定是需要一个确定的结果。

### 6.6 解决方向：原子性

怎么解决这个问题？你必须要有一种合理的机制来保证：不管中途调度的顺序是怎么样，我都能保证它的结果是我想要的那个结果。

老师回到根源：出现竞态条件的最根本原因，在于从我们高层的意图来讲，这条语句只是一条语句，所以我们理论上认为这条语句不会被中断；但实际上这条语句翻译成机器指令的时候，至少有那三条语句。这三条语句如果不是连续地执行，就会出现刚才讲的不一致、非确定性的情况。

于是思路就出来了：既然问题来源于并发的执行过程，那我们能不能让这三条语句还是当作一条语句执行，就是它在执行过程中不要中断？如果这三条指令的确能够不中断、一次性地执行完毕，结果的确是我们预期的那样，因为加一的操作就是加一前和加一后这个状态，我们只要中间状态不要去改变就可以了。

> **老师强调**：我们需要有一些机制来实现这种不可中断性——这就是后面所有同步机制要解决的问题。

## 七、临界区与锁 [01:04:02–01:19:48]

### 7.1 临界区

**定义**：**临界区**（critical section）指一段访问共享变量的代码，这段代码不能被多个线程同时执行。

我们通常把需要对共享变量进行访问的那个代码区叫做临界区。前面那三条语句，其实就是访问临界区的一个代码。在进入临界区的时候，必须要有一些机制来保证它是以互斥的、或者说是以原子方式执行的，这样就可以保证执行的结果是我们预期的结果。

最原始、最简单的实现思路是：既然这个代码区域是对共享变量访问、我们不希望它中断，那我们可不可以就在临界区的外面加一个限制——当某个进程或某个线程的代码要执行临界区的时候，它必须要获得一种许可；只有获得许可的线程可以执行，没有获得许可的线程就在这里等着。这样就可以保证同一时间只有一个线程在执行这段代码，也就保证它不被中断，不至于产生预期不到的非确定结果。

实现临界区互斥访问的机制有很多，有硬件的机制，也有软件的机制。硬件的机制包括底层的那种硬件锁方式；软件的方式可以用操作系统来支持，包括信号量、条件变量，还有一些其他机制。

临界区是风险比较高的代码：多个线程同时运行这个临界区的代码时，会导致预期不到的结果。

### 7.2 锁的抽象

锁的机制是这样的：既然临界区是大家都要访问的公共资源，那这个公共资源如何被多个线程所使用、而且同一时间只有一个线程使用？

一个最朴素、最原始的方法，就是在访问这个共享变量的前后加上锁的机制。典型的就是设置一个锁，这个锁叫做**互斥量**（mutex），把它设在访问 balance 这个变量的前后：在访问 balance 之前你要去获得这个锁，访问完了你要去释放这个锁。这就可以保证执行 `balance = balance + 1` 这个操作不会被中断掉。

```c
lock_t mutex;
...
lock(&mutex);
balance = balance + 1;
unlock(&mutex);
```

这就是实现原子操作最基本的方法——加锁。加锁的逻辑可以这样理解：在访问某个共享变量的时候，在它的前后加一个访问入口；只有获得这个锁，你才能进入临界区；进入临界区访问完、结束以后，你得把这个锁重新还回来。

老师强调这把锁本身只有两个状态：**锁着**或者**没锁**。加了锁以后，其他线程就没法访问；这样就能保证大家是以串行的方式访问这个资源，从而避开并发带来的后果。

> **老师比喻**：这就像我们要进一个房间。进一个房间，你得首先拿锁把这个房间的门打开，打开以后你再把它关上；这时候钥匙你不要给他，你先保留着；等到你出来的时候再把门打开，同时把钥匙交出来。这样其他人就可以拿钥匙进去。

所以锁的逻辑还是比较简单、比较清晰的，它可以保证原子操作。但锁最关键的是什么？

> **老师强调**：在这个共享变量访问前加个锁、访问后释放锁，这只是一个比较抽象的原理；**到底怎么实现这个锁才是最关键的**。

### 7.3 实现锁的两条路线

锁的实现有各种各样的机制，包括底层的 `load`、`store`、`test-and-set` 这些原子指令，还有就是禁止中断等等。它的逻辑本质上就是把这段程序变得不可中断：你在执行这段代码的过程中，不要被其他事情中断掉，就可以保证你连续地执行完这段代码。

### 7.4 忙等锁与睡眠锁

锁的实现有两种典型形态：一种是**自旋锁**（spin lock），一种是**睡眠锁**（sleep lock）。睡眠锁的意思是：我们把等待的线程放到一个队列里面，直到这个锁被释放以后，你才会去唤醒其他线程。

老师用收快递打比方来说明这两者的区别。

> **老师比喻**：收快递就相当于你要访问的那个资源。自旋的意思就是，你为了能访问这个资源，就不断地去问快递员「到了没有」；到了你就去拿，没到你就不断地在循环问「到了没有、到了没有」。这相当于你这个人还是要不断地去执行「问」这个任务，你还是在消耗 CPU。睡眠锁的意思就是，你不用去问快递到了没有，到了的话快递员直接打你电话——你只需要在这里做其他事情，或者干脆阻塞在那里，等快递到了他自然来打你电话，相当于「打电话」这个动作说明东西到了、你可以去执行了。

所以两者的最大区别就在于：**自旋锁在等这个事件的时候要消耗 CPU 周期**，因为你要执行那个 while 循环、循环地去问好了没有；而睡眠锁不需要循环去问，你放在队列里面，到了自然会通知你。

这一区别在后面还会反复出现：条件变量本质上就是为了解决忙等效率不高的问题；信号量也是同样的道理。

### 7.5 互斥之外还剩什么：ordering

锁解决的是互斥。但互斥只是并发的目标之一，第二个目标是**顺序**（ordering），也就是同步问题。

同步问题要解决的是：我们有两个任务，必须要求 A 任务和 B 任务按照某个顺序执行——A 主要运行在 B 之前或者之后，我们就认为它是以某种顺序执行。

实现这种顺序需要一些额外的机制，这个额外机制就是条件变量或者信号量。简单说就是：锁可以实现互斥，条件变量和信号量可以实现同步；当然信号量也能实现互斥。

老师在这里提出了后面反复使用的经典问题——**生产者–消费者问题**（producer–consumer problem）：有一个生产者、一个消费者，他们可以从一个缓冲区里面拿东西和放东西；在生产者和消费者执行的过程中，有时候需要相互等待对方。

什么时候呢？典型的例子就是：当缓冲区满的时候，你就不能往里面再放东西了，因为放不下了；当缓冲区是空的时候，你也不能从里面取东西，因为你取不出来。

所以这两个事情是需要去同步的：消费者要等待生产者往里面放一个东西；生产者满的时候要等待消费者从里面至少取走一个东西，留一个空档出来。生产者必须等待消费者（缓冲区快满时），消费者必须等待生产者（缓冲区为空时）。

那除了同步，是否还需要考虑互斥？老师明确回答：当然需要考虑。因为对这个缓冲区（buffer）的访问你必须要考虑互斥——缓冲区是一个共享变量，生产者和消费者肯定需要以互斥的方式访问，你不能说是这个生产者在放的时候，你这个消费者也在取。

所以生产者–消费者问题同时包含两个限制条件：空的时候不能取，满的时候不能放（同步）；以及同一时间只能有一个人在操作缓冲区（互斥）。

## 八、条件变量 [01:19:59–01:44:10]

### 8.1 从互斥到等待：条件变量的动机

前面讲的所有机制都是为了解决互斥，而并发还有第二个目标——顺序。实现顺序、或者说实现同步，最常用的机制就是条件变量。

条件变量从字面上看就是「条件」加「变量」，所以它本质上是一个变量，这个变量用来判断我们某个条件是否满足，所以叫条件变量。

一个比较简单、也比较常用的例子是 join。在类似 Java 的语言里，你可以用一个 join 操作来表示子线程和父线程之间的同步。它的典型过程是：如果线程 T1 执行了 `T2.join()`，那就说明 T1 要等待 T2，直到 T2 运行结束，T1 才能继续执行后续的代码。这样就实现了「T1 要等 T2 运行、直到它运行结束才可以继续执行后续代码」的顺序问题。

它的典型应用场景是：T1 要去处理 T2 读出来的数据的时候，就可以这样操作，保证 T1 要等待 T2 把数据处理好之后再接着下面的操作。这样两个本来并行的线程 T1 和 T2，就以一个串行的方式来执行了。

### 8.2 先用一个标志变量忙等

先看目标。假设 child 的代码就是打印 `child` 然后返回；main 的代码是打印 `parent: begin`、创建子线程，然后要等待 child 运行，再打印 `parent: end`。问题是：main 怎么等待 child？

一个简单的办法是用一个变量作为「是否运行结束」的标志：child 运行结束时把这个标志置成 1，表示我运行结束了，父线程就可以往下执行；父线程为了满足这个条件，就在这里用一个 while 循环判定这个标志有没有变成 1——变成了就往后执行，没变成就在这里不断地循环消耗。

```c
volatile int done = 0;

void *child(void *arg) {
    printf("child\n");
    done = 1;
    return NULL;
}

int main(int argc, char *argv[]) {
    printf("parent: begin\n");
    pthread_t c;
    Pthread_create(&c, NULL, child, NULL);
    while (done == 0)
        ; // spin
    printf("parent: end\n");
    return 0;
}
```

这个状态就叫做**忙等**（busy waiting）。忙等的意思就是：parent 是在等待 child，但他在等待的过程中又是很忙的（busy），他要消耗 CPU 周期——消耗 CPU 周期就是执行这个 while 循环，不断地判定有没有把这个标志位改成 1。但其实在这里循环这个语句没有任何实质的意义，因为它没有执行有效代码，只是在判定要不要往后执行。

所以忙等可以总结为：这个进程处于等的状态，但它又不是在这里闲着，它在消耗 CPU 周期。因此忙等一般被认为是一种效率不太高的办法。因为 parent 虽然没有有效地执行后续代码，但仍然在消耗 CPU 周期——在 child 和 parent 不断切换的过程中，parent 还是在消耗 CPU 周期。这种方式就类似于前面讲的自旋锁：它要执行忙等来消耗 CPU 周期，保证即使调度到 main 这个进程的时候，它也不会往后去执行，而是靠这个 while 循环把它固定在那个点上。

这种方式最大的问题就是对资源的利用率不高，因为 parent 在不断地消耗 CPU 时间。

### 8.3 条件变量的定义与基本操作

那么怎么让 wait 这个操作变得更高效一点？这就引入了条件变量。

条件变量的基本思想是：让线程等待某个事件发生，然后再接着做；而这个事件的状态是被多个线程所共享的。所以简单说，它首先是一个变量，这个变量可以设置成不同的值（就是这里的状态），用来判定某个事件是否发生。

条件变量的基本操作就是 wait 和 signal：

- wait：让这个线程去等待这个条件发生。它把这个线程放到一个等待队列里面；放到队列里面以后，它就不会去消耗 CPU 周期了，而是一直在队列里面等。老师在这里的说法是：如果条件已经满足（他借用「锁是否可用」来讲这一步），那就直接执行后续的代码；如果条件不满足，那它就等待——需要进入一个等待队列，并且这个线程进入休眠状态，因为它没必要被调度来执行，它要等某个事件发生之后再来执行才有效。
- signal：什么时候去通知它重新来运行呢？就是这个条件发生以后，我们去通知它。有多个等待的线程时，就唤醒一个（也可以唤醒多个）；如果没有等待的线程，那就什么也不做。

所以 wait 就是让它去「登记」一下：我要等待这个事件发生；signal 就是来通知它：这个条件已经发生了。

> **老师比喻**：这就像大家去医院看医生。医生同一时间只能看一个病人，那怎么办？我们就把自己加到一个等待队列里面，等到医生空的时候，他会去通知「下一个病人进来」。这样你就不用随时去医生的门口看「医生看好没有、医生看好没有」，而是另外有一套机制，好了以后会通知你。如果没有叫号系统，你就得不断地去医生那里推开门看他空了没有，效果肯定不好；有了叫号系统，医生好了会自动叫你。

所以条件变量本质上解决了忙等效率不高的问题：以前要靠线程自己去查这个状态，现在变成我们有一个队列，让它去这里排队就行了；等到事件发生以后，我们通过通知这个队列，让它重新来运行。这是一种从「主动去查」变成「被动去通知」的转变，相对来说就不用消耗额外的 CPU 时间。

signal 有两种机制：一种是可以通知其中一个线程——如果有很多人在这里排队等这个事件发生，我们就唤醒排在最前面的那个，这是我们常用的方式，就像医院的叫号系统；另一种是通知所有等待的线程，告诉所有等待者这个事件已经好了。这两种方式后续的处理肯定是有所不同的。

所以条件变量部分的基本操作就是：wait 就是让你去登记、然后排队；signal 就是通知你可以来执行了。另外还有 `broadcast`，就是唤醒多个，让所有等待的线程都知道这个条件发生了。

需要注意的是，条件变量总是和一个互斥量配合使用，因为「状态」和「队列」都是被多个线程访问的。

**补充说明**：根据本节补充材料《30. Condition Variables》第 9–10 张幻灯片，`pthread_cond_wait(c, m)` 的语义是：调用时假定已经持有锁；它把调用者挂起睡眠并且**原子地释放**这把锁；当它被唤醒返回时，会重新获得这把锁。`pthread_cond_signal(c)` 唤醒一个等待线程（如果没有等待者就直接返回、什么也不做）；`pthread_cond_broadcast(c)` 唤醒全部等待线程。字幕讲到了「wait 要持锁、signal 唤醒一个或全部」，但未点明「释放锁与睡眠是原子的一步、返回时重新持锁」，故按材料补全。

### 8.4 用条件变量重写 join

把上面的 join 例子用条件变量实现，代码是这样的：

```c
int done = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t c = PTHREAD_COND_INITIALIZER;

void thr_exit() {
    Pthread_mutex_lock(&m);
    done = 1;                 // state
    Pthread_cond_signal(&c);  // signal cv
    Pthread_mutex_unlock(&m);
}

void *child(void *arg) {
    printf("child\n");
    thr_exit();
    return NULL;
}

void thr_join() {
    Pthread_mutex_lock(&m);
    while (done == 0)
        Pthread_cond_wait(&c, &m);  // wait cv
    Pthread_mutex_unlock(&m);
}

int main(int argc, char *argv[]) {
    printf("parent: begin\n");
    pthread_t p;
    Pthread_create(&p, NULL, child, NULL);
    thr_join();
    printf("parent: end\n");
    return 0;
}
```

执行过程是这样的。

父线程：创建子线程后继续运行自己；调用 `thr_join()` 等待子线程完成；获得锁；检查子线程是否完成；如果没完成，就调用 wait 把自己放到队列里睡眠（同时原子地释放锁）；被唤醒后重新获得锁，检查通过再释放锁。

子线程：打印 `child`；调用 `thr_exit()` 去唤醒父线程；获得锁；设置状态变量 done；signal 父线程从而唤醒它；释放锁。

这个代码是正确的、可以工作的，因为它是把 parent 放到一个队列去等，等的时候它不需要参与 CPU 的调度，不用去浪费 CPU 的 cycle。

老师在这里强调了这个锁的作用：这个锁其实就是用来实现对 done 这个状态的保护——因为 done 这个状态和条件变量的队列都是被多个线程访问的，必须用锁保证「检查状态」和「进入等待」这两件事之间不被打断。

### 8.5 必须另有状态变量

老师接着问：如果 `thr_exit` 和 `thr_join` 不去加这个状态变量 done，会出现什么问题？

肯定要出错。因为一定要有一个状态来表示它是否完成。

具体地看：假定 parent 执行的三条语句是 x（lock）、y（cond wait）、z（unlock），child 执行的代码是 a（lock）、b（signal）、c（unlock）。那么有可能会出现一个调度顺序：先把 child 的 a、b、c 都执行完毕了，再执行 parent 的 x、y。执行到 y 以后，parent 其实是永远唤醒不了了——原因就是它一直在那里等待，而没有任何人会来唤醒它了。因为 child 已经一次性把 signal 发完了，而当时还没有人在等待。

所以设置条件变量时必须要有一个注意事项：必须加一个状态，这个状态是比较关键的。条件变量通知的典型时机，就是在这个状态发生变化的时候，我们去通知其他的线程。如果没有这个状态，就有可能会导致没人去唤醒被睡眠的那个线程。

> **老师强调**：条件变量必须和一个状态变量合在一起使用，不能只用一个条件变量。

### 8.6 必须持锁调用 wait 和 signal

老师又给出了另外一种实现：虽然加了状态变量 done，但加的时候用的是 `if` 而不是 `while`。用 `if` 和 `while` 会有什么区别？

用 `if` 就是一次性的判定。一次性判定可能出现的问题是：如果那次判定没有通过，那就有可能一直睡下去了——相当于你正好不巧，那次没有判定（通过），或者被中断，那它也会永远在这里睡下去。而用 `while` 显然不会，因为 `while` 会不断地去判定这个事情。

具体的调度序列是这样的：parent 执行到 `if (done == 0)`，判定通过（done 还是 0），就在它还没有执行 wait 的时候被中断掉；接着 child 执行了 a（done = 1）和 b（signal）；等 parent 回来的时候，它直接执行了 wait，就把自己放到队列里面——但是 b 这个 signal 已经执行完毕了，所以它 wait 以后就永远在这里等。

**补充说明**：根据本节补充材料《30. Condition Variables》第 16–18 张幻灯片，还有第三种错误写法：保留了 done 变量，但调用 `signal` 或 `wait` 时不持锁。此时父线程检查 done 得到 0、正准备睡眠，在它调用 wait 之前被中断；子线程把 done 改成 1 并 signal，因为没有线程在等待，这个信号被丢掉；父线程恢复后进入 wait，永久睡眠。该页由此给出第二条规则：调用 signal() 或 wait() 时必须始终持锁，用互斥量保证「与状态交互」和「wait/signal」之间没有竞态。字幕只讲了「必须与状态变量配合使用」这一层道理，未点名这一反例，故按材料补充。

### 8.7 必须用 while 而不是 if

所以 `thr_join` 和 `thr_exit` 一定要配合一个状态变量，而这个状态变量也要用一个合理的循环去判定，也就是用 `while` 而不是 `if`。

为什么？老师的推理是：用 `if` 就是一次性的判定，而一次性判定可能碰上「判定通过之后、真正进入 wait 之前被中断」这种时机——那次判定没有起到作用（或者被判定的状态随后就被改变），于是它也就一直睡下去了。也就是说，正好不巧那一次判定被错过，它就会永远在这里睡眠。而用 `while` 显然不会，因为 `while` 会不断地去重新判定这个事情。

任何一次唤醒之后都要重新检查状态，这就是为什么必须写成 `while (done == 0) wait(...)`。

**补充说明**：根据本节补充材料《30. Condition Variables》第 19–20 张幻灯片，这种「唤醒后状态已不再成立」的现象统称**虚假唤醒**（spurious wakeup），有两类典型情形：一是 `broadcast()` 会唤醒所有等待的线程，但其中只有一个线程能退出 while 循环、拿到锁，其他线程醒来后必须重新检查状态，条件不成立就继续睡；二是一个线程被唤醒后被放进就绪队列（并没有立即被调度），而在这期间另一个线程可能先被调度运行并且改变了状态，因此被唤醒的线程在被调度后必须重新检查状态。该页还留了一句「请课后自己搜索原因」，字幕没有展开这两类情形，故按材料补全。

这里也顺便说明了锁与 wait 的关系：必须保证在调用 `wait` 的时候持有这把锁，而且获得锁之后再检查状态。所以条件变量的使用要合理：状态、循环判定、持锁调用，三件事缺一不可。

### 8.8 条件变量的定位

条件变量的本质问题是：它需要一个状态和一个条件变量合在一起使用，相对来说处理这个事情比较麻烦。

正因为条件变量用起来比较复杂，后续才引入信号量这种机制去解决同样的问题。老师很直接地说：大家觉得条件变量用起来很复杂，都不愿意用它；后续大部分情况下我们都更多地去使用信号量那种机制，信号量的理解相对来说更简单，不用条件变量那么复杂。

条件变量本身可以这样理解：它就是把某个事件的发生用一个队列来进行排队等候，这样就可以用一个比较好的排队方式，不去参与 CPU 的竞争，然后再来等待某个事件发生，相对来说可以比较好地节省资源。但是它的使用要结合一些状态变量一起来用，理解比较复杂。大家知道有条件变量这个事情、知道它可以解决顺序问题就可以了。

## 九、信号量 [01:45:53–02:10:11]

### 9.1 信号量的引入

信号量是在条件变量的基础上，提供了一种更友好的实现互斥和同步的机制。

并发要解决两大基本问题：第一个是互斥，第二个是同步。互斥前面用锁的方式解决，同步用条件变量解决。这两种机制都可以达到目的，但相对来说比较复杂。于是引入另外一种机制——信号量。信号量正好可以把这两个问题同时解决：既可以实现互斥，又可以实现同步；既可以用来实现对共享变量的访问，又可以用来实现多个任务之间按顺序执行。

简单说，信号量就是「锁 + 条件变量」的一种实现：它的锁实现了互斥，它的条件变量实现了同步。信号量通常是操作系统提供的系统调用接口，同时在很多高级语言里面也有封装，所以在很多高级语言里可以直接调用。

### 9.2 信号量的定义与两个原语

**定义**：信号量是一个带有整数值的对象，我们可以用两个例程来操作它——`sem_wait()` 和 `sem_post()`。

初始化用 `sem_init(&s, 0, 1)`：第二个参数 0 表示这个信号量在同一进程的线程之间共享，第三个参数是它的初始值。

你可以认为信号量是一个类似于面向对象编程的对象：对象里面有它的变量值，也有一些对应的操作。典型的操作就是 wait 和 post（也叫 wait 和 signal，或者 P 和 V）。

- `sem_wait()`：把信号量的值减 1；如果减完以后信号量的值是负的，就等待。也就是说，如果调用时信号量的值大于等于 1，就立即返回；否则调用者被挂起，等待后续的 post。
- `sem_post()`：把信号量的值加 1；如果有线程在等待，就唤醒其中一个。

所以这两个操作分别代表了：我首先要等待这个信号量，接着对信号量进行一个通知。

### 9.3 值的含义：资源数量与等待线程数

怎么理解信号量这个数据结构？简单认为：它是某种资源（resource），这个整数值就表示我们这个资源到底有多少份。比如二进制的信号量，它的值可以是 0 或者 1；如果信号量等于 N，就表示我这个信号量的资源数量有 N 个。

- 执行 wait 的时候，只要你这个信号量大于 0，那我就可以不用等，直接执行——因为有资源，就把资源分配给他，同时把资源数量减 1。
- 执行 post 的时候，说明这个资源被释放回来了，就把资源加 1；同时要通知那些在等的人可以来使用这个资源。

所以 wait 和 post 本质上就是对信号量这个资源的加一和减一的操作。

一个很重要的性质是：**当信号量的值为负数时，它的绝对值等于正在等待的线程数**。因为如果整数值目前大于零，那这个队列肯定是空的，因为不需要等待、资源是足够的；如果是需要等待，那就说明这个值肯定是负数——负多少，就说明有多少个线程在等。

老师用羽毛球场来讲这个数据结构：

> **老师比喻**：就像大家去预约羽毛球场，场地只有 10 个。这 10 个场地就是一个受限的资源，我们把它当作信号量，刚开始这个资源数量就是 10。所有人都想去打羽毛球，而同一个场地不可能两个队伍同时打，所以必须互斥地访问任何一个场地。某个人要去打球，他首先要执行 wait：如果信号量大于 0，就说明还有场地，他直接可以去打，不用等；打完以后他执行 post，把这个场地释放出来还给别人。如果某个人执行 post，就相当于把资源还回来了，还得去通知正在等待打球的那个人，让后续的线程接着来使用这个资源。如果当前资源数量等于 -2，那就说明目前还有两个人在等待这个场地，队列里排了两个人。

所以信号量可以概括为：一个资源数量，加一个等待队列。资源数量大于 0 时队列肯定是空的；资源变成负数，绝对值就是排队的人数。

老师在这里还用生产者–消费者提前示意了同步信号量的用法：设缓冲区能放的位置数是 N，就设一个信号量 empty，初值等于 N，表示刚开始缓冲区全是空的；生产者要往里面写，就先对 empty 执行 wait，也就是只有 empty 的数量大于 0 才能往里写。这个资源数量刚开始是 N，写一次就减少一次，写满了 empty 就变成 0；这时如果还要往里面写，就必须等 empty 重新变成正数才能继续操作。这就是一个典型的用信号量实现同步的例子。

另一个操作是 post：post 就是对资源加 1，也就是它释放资源——把这个信号量加 1，如果有等待的线程就把它唤醒。

### 9.4 二进制信号量与锁

信号量可以是整型信号量，也可以是二进制信号量。所谓二进制信号量，就是取值只能是 0 和 1 两种值。

它的典型用途就是用作锁：如果值是 1，说明这个锁目前是空的、你可以用；如果变成 0，就说明锁被别人占用了、你就不能用。这样我们就可以用信号量的方式来实现锁：

```c
sem_t m;
sem_init(&m, 0, 1);   // 初值必须是 1
sem_wait(&m);
// critical section
sem_post(&m);
```

如果初值不是 1 而是别的值，就不能保证互斥了——初值必须是 1。

### 9.5 两个线程使用信号量的执行轨迹

老师逐行念了这个执行轨迹（初值为 1，两个线程 T0、T1）：

| 信号量值 | T0 | T0 状态 | T1 | T1 状态 |
|---------|----|---------|----|---------|
| 1 | — | 运行 | — | 就绪 |
| 1 | 调用 sem_wait | 运行 | — | 就绪 |
| 0 | sem_wait 返回 | 运行 | — | 就绪 |
| 0 | 进入临界区 | 运行 | — | 就绪 |
| 0 | 被中断，切换到 T1 | 就绪 | — | 运行 |
| 0 | — | 就绪 | 调用 sem_wait | 运行 |
| -1 | — | 就绪 | 值减 1 | 运行 |
| -1 | — | 就绪 | 值 < 0，睡眠 | 睡眠 |
| -1 | — | 运行 | 切换到 T0 | 睡眠 |
| -1 | 退出临界区 | 运行 | — | 睡眠 |
| -1 | 调用 sem_post | 运行 | — | 睡眠 |
| 0 | 值加 1 | 运行 | — | 睡眠 |
| 0 | 唤醒 T1 | 运行 | — | 就绪 |
| 0 | sem_post 返回 | 运行 | — | 就绪 |
| 0 | 被中断，切换到 T1 | 就绪 | 运行 | 运行 |
| 0 | — | 就绪 | sem_wait 返回 | 运行 |
| 0 | — | 就绪 | 进入临界区 | 运行 |
| 0 | — | 就绪 | 调用 sem_post | 运行 |
| 1 | — | 就绪 | 值加 1 | 运行 |

关键是：T1 在值为 0 的时候去 wait，值被减到 -1，于是它睡眠；直到 T0 执行 post 把值加回 0 并唤醒它，它才能返回并进入临界区。这就保证了同一时间只有一个线程在临界区里。

### 9.6 用信号量做同步：parent 等 child

信号量也可以作为条件变量来使用，也就是用来做同步。怎么实现同步呢？就是把信号量设成一个整数，在两个不同的线程里面分别用 wait 和 post。

看 parent 等 child 的例子：

```c
sem_t s;
sem_init(&s, 0, 0);   // 初值是 0

void *child(void *arg) {
    printf("child\n");
    sem_post(&s);     // signal: child is done
    return NULL;
}

int main(int argc, char *argv[]) {
    sem_init(&s, 0, 0);
    printf("parent: begin\n");
    pthread_t c;
    pthread_create(&c, NULL, child, NULL);
    sem_wait(&s);     // wait for child
    printf("parent: end\n");
    return 0;
}
```

初值必须是 0。老师讲了两种执行情形。

情形一：parent 在 child 调用 post 之前就调用了 wait。

| 值 | parent | parent 状态 | child | child 状态 |
|----|--------|-------------|-------|------------|
| 0 | 创建 child | 运行 | 已存在、可运行 | 就绪 |
| 0 | 调用 sem_wait | 运行 | — | 就绪 |
| -1 | 值减 1 | 运行 | — | 就绪 |
| -1 | 值 < 0，睡眠 | 睡眠 | — | 就绪 |
| -1 | 切换到 child | 睡眠 | 运行 | 运行 |
| -1 | — | 睡眠 | 调用 sem_post | 运行 |
| 0 | — | 睡眠 | 值加 1 | 运行 |
| 0 | — | 就绪 | 唤醒 parent | 运行 |
| 0 | — | 就绪 | sem_post 返回 | 运行 |
| 0 | — | 运行 | 切换到 parent | 就绪 |
| 0 | sem_wait 返回 | 运行 | — | 就绪 |

情形二：child 在 parent 调用 sem_wait 之前就已经运行完。

| 值 | parent | parent 状态 | child | child 状态 |
|----|--------|-------------|-------|------------|
| 0 | 创建 child | 运行 | 已存在、可运行 | 就绪 |
| 0 | 被中断，切换到 child | 就绪 | 运行 | 运行 |
| 0 | — | 就绪 | 调用 sem_post | 运行 |
| 1 | — | 就绪 | 值加 1 | 运行 |
| 1 | — | 就绪 | 唤醒（无人） | 运行 |
| 1 | — | 就绪 | sem_post 返回 | 运行 |
| 1 | parent 运行 | 运行 | 切换到 parent | 就绪 |
| 1 | 调用 sem_wait | 运行 | — | 就绪 |
| 0 | 值减 1 | 运行 | — | 就绪 |
| 0 | 值不小于 0，直接返回 | 运行 | — | 就绪 |
| 0 | sem_wait 返回 | 运行 | — | 就绪 |

第二种情形正好说明信号量为什么比「只用一个条件变量」更简洁：即使事件先发生了，值会先被加到 1，后来的 wait 只需要把 1 减成 0 就直接返回，不会丢失这个「已经发生」的信息。也就是说，信号量的整数值本身就充当了那个必须额外维护的状态变量。

### 9.7 互斥与同步在写法上的判据

老师在这里停下来对比了两段代码，要求学生自己看：实现互斥时 wait/post 的代码、和实现同步时 wait/post 的代码，有什么区别。

实现互斥：`wait` 和 `post` 是在**同一个线程**里面成对出现的——同一个线程里，在临界区前面加 wait，临界区结束以后 post。

实现同步：`wait` 和 `post` 的代码**不在同一个线程**里面出现，而是一个线程用 wait、另一个线程用 post。只有这样才能实现同步。

具体到 parent/child 这个例子：parent 执行的是 wait，child 执行的是 post。这就是为了在多个线程之间实现同步：把同一个信号量的 wait 和 post 分到两个不同的线程里去执行。

接着老师又追问：既然 wait 和 post 分处两个线程，那到底是先发生的那个事件执行 post，还是后发生的事件执行 post？答案是：**先发生的那个事件执行 post**——先发生的事件执行完毕以后 post；后发生的事件在它前面加一个 wait，在那里等着，等到 post 之后 wait 才接着执行。

> **老师强调**：大家一定要知道，信号量用作互斥也可以、用作同步也可以，但是用作互斥的时候它是在同一个线程里面成对出现，用作同步的时候它是分别在两个不同的线程里面出现。

## 十、经典同步问题之一：生产者–消费者 [02:10:17–02:20:09]

### 10.1 有界缓冲区与 put/get

生产者–消费者问题就是一个**有界缓冲区**（bounded buffer）问题：有一个固定容量的缓冲区，有一类线程往里面放，有一类线程从里面取。这一放一取，就必然要涉及同步和互斥。

数据结构是这样的：`buffer[MAX]` 是一片缓冲区，`fill` 是下一次写入的位置，`use` 是下一次读取的位置。

```c
int buffer[MAX];
int fill = 0;
int use = 0;

void put(int value) {
    buffer[fill] = value;      // f1
    fill = (fill + 1) % MAX;   // f2
}

int get() {
    int tmp = buffer[use];     // g1
    use = (use + 1) % MAX;     // g2
    return tmp;
}
```

put 就是往 buffer 的当前位置放一个东西，同时把 fill 指针往前移一个（循环缓冲区，所以要对 MAX 取模）；get 就是从当前位置取一个东西，同时把 use 指针也往前移一个。

如果所有 producer 的代码和所有 consumer 的代码都一次性地运行结束，那就不会出现冲突问题，它可以正常工作。问题就在于 producer 和 consumer 可以并发地运行：并发运行就意味着 producer 的这几行代码跟 consumer 的几行代码可以交替运行，而交替运行就可能带来一个问题——对共享变量的访问可能因为顺序不一样，导致它判定的条件不一样。

### 10.2 只用 empty/full 做同步的第一版

第一版的思路只用两个信号量做同步：`empty` 表示空闲槽位数，初值 MAX；`full` 表示已填入的槽位数，初值 0。

```c
sem_t empty;
sem_t full;

void *producer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        sem_wait(&empty);   // P1
        put(i);             // P2
        sem_post(&full);    // P3
    }
}

void *consumer(void *arg) {
    int i, tmp = 0;
    while (tmp != -1) {
        sem_wait(&full);    // C1
        tmp = get();        // C2
        sem_post(&empty);   // C3
        printf("%d\n", tmp);
    }
}

int main() {
    sem_init(&empty, 0, MAX);  // MAX 个缓冲区一开始都是空的
    sem_init(&full, 0, 0);     // 0 个是满的
}
```

生产者先 wait empty（有空位才写），写完 post full（告诉消费者有东西了）；消费者先 wait full（有东西才取），取完 post empty（告诉生产者有空位了）。

那么如果不止一个生产者、不止一个消费者呢？

### 10.3 多生产者暴露的互斥缺失

当 MAX 大于 1、且有多个生产者时，竞态条件会发生在 f1 这一行：多个生产者可能同时判断出「有多个空位」，于是同时执行 `buffer[fill] = value`，写到同一个位置去，旧的数据就被覆盖了。也就是说，我们忘掉的是互斥：填充缓冲区、递增索引这两件事是一个临界区。

所以第一版的问题很清楚：只有同步、没有互斥。

### 10.4 在外层加大锁导致死锁

于是很自然地想到加一个互斥量 `mutex` 来保护缓冲区。但加在哪里很关键。一个错误的写法是把大锁加在最外层：

```c
void *producer(void *arg) {
    for (i = 0; i < loops; i++) {
        sem_wait(&mutex);   // p0（新加）
        sem_wait(&empty);   // p1
        put(i);             // p2
        sem_post(&full);    // p3
        sem_post(&mutex);   // p4（新加）
    }
}

void *consumer(void *arg) {
    for (i = 0; i < loops; i++) {
        sem_wait(&mutex);   // c0（新加）
        sem_wait(&full);    // c1
        int tmp = get();    // c2
        sem_post(&empty);   // c3
        sem_post(&mutex);   // c4（新加）
        printf("%d\n", tmp);
    }
}
```

老师在这里先请大家自己判断这个写法行不行，然后带着大家逐句读了这段代码：生产者首先去获得大锁，获得以后判定是不是有空的位置，有空位就往里面放，接着把 full 的值加 1（目前放了一个东西，取的人可以来取了），然后把大锁释放掉。消费者也是这样：加大锁、wait full、取一个、post empty、释放大锁。

这个操作会有什么问题？问题最主要就是：消费者获得了一个互斥量以后，这时候里面是没东西的（缓冲区为空），但它已经获得了访问缓冲区的权限；这时候它被切换到生产者那边，生产者又在等待这个互斥量，于是它也生产不了、往里面放不了东西。这样一个在那里空等、一个又放不了东西，大家都执行不下去——这就是**死锁**（deadlock），就卡在这里了。

> **老师强调**：在外层加这个大锁是不合理的。它会导致某一个生产者或某一个消费者获得了大锁，但生产者想往里面放的时候放不进去。

这个死锁的机制值得单独记一笔：消费者持有 mutex 去等 full，而生产者需要 mutex 才能往里放东西、从而让 full 变成正数——互相等待，形成环。

### 10.5 正确的加锁位置

解决的办法是把锁尽量放到靠近被保护操作最近的位置，也就是把对缓冲区的互斥操作范围缩到最小，不要去额外扩大范围——扩大范围就意味着有可能会出现不可预期的情况。

于是改成：

```c
void *producer(void *arg) {
    for (i = 0; i < loops; i++) {
        sem_wait(&empty);   // p1
        sem_wait(&mutex);   // p1.5（移到这里）
        put(i);             // p2
        sem_post(&mutex);   // p2.5（移到这里）
        sem_post(&full);    // p3
    }
}

void *consumer(void *arg) {
    for (i = 0; i < loops; i++) {
        sem_wait(&full);    // c1
        sem_wait(&mutex);   // c1.5（移到这里）
        int tmp = get();    // c2
        sem_post(&mutex);   // c2.5（移到这里）
        sem_post(&empty);   // c3
        printf("%d\n", tmp);
    }
}

int main() {
    sem_init(&empty, 0, MAX);
    sem_init(&full, 0, 0);
    sem_init(&mutex, 0, 1);   // mutex = 1，因为它是一把锁
}
```

现在生产者先去判定是不是有空位置可写：如果有空位，才去锁定缓冲区、往里面写；写完以后把缓冲区释放掉，同时再通知消费者「我生产了一些东西，你可以来取了」。消费者同理。

这个代码是可以的，它不会造成刚才讲的那个死锁问题——因为等待 empty/full 的时候并没有持有 mutex。

所以这个例子给出了一个通用原则：**同步信号量的 wait 放在互斥量之前，互斥量只包住真正访问共享数据的那几条语句**。

## 十一、经典同步问题之二：读者–写者 [02:20:09–02:27:12]

### 11.1 读者–写者的语义

读者–写者和生产者–消费者略有不同：它允许多个线程对某个变量进行读，同时只允许一个线程对它进行写。

这也是符合常识的：某一个变量是允许并发地读的，要读的话没有问题；但是写，同一时间只能一个人写。

所以规则是：

1. 有人读的时候，不能去写，直到所有人都读完以后才能写。
2. 写的时候不能有人读，也不能有人写。
3. 已经有读者在读时，后来的读者可以直接进入。

这是一个非常经典的锁，常用来实现对共享变量的读写并发操作。

### 11.2 数据结构

实现读写锁用一个比较简单的结构：

```c
typedef struct _rwlock_t {
    sem_t lock;        // 二进制信号量，保护 readers 计数
    sem_t writelock;   // 允许一个写者或多读
    int readers;       // 临界区内正在读的读者数
} rwlock_t;

void rwlock_init(rwlock_t *rw) {
    rw->readers = 0;
    sem_init(&rw->lock, 0, 1);
    sem_init(&rw->writelock, 0, 1);
}
```

初始化时把读者计数置 0，两个信号量的初值都是 1。

### 11.3 读者与写者的加解锁

读者获得读锁：

```c
void rwlock_acquire_readlock(rwlock_t *rw) {
    sem_wait(&rw->lock);
    rw->readers++;
    if (rw->readers == 1)
        sem_wait(&rw->writelock);   // 第一个读者去拿写锁
    sem_post(&rw->lock);
}
```

老师的解读是：首先获得这把保护读者计数的锁，然后把当前读者数加一；如果当前读者数变成 1，说明以前没有人读，这时是需要去获得写锁的——因为你是第一个来读的人，第一个来读的人要判定一下里面有没有写的人：如果有写的人就在这里等；如果没问题，就对 readers 的修改完成、释放这把锁。

读者释放读锁：

```c
void rwlock_release_readlock(rwlock_t *rw) {
    sem_wait(&rw->lock);
    rw->readers--;
    if (rw->readers == 0)
        sem_post(&rw->writelock);   // 最后一个读者释放写锁
    sem_post(&rw->lock);
}
```

我是读者要释放：首先获得修改 readers 变量的权限，把 readers 减 1；减完以后如果变成 0，就说明我是最后一个，最后一个就必须去把写锁释放掉，让其他写的人来写；然后把保护 readers 的那把锁释放掉。

写者就简单了，因为它不需要考虑其他问题：

```c
void rwlock_acquire_writelock(rwlock_t *rw) {
    sem_wait(&rw->writelock);
}
void rwlock_release_writelock(rwlock_t *rw) {
    sem_post(&rw->writelock);
}
```

老师总结了这个代码的核心：最大难处就是读的时候要判断一下当前是第几个读者。如果是第一个读者，你必须去获得写锁；如果不是第一个读者，说明已经有其他读者获得这个权限了，你就不要去获得。如果你是最后一个读者，你必须把写锁释放掉；如果还有多个读者，说明你不是最后一个，你就不需要释放——因为还有人在读，你就不能把写的权限释放掉。

所以读写者问题的代码核心在于：读者的获得与释放，和写者的获得与释放，它们的逻辑是不一样的。

### 11.4 公平性问题

这个锁有一个最大的问题，就是**公平性**问题。

看刚才那个代码，最大的问题就是：只要有人在读，写的锁就一直不会释放。所以当一个写者来的时候，只要有人不断地来读，你就永远不能去写，这就是公平性问题。这个代码对写者来讲是不太公平的——只要有读的人一直不断地来读，写者就永远拿不到写的权限。

怎么解决这个公平性问题呢？可以修改它的代码来解决。老师把「写一个保证写者公平的代码」留成了作业（详见课程事务一节）。

## 十二、经典同步问题之三：哲学家就餐 [02:27:19–02:34:52]

### 12.1 问题设定

哲学家就餐是一个非常经典的问题：五个哲学家围着桌子坐，桌上一共只有五把叉子。哲学家有时候思考（不需要叉子），有时候要吃东西；吃东西需要同时拿起左右两边的两把叉子。

这个问题是著名计算机科学家 Dijkstra 提出来的。老师顺带提到：Dijkstra 提了很多算法、也提了很多问题，最知名的就是我们这个最短路算法，也是他提出来的。

老师补充了一个更直观的说法：用筷子的例子更好一点——每个人左边有一只筷子，他要吃东西必须把左右两边的筷子同时拿起来，才能凑成一双筷子来夹东西吃。

这个问题的要求是两条：不能有死锁（no deadlock），也不能有哲学家饿死（no starvation），也就是不能有人永远吃不到。

每个哲学家的基本循环是：

```c
while (1) {
    think();
    getforks();
    eat();
    putforks();
}
```

**补充说明**：根据本节补充材料《31. Semaphore》第 26 张幻灯片，哲学家 $p$ 的左右叉子编号写作 $\mathrm{left}(p)=p$、$\mathrm{right}(p)=(p+1)\bmod 5$，即第 4 位哲学家的右手边绕回到第 0 把，正好把五个人围成一个圈。字幕只讲了「拿起左右两边的叉子」，没有给出这个编号公式，故按材料补全。

### 12.2 朴素实现与死锁

最直接的做法是给每把叉子一个信号量 `sem_t forks[5]`，初值都是 1：

```c
void getforks() {
    sem_wait(forks[left(p)]);
    sem_wait(forks[right(p)]);
}
void putforks() {
    sem_post(forks[left(p)]);
    sem_post(forks[right(p)]);
}
```

这个实现会发生死锁。老师讲的场景是：如果正好每个人都先拿起他左边的那把叉子，那么他再去拿右边的就拿不到了，因为右边那把已经被右边的人拿走了。这样每个人拿了一把叉子、又想去获得另外一把叉子，就永远维持下去了——所有哲学家都吃不到东西，这就是死锁。

> **老师提示**：什么是死锁，后面会有专门的章节详细讲。

死锁发生以后，就意味着所有的哲学家都不能运行下去，都在这里等着。

### 12.3 打破循环等待

第一个解决办法是一个比较巧的设计：原来的话每个哲学家都是先拿左边后拿右边，那么我们让其中一些哲学家先拿右边再拿左边，这样就可以解决这个问题了。

课堂上老师指定的是一位哲学家改变顺序（他口述为「第四个哲学家」，代码里对应 $p=4$，即最后一位）：让 4 号哲学家先拿右、后拿左。老师解释说：先拿右后拿左就意味着至少有一个哲学家不会去形成这个死锁，因为他的第一把叉子和别人的第一把叉子方向相反；这样至少有一个哲学家能够吃到东西，只要有人吃完了以后就会把叉子放下来，资源就会变多，于是就不会出现死锁。

**补充说明**：根据本节补充材料《31. Semaphore》第 28 张幻灯片，代码上写成 `if (p == 4) { sem_wait(forks[right(p)]); sem_wait(forks[left(p)]); } else { sem_wait(forks[left(p)]); sem_wait(forks[right(p)]); }`，即把「最后一位哲学家」的取叉顺序反过来，从而打破等待环。

### 12.4 其他解法

老师接着列了另外几种解法：

1. **奇偶分工**：奇数号的哲学家先拿左边，偶数号的先拿右边。这其实是上一种解法的一个变体。
2. **多给一把叉子**：一共六把叉子。这很简单，因为五个人、六把叉子，至少有一个人可以拿到两把，他吃好以后把两把都放下，让其他人接着吃。
3. **限制人数**：限制最多有四个人同时吃饭，这样总有一个人能拿到一双（两把叉子）。
4. **拿不到就放下**：如果拿不到两把叉子，你必须把已经拿到的资源释放掉——不能拿着一把叉子一直在这里等；拿不到两把就放掉。

老师最后总结：哲学家就餐问题本质上就是一个互斥访问资源的问题，你需要解决的是在访问的时候有足够数量的资源来保证这些哲学家能够使用。

## 十三、通用化习题：N 个线程、M 个实例、R 个需求 [02:34:53–02:39:42]

### 13.1 题目

老师把哲学家问题抽象成一个通用的练习。

**例题**：

**题目**：现在有 N 个线程要竞争一种资源，这种资源总共有 M 个实例（就像叉子这个资源有 M 把叉子），每个线程需要 R 个实例（每个哲学家需要两把叉子）。如果想要这个系统不出现死锁，这几个变量应该满足什么条件？

**解答**：考虑最极端的情况，也就是临界点——所有线程恰好都只差一个实例就能运行完：每个线程都已经持有 $R-1$ 个实例，一共被占用了 $N(R-1)$ 个。这时资源池里如果还剩 1 个实例，就必然有一个线程能凑齐 $R$ 个、运行结束，并把它持有的全部实例释放出来，于是其他线程依次也能凑齐。所以临界点就是

$$M \ge N(R-1) + 1$$

只要 M 达到这个值，就不会出现「所有人都差一个、谁也动不了」的僵局；反之，如果 $M \le N(R-1)$，就可能出现每个线程各持 $R-1$ 个、谁也不放手的情形，也就是死锁。

**结果与点评**：把这个条件代回哲学家就餐问题，N = 5、R = 2，得到 $M \ge 5 \times (2-1) + 1 = 6$。这正好印证了前面的结论：五把叉子不够（$5 < 5 \times 1 + 1$，可能死锁），六把叉子就够（$6 = 5 \times 1 + 1$，无死锁）。老师点评说：本质就是考虑一个最极端的情况，也就是所有线程都恰好只差一个实例；哲学家就餐问题其实本质上就是这个问题的一个特例，只不过这里把它通用化了。

### 14.2 互斥与同步的写法差异

用信号量实现互斥和实现同步，在写法上是不一样的：

- 实现互斥：`wait` 和 `post` 在**同一个线程**里成对出现，包住临界区。
- 实现同步：`wait` 和 `post` 分别出现在**两个不同的线程**里。

> **老师总结**：如果大家想更好地理解，就用生产者–消费者的例子来理解。生产者–消费者里用了三个信号量：一个是**用作互斥**的，就是对缓冲区的访问，同一时间只有一个线程访问缓冲区；另外有两个**同步信号量**，一个是 full，用来同步消费者（只有 full 里有东西的时候你才能从里面取东西），一个是 empty，用来同步生产者（只有 empty 有空的时候你才能生产）。

### 14.3 必须掌握的三个经典问题
