## 一、课程定位与学习目标 [00:02:52–00:07:07]

### 1.1 课程不是学习“如何使用操作系统”

**定义**：**操作系统**（Operating System, OS）是位于计算机硬件与上层应用之间、负责管理和抽象硬件资源，并向上层提供服务的平台性软件。

操作系统既需要理解底层硬件的能力，也需要理解上层应用的需求。它把硬件的计算、存储和 I/O 能力组织起来，转换成应用能够使用的接口。因此这门课讲的是操作系统内部怎样工作，而不是单纯学习 Windows、Linux 或 macOS 的命令和图形界面。

课程目标主要有两类：

1. 理解操作系统的概念、结构和核心工作机制，形成对系统内部原理的认识。
2. 理解操作系统设计中的取舍，例如资源利用率与性能、通用性与复杂度、功能与能耗之间的平衡。

> **老师强调**：学习操作系统，不是学“怎样使用 OS”，而是理解“OS 怎样工作”。

老师引用“不闻不若闻之，闻之不若见之，见之不若知之，知之不若行之”，强调这是一门偏系统的课程，必须把思考与动手结合起来；AI 可以辅助二者，但不能代替自己的理解和实践。

课程采用 *Operating Systems: Three Easy Pieces*（常简称 OSTEP，中译名通常为《操作系统导论》）作为教材。该书有公开电子版，不需要购买纸质教材。

### 1.2 操作系统处在软硬件的中间层

操作系统常被概括为“软硬兼施”：向下要面对 CPU、内存、磁盘、网络等异构硬件；向上要为应用程序提供稳定、统一的运行环境。它要回答两个方向的问题：

- 硬件有哪些能力，怎样把这些能力安全、高效地调度起来；
- 应用提出什么需求，怎样把这些需求映射到硬件能够完成的操作上。

因此，操作系统不是一个只关心某一类应用的软件，而是提供通用底层能力的系统软件。它的设计往往不是追求单一指标最优，而是在多个彼此冲突的目标之间寻找平衡。

## 二、AI 时代下操作系统课程的教学重构 [00:18:10–00:48:03]

### 2.1 AI 对传统课堂和知识传授的冲击

老师从教师群中的一段讨论引入：本科课程中按时到课人数减少，学生更倾向通过实践平台学习真实技术、通过回放和资料复习，并把 PPT 直接交给大模型梳理。其结果是，教师在知识传授环节不再是学生的唯一来源，甚至不一定是首选来源。

传统教学模式主要发生在教师和学生之间：教师处在较权威的位置单向讲授，学生在课堂中相对被动地接收知识。大模型出现后，教学关系变成“教师—学生—AI”的三元结构。AI 的知识面、调用便利性和个性化回答能力，使“老师讲、学生听”的单一模式受到冲击。

老师认为，应对方式不应是“学生用 AI、老师也用 AI 来互相检测”的对抗模式，而应当是让 AI 成为学习和评价全过程的辅助工具。教师的工作重点要从知识传授转向任务设计、学习引导和能力评估；学生则要从被动接收转向主动构建知识体系。

> **老师强调**：教学不是老师和学生之间的对抗，也不是比较谁使用的大模型更厉害，而是借助 AI 真正培养出底层理解和系统能力。

> **老师强调**：不要与时代浪潮对抗，应当顺应 AI 的发展，用它去辅助知识构建和能力评估，同时培养驾驭 AI 的能力。

### 2.2 从知识传授转向能力培养

课程采用的教学指导思想是把学习目标从“知道概念”推进到“能够理解、设计、验证和解释系统”。除了基础知识，还要培养批判性思维、全球视野、复杂问题求解能力、研究能力以及跨学科协作能力。

现有操作系统教学原本以理论与实践结合为主线：

- 通过课堂讲授基本概念、原理和算法；
- 以 Linux、Windows 等典型系统作为案例，理解真实系统中的模块与工作机制；
- 通过翻转课堂、在线课程和讨论课补充课堂学习；
- 通过模块化实验逐步搭建一个可以工作的操作系统内核。

在没有大模型时，这种“自己编程、自己调试、逐步完成内核”的方式能够有效训练系统能力。但在有 AI 后，如果学生只是把 xv6 一类实验的需求、代码和报告全部交给大模型，虽然可以得到可运行结果，却可能出现三个问题：

| 问题 | 含义 |
|---|---|
| 认知遮蔽（Cognitive Masking） | 可运行代码和生成报告制造出“已经掌握原理”的假象，学生未必理解机制。 |
| 过程破坏（Process Disruption） | 编程、调试和从错误中迭代的链路被 AI 代替，资源约束设计和系统思维得不到训练。 |
| 评价盲区（Assessment Blindness） | 传统上“代码能运行、报告已提交”就能得分，但无法证明学生真正理解。 |

### 2.3 AI 使用的原则与实验改革

课程鼓励使用 AI，但不提供 token，也不限制必须使用哪一种模型或工具。AI 可以用于梳理知识、辅助设计、编写代码、生成测试和完成报告，但学生必须对提交结果负第一责任。

**定义**：**Vibe Coding** 指以自然语言和高层意图驱动大模型生成、修改、调试代码的编程方式。其优势是提高开发速度，但如果没有验证和理解，容易把系统能力训练变成“复制结果”。

实验改革的基本思路是“允许 AI 参与，同时要求学生解释和验证”：

1. 任务从简单复现转向具有真实约束的系统问题，教师负责把目标和边界定义清楚。
2. 鼓励学生用测试用例驱动开发。学生不只接受 AI 给出的实现，还要主动设计正常用例、边界用例和异常用例，检验 AI 生成的代码。
3. 评价不只依据最终代码和报告，还要进行过程复盘和深度答辩，要求学生解释“为什么这样设计”“为什么能够工作”“在什么条件下会失败”。
4. 对 AI 生成的代码和报告，学生要能够定位错误、判断不足，并能给出修改依据。

> **老师强调**：个人是 AI 结果的第一责任人。AI 可以帮你做事，但你必须验证结果，并对“为什么这样做”给出自己的解释。

老师还举了“二传手”的比喻：如果老师把题目交给学生，学生立刻交给大模型，大模型返回结果后再原样交给老师，学生只是信息转发者，没有发生真正的学习和训练。

## 三、计算机系统结构与操作系统的地位 [00:57:48–01:17:07]

### 3.1 计算机系统的四个组成部分

计算机系统可以划分为硬件、操作系统、应用程序和用户四部分。

| 组成部分 | 主要职责 | 典型例子 |
|---|---|---|
| 硬件（Hardware） | 提供底层计算资源 | CPU 提供算力，内存和磁盘提供存储，网卡和**输入/输出**（Input/Output, I/O）设备提供输入输出。 |
| 操作系统 | 控制并协调硬件资源，为应用和用户提供服务 | Linux、Windows、macOS、Android、iOS。 |
| 应用程序（Application Program） | 利用系统资源解决具体领域问题 | 文字处理器、编译器、浏览器、数据库、视频播放器。 |
| 用户（User） | 使用系统完成具体任务，也可能是其他机器或系统 | 人、机器、其他计算机系统。 |

四者之间不是简单堆叠：硬件提供能力，操作系统把能力编排成服务，应用程序利用服务解决问题，用户最终通过这些应用使用系统。

### 3.2 为什么必须要有操作系统

**定义**：操作系统是应用和硬件之间的中介，向下管理硬件，向上提供标准化接口。

最根本的动机来自硬件和应用的异构性。假设有 $M$ 种应用程序、$N$ 种硬件架构，如果没有操作系统，每一种应用都要分别适配每一种硬件，开发者需要维护 $M\times N$ 套版本。操作系统把硬件差异封装起来，向上提供统一接口，于是应用只需要面向一种接口开发，操作系统再分别适配不同硬件，整体复杂度降为 $M+N$。

这个抽象带来三方面价值：

1. **标准化接口**：应用面向统一 API 开发，例如 Windows 的 Win32 API、类 Unix 系统的 POSIX API。
2. **硬件管理**：统一管理 CPU、内存、磁盘和其他 I/O 资源。
3. **多任务调度**：让多个程序在同一台机器上并发运行，并决定谁先运行、运行多久。
4. **资源请求响应**：应用程序可以在运行过程中动态申请内存或其他资源，以提高资源利用率。
5. **访问控制**：判断某个用户或进程是否有权访问某项资源，处理认证、权限和隔离问题。

> **老师总结**：操作系统是一个承上启下的中间层。向下管理和抽象硬件，向上提供方便、统一的服务，因此它位于整个计算机系统的核心位置。

### 3.3 程序怎样运行，操作系统为何要提供运行环境

程序的本质是一组存储在内存中的指令。处理器按照程序规定的顺序执行“取指—译码—执行—写回结果—取下一条指令”的循环。

操作系统本身不改变“程序是指令序列”这一事实，它的作用是提供正确的运行环境和资源分配机制，使指令能够被安全地执行，使程序能够与其他资源交互，并尽可能减少资源浪费和运行时间。

操作系统总体上追求两个目标：

- **正确性**（Correctness）：程序按照预期方式运行，得到确定、可信的结果。
- **有效性**（Efficiency）：资源得到高效利用，系统运行时间、开销和浪费受到控制。

在此基础上，操作系统还要让用户程序更容易编写、让计算机更容易使用、让硬件使用得更高效。

## 四、资源抽象、虚拟化与系统调用 [01:17:07–01:39:06]

### 4.1 操作系统是资源管理器

**定义**：**虚拟化**（Virtualization）是把一个物理资源抽象成多个逻辑资源，使不同使用者能够共享底层能力的技术。

操作系统管理的典型资源包括：

- **中央处理器**（Central Processing Unit, CPU）：计算资源；
- **内存**（Memory）：运行时的指令和数据存储；
- **磁盘**（Disk）：持久存储和文件系统；
- **I/O 设备**：键盘、显示器、网卡、控制器等输入输出设备。

资源管理的直接目标是提高利用率。一个基本办法是提高并发度，允许多个程序同时使用资源。对于 CPU，采用多个程序轮流使用的共享方式；对于内存，采用多个进程分别占用不同空间的方式；对于设备，则提供共享访问和设备抽象。应用程序使用 CPU 时通常被抽象为**进程**（Process）；同一进程内可以包含多个执行流，即**线程**（Thread）。

### 4.2 系统调用与应用编程接口

操作系统把底层能力抽象成**系统调用**（System Call），并通过 **应用编程接口**（Application Programming Interface, API）暴露给应用。系统调用是操作系统核心能力的入口；API 往往在系统调用之上继续封装，使程序员使用起来更简单、更统一。

例如，应用要申请内存、打开文件、读写数据或退出程序，最终都需要通过系统调用请求操作系统服务。API 隐藏了系统调用的细节，因此同一个 API 可以在遵循相同标准的系统上使用，而不用让上层程序直接理解每台机器的底层实现。

**补充说明**：这里应把字幕中的“system core”理解为 system call，把“process 接口”结合上下文校正为 POSIX 接口。

### 4.3 CPU 虚拟化：时分复用

操作系统希望把物理上只有一个或少量 CPU 的机器表现得像有很多个 CPU，让每个进程都仿佛有自己专用的处理器。最基本的办法是把 CPU 时间切成多个时间片，让不同进程轮流运行。

**定义**：**时分复用**（Time-Division Multiplexing, TDM）是把同一个物理资源按时间划分给不同使用者，使多个进程交替占用 CPU 的机制。

例如，一台电脑同时运行文字处理器和音乐播放器。看起来两个程序都在同时工作，实际上 CPU 在它们之间快速切换。只要切换足够快，人感受不到中断，就形成了并发运行的体验。

> **老师比喻**：只有一辆自行车却多个人要用，最直接的办法就是大家轮流骑一会儿；CPU 的时分复用也是同一个逻辑。

**演示**：幻灯片中的 `cpu.c` 程序会循环打印字符。只有一个程序运行时，输出节奏较确定；多个程序同时运行时，打印内容会交错，说明多个进程看起来在“同时”运行，实际上是 CPU 在快速轮换。

要让多个进程轮流使用 CPU，操作系统必须回答调度问题：谁先运行、每个进程运行多久、何时切换、切换时怎样保存和恢复现场。因此，虚拟化只提供了并发运行的可能性，还需要调度机制规定资源如何分配。

### 4.4 内存虚拟化：空分复用

内存可以被抽象为一段连续的字节空间。与 CPU 不同，内存不适合频繁地在程序之间来回换出换入，因为每次切换都要搬运大量数据，开销很大。因此，内存主要采用**空分复用**（Space-Division Multiplexing, SDM）：不同进程分别拥有自己的虚拟地址空间，由操作系统映射到物理内存的不同区域。

**定义**：**虚拟内存**（Virtual Memory, VM）是操作系统为进程提供的逻辑存储抽象；进程看到独立、连续的地址空间，而实际数据按**页面**（Page）映射到物理内存。

**定义**：**虚拟地址空间**（Virtual Address Space）是进程看到的连续、独立的逻辑地址范围。进程不需要知道这些地址最终位于哪些物理内存单元；映射和隔离由操作系统与硬件共同完成。

虚拟地址空间的大小由地址位数决定：

$$2^{32}\text{ B}=4\text{ GiB},\qquad 2^{64}\text{ B}=16\text{ EiB}.$$

32 位进程的理论地址空间约为 4 GiB，64 位进程的理论地址空间更大。但进程不会、也不需要把整个地址空间同时放进物理内存。程序具有局部性：在某一时刻通常只执行某个区域的代码、访问某个区域的数据，因此操作系统只需把当前真正需要的页面驻留到物理内存。

**演示**：内存程序 `mem.c` 反复读取和写入某个地址。幻灯片示例在关闭地址空间随机化（Address Space Layout Randomization, ASLR）后多次运行程序，显示它们都访问相同的虚拟地址（例如 `0x00200000`），但彼此的修改不会互相影响。这说明每个进程看到的是自己的私有虚拟地址空间，操作系统负责把它们映射到不同的物理空间。

> **老师强调**：每个进程都有自己的完整虚拟地址空间，但虚拟空间是稀疏使用的；物理内存只需保存当前活跃的部分。

## 五、并发与共享资源 [01:39:06–02:13:10]

### 5.1 为什么并发需要额外机制

虚拟化让多个进程可以在同一台机器上交替运行，但只允许并发还不够。操作系统还要协调多个执行单元对共享资源的访问顺序、访问时长和同步关系。否则，多线程程序可能在看似正确的代码上产生不可重复、甚至错误的结果。

**定义**：**并发**（Concurrency）是指多个执行单元在一段时间内交替推进。它们可能访问同一块内存或同一个共享变量，因此执行顺序会影响最终结果。

### 5.2 两个线程共同增加计数器的例子

**例题**：两个线程共享一个全局计数器 `counter`，每个线程循环执行 `counter++`。若两个线程各循环 1000 次，理论上结果应当是 2000；若各循环 100000 次，理论上结果应当是 200000。实际运行中，结果是否一定正确？

**题目**：

```c
static volatile int counter = 0;
int loops;

void *worker(void *arg) {
    for (int i = 0; i < loops; i++) {
        counter++;
    }
    return NULL;
}

int main(int argc, char *argv[]) {
    loops = atoi(argv[1]);

    pthread_t p1, p2;
    printf("Initial value: %d\n", counter);

    pthread_create(&p1, NULL, worker, NULL);
    pthread_create(&p2, NULL, worker, NULL);

    pthread_join(p1, NULL);
    pthread_join(p2, NULL);

    printf("Final value: %d\n", counter);
    return 0;
}
```

**解答**：`counter++` 在高级语言中是一行，但编译成机器指令后不是原子操作。它至少包含三步：

```asm
mov   counter, %eax   # 从内存读出 counter
add   $1, %eax        # 寄存器中的值加一
mov   %eax, counter   # 写回内存
```

假设 `counter` 初始值为 1，两个线程都要把它加一。若执行顺序是 P1 完整执行三步，P2 再完整执行三步，则结果为 3。但 CPU 可以在三条指令之间切换线程，于是可能出现：

1. P1 读到 1，放入自己的寄存器；
2. 切换后，P2 也读到 1；
3. P1 计算得到 2，并写回 `counter`；
4. P2 用先前读到的 1 计算得到 2，再写回 `counter`；
5. 两个线程都执行了加一，但最终 `counter` 仍为 2，而不是 3。

**结果与点评**：当 `loops = 1000` 时，程序可能“运气较好”，没有在关键位置切换，得到预期的 2000。当 `loops = 100000` 时，运行时报告的结果可能约为 14 万或 13 万，低于预期的 20 万；不同次运行还可能得到不同结果。这个例子说明，并发提高资源利用率的同时，会引入由共享变量和非原子访问造成的正确性问题。

**定义**：**原子性**（Atomicity）是指一组操作要么全部完成、要么完全未执行，中间不能被其他线程观察到或插入执行。

**定义**：**竞争条件**（Race Condition）是指多个执行单元对共享数据进行非同步访问，最终结果依赖它们的具体执行时序。

操作系统解决这类问题的典型手段包括锁、原子指令等同步机制。并发机制的目标不是阻止并发，而是在并发的前提下保证共享资源访问的互斥、顺序和正确性。

> **老师强调**：虚拟化只是提供了“可以让多个程序同时运行”的能力，真正保证结果正确，还必须依靠额外的并发控制机制。

## 六、持久性与文件系统 [02:13:11–02:22:10]

### 6.1 什么是持久性

**定义**：**持久性**（Persistence）是指数据或信息的生命周期长于创建它的进程，并且在断电、重启或进程结束后仍然能够保存和再次读取。

内存通常依赖 DRAM 等易失性介质，断电后内容丢失。为了让数据在断电后继续存在，需要把信息保存到硬盘、SSD 等非易失性存储设备，并由**文件系统**（File System）管理这些设备上的空间。

持久化需要软硬件共同完成：

- 硬件提供真正的非易失存储介质，例如**机械硬盘**（Hard Disk Drive, HDD）和**固态硬盘**（Solid-State Drive, SSD）；
- 软件把存储设备抽象成文件、目录和访问接口，负责空间分配、地址映射、读写控制和权限控制。

持久性还要面对异常和故障：如果写入过程中断电，文件系统必须尽量保证元数据和文件内容一致；日志（Journaling）可以把关键写操作先记录下来，以便故障后恢复。延迟写、写回（Write-back）等机制则用于提高性能，但必须同时处理一致性和数据丢失风险。

### 6.2 文件系统怎样抽象磁盘

**演示**：程序要在一个文件中保存字符串，典型操作是：

1. 打开或创建目标文件；
2. 循环调用读写接口，把内容写入文件；
3. 关闭文件，使相关状态和元数据得到整理。

例如向 `/tmp/file` 写入 `"hello world"`，应用通常调用 `open`、`write`、`close` 等接口；这些接口最终被路由到操作系统中的文件系统，由文件系统负责分配磁盘块并完成实际读写。

文件系统至少要解决两个基本问题：

- 文件内容应该存放在磁盘的哪些位置；
- 访问文件时，怎样根据文件名和偏移量找回对应内容。

因此，文件系统的基本能力包括磁盘空间分配、文件读写、目录组织以及访问控制；在基本能力之外，还提供日志、恢复、缓存和延迟写等增强机制。

## 七、操作系统的设计目标与演进 [02:22:10–02:36:56]

### 7.1 抽象是处理复杂系统的核心方法

**定义**：**抽象**（Abstraction）是隐藏底层实现细节、只暴露稳定接口和必要语义的过程。

抽象的基本思路是分而治之：先建立系统的架构性理解，再把复杂功能分解成若干相互独立的小问题，通过逐层接口把问题拆开。标准 API 是一种抽象，操作系统通过 API 把硬件的复杂细节隐藏起来，应用只需要理解接口的语义。

计算机网络的分层也是抽象：IP 层不需要直接面对物理硬件，只需要通过相邻链路层的接口工作；每层只暴露有限的抽象，最终把复杂通信问题分解成多个可解决的问题。操作系统同样把文件、进程、虚拟内存、设备等抽象提供给应用。

理解操作系统还可以从三个维度展开：它向外提供的服务、面向用户和程序员提供的接口，以及内部各模块的组成与相互关系。

抽象的直接收益是解耦：应用不再依赖具体硬件，操作系统负责把统一接口映射到多种硬件；开发者只学习一套接口，硬件只需要实现相应的驱动和适配层。

### 7.2 操作系统的多维设计目标

操作系统设计既追求资源利用率，也追求性能。虚拟化必须尽量降低开销，不能为了支持更多并发而使应用明显变慢。

其他目标包括：

| 目标 | 含义 |
|---|---|
| 性能（Performance） | 减少虚拟化、调度、系统调用和 I/O 的开销，保证应用响应时间。 |
| 保护与隔离（Protection and Isolation） | 一个进程不能读取或破坏另一个进程的空间，故障不能无边界扩散。 |
| 可靠性（Reliability） | 系统长期运行而不崩溃，能够应对异常和局部故障。 |
| 能耗效率（Energy Efficiency） | 手机、嵌入式和物联网设备必须控制发热和功耗，不能只追求性能。 |
| 安全性（Security） | 对关键场景进行认证、访问控制和外部攻击防护。 |
| 移动性（Mobility） | 支持手机、物联网和其他移动设备的资源约束与运行方式。 |

这些目标经常相互冲突，因此操作系统设计是典型的工程权衡：既要提高并发，又不能让调度开销过大；既要提供保护，又要保留高效率；既要通用，又要针对场景优化。

### 7.3 从早期计算机到具身智能

早期计算机曾使用磁带机等设备，只有非常简单的抽象，甚至没有现代意义上的操作系统。随着 PC 出现，DOS、Windows、macOS 等系统逐步发展；智能手机时代出现 iOS、Android；汽车、机器人、工厂设备甚至战斗机都需要各自的实时或专用操作系统。

面向 AI 和具身智能的设备进一步改变了操作系统需求：硬件形态不同，任务可能要求实时性、轻量化和确定性，资源管理的目标也与通用 PC 不同。因此操作系统不会因为技术发展而消失，反而会在新硬件、新应用和新约束下持续演进。

> **老师总结**：只要有硬件和软件，就需要操作系统在中间解决抽象、资源利用和安全问题。无论技术怎样变化，操作系统都处在软硬件之间最关键的位置。

## 八、操作系统服务、系统调用与 API [02:36:56–02:43:33]

### 8.1 操作系统提供哪些服务

从服务角度看，操作系统通常提供：

1. **用户接口**：命令行接口（Command-Line Interface, CLI）以及图形用户界面（Graphical User Interface, GUI）。图形界面更易于普通用户使用，命令行则更适合需要批量、自动化和精细控制的开发者。
2. **程序执行**：为程序提供运行容器，创建进程、分配资源、调度执行并完成终止和回收。
3. **I/O 操作**：统一管理设备输入输出，隐藏不同控制器和设备协议的差异。
4. **文件系统服务**：创建、打开、读写、关闭和删除文件，组织目录和管理权限。
5. **通信服务**：支持进程间通信、共享内存、消息传递以及网络通信。
6. **错误检测与保护**：发现非法操作、越界访问、资源错误和进程间干扰，保护系统和其他程序。
7. **资源分配与记账**：在多个用户和进程之间分配 CPU、内存、存储和设备，并记录资源使用情况。
8. **保护与安全**：控制对系统资源的访问，进行用户认证，阻止外部设备或非法请求的无效访问。保护机制必须贯穿整个系统，因为系统安全性受最薄弱环节限制。

### 8.2 系统调用和 API 的关系

系统调用是操作系统面向应用程序提供的底层核心能力，例如文件操作、内存分配、进程控制和设备访问。C 语言库等运行时通常把系统调用进一步封装成 API，使应用程序使用更方便、更标准。

**例题**：实现“把一个文件复制到另一个文件”的程序。

**题目**：程序接收源文件名和目标文件名，把源文件内容复制到目标文件，并报告错误。

**解答**：程序通常需要依次完成以下动作：

1. 从命令行取得输入和输出文件名，并在必要时给出用法提示；
2. 打开源文件，若失败则输出错误并退出；
3. 创建或打开目标文件；
4. 循环从源文件读取数据，把读取到的字节写入目标文件；
5. 处理读、写和关闭过程中的错误；
6. 关闭源文件和目标文件。

**结果与点评**：从表面看，复制文件只是一个简单功能，但程序内部会调用 `open`、`read`、`write`、`close` 等系统调用或由它们封装的库函数。系统调用相对原始，参数和错误处理更细；API 在系统调用之上封装，跨平台性和易用性更好。

系统调用与 API 的分工可以概括为：

- 系统调用提供“操作系统能做什么”的核心入口；
- API 提供“程序员怎样方便、稳定地使用这些能力”的抽象；
- 同一套 API 可以在不同实现上复用，底层再映射到不同操作系统和硬件。

> **老师总结**：操作系统通过系统调用暴露核心能力，再通过 API 把这些能力包装成程序员容易使用的接口。
